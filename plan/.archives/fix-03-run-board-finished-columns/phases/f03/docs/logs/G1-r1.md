## Architecture gate G1 — decisions, revision 1 (2026-10-31)

### G1-D1 `finished_at` (plan 01)

- Column `workflow_runs.finished_at timestamptz` (nullable) in the init schema, and CHECK
  `workflow_run_finished_shape`:
  `(state IN ('succeeded','failed','cancelled')) = (finished_at IS NOT NULL)`.
- Trigger `workflow_run_finished BEFORE INSERT OR UPDATE OF state ON workflow_runs`, function
  `stamp_workflow_run_finished()`:
  - terminal `NEW.state` with a terminal `OLD.state` (UPDATE) → keep `OLD.finished_at`;
  - terminal `NEW.state` otherwise (INSERT, or entering terminal) → `clock_timestamp()`;
  - non-terminal `NEW.state` → `NULL` (retry clears it).
- Invariants: no writer sets the column. The trigger covers all 26 `UPDATE … state` statements in
  `src/adapters/persistence` without editing them. The CHECK catches any path the trigger misses.
  No existing BEFORE trigger on `workflow_runs` assigns `NEW.state` (claim retirement, state
  witness, wakeup allocation, revision, parent/association guards only read it). So the result
  does not depend on alphabetical firing order.
- Failure modes:
  - a write that sets `finished_at` without `state` (only tests, to backdate) is allowed while the
    CHECK holds;
  - `UPDATE … SET state = <same terminal>` keeps the original time;
  - a terminal-to-terminal change keeps the first finish.
- Read side moves together (persistence AGENTS §3): `RUN_COLUMNS`, `RunRow`, `run_summary`,
  `RunSummary.finished_at`.
- Verification: `run_finished_at_*` DB tests (success/failure/cancel stamp; open states none;
  retry clears and re-stamps later; an UPDATE to terminal that also sets `finished_at = NULL` is
  still stamped; a hand-written row violating the CHECK is rejected), and the run control suites.
  Run `scripts/lease-budget.sh`, because the trigger runs inside leased transitions.

### G1-D3 Board read contract (plan 02)

- **Application** (`src/application/workflow/reads.rs`):
  - `BoardWindow::{Day, Week, Month}`, default `Week`, with `duration()` and slug `parse`.
  - `RunBoardScope { binding, agent }`: the list's scope; always top-level, no state. `workflow`
    joins it in new-board-view.
  - `BOARD_COLUMN_CAP = 50`, with `const _: () = assert!(MAX_ROLLUP_PARENTS >= 6 * BOARD_COLUMN_CAP)`.
  - Port methods on `WorkflowReads`:
    - `run_board_counts(company, &scope, cutoff) -> Vec<BoardCount { state, channel: Option<Uuid>, runs: u64 }>`;
    - `run_board_cards(company, &scope, cutoff, &VisibleChannels { channels: Vec<Uuid>, company: bool }, per_column: i64) -> Vec<RunSummary>`.
- **Orchestration, in the HTTP layer** beside `Visibility` (`src/adapters/http/routes/workflows/bindings.rs`),
  as the list does in `run_page`. `visible_board(engine, company, actor, scope, window, as_of)`:
  1. cutoff = `as_of − window`;
  2. counts;
  3. `Visibility::allows` once per distinct channel (`None` → `RelatedAssociation::Company`);
  4. visible totals;
  5. cards (`per_column = BOARD_COLUMN_CAP + 1`) for the visible channels;
  6. per column, `cut = len > cap`, drop the look-ahead card, `total = max(sum, shown)`;
  7. `child_rollup` over the shown cards (≤ 300);
  8. `warn_if_run_board_is_slow`.

  It returns `RunBoard { window, cutoff, columns: [RunBoardColumn { state, cards, total, cut }], children }`.
  No transaction spans the reads: the authorization step sits between them, and a change between
  them reaches the viewer on the next wake-up (every state change notifies `workflow_run_changed`).
- **A production caller now:** `GET /api/companies/{company_id}/workflow-runs/board?binding_id&agent_id&window`.
  - It authorizes the company first; `agent_id` goes through `company_agent`, and `binding_id`
    through the company-scoped binding read (another tenant's id → not found).
  - It returns `{window, cutoff, columns: [{state, total, cut, items: [run_json + children]}]}`.
  - The route keeps `visible_board` from being dead code, matches the JSON parity of `agent_id` and
    `lineage`, and is the read new-board-view's page reuses.
  - The static `/board` segment wins over `/{run_id}`.

### G1-D4 Board statements and index (plan 02, step 5)

- **Literal states, so partial indexes apply in generic plans.** These state literals come from
  `RunStateName`, never from input.
  - Counts: the open part `state IN ('queued','running','waiting')` (the predicate of
    `workflow_runs_open_by_channel`) `UNION ALL` the finished part `finished_at >= $cutoff`. Both
    take `parent_run_id IS NULL`, the scope, and `GROUP BY state, channel_id`.
  - Cards: `UNION ALL` of six per-state subqueries, each with its literal state and
    `(channel_id = ANY($visible) OR (channel_id IS NULL AND $company_visible))`.
    - Open columns: `ORDER BY created_at, id LIMIT $n`.
    - Finished columns: `finished_at >= $cutoff ORDER BY finished_at DESC, id DESC LIMIT $n`.
- **Agent scope.** `version_id IN (versions using the agent)` as a semi-join. The board reads only
  the working set (open runs, and runs finished inside the window), never per-version ranges, so a
  child-only version costs only its working-set rows (carried f02 item).
- **Evidence.**
  - The dump gains the board statements.
  - The script seeds `finished_at` for terminal runs: the copied CHECK requires it, and the trigger
    is not copied.
  - Board shapes are measured with no finished index, then with candidates (A)
    `(company_id, finished_at DESC, id DESC) WHERE finished_at IS NOT NULL` and (B)
    `(company_id, state, finished_at DESC, id DESC) WHERE finished_at IS NOT NULL`.
  - Adopt the one whose plans read only the window, and record it in `docs/performance/run-list.md`.
    The other doc figures are refreshed after the re-run.

### G1-D5 Truncation and tripwire (plan 03)

- `RunBoardColumn { cut, total }`: `cut` comes from the cap + 1 read; `total = max(visible sum, shown)`.
- `warn_if_run_board_is_slow` (500 ms) times counts + visibility + cards + rollup. It logs:
  - `elapsed_ms`, `company_id`;
  - `binding` and `agent` as booleans, `window`;
  - `eligible_runs` (sum of all counts, hidden channels included);
  - `returned_cards`, `channels_checked`.
- The threshold decision is pure and unit-tested. The "Revisit when" readings go in run-list.md.
- F02-B1-F6: the deferred link-table plan's design gains lineage (a `top_level` column with a
  partial index).
