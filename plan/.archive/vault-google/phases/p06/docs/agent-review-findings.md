## VG-P06-B1-F2 — cancellation does not stop MCP initialization work

- **Context:** same date/workflow/role/worktree/base/digest as F1; round VG-P06-B1-R1, D1/r1.
- **Classification:** actionable, medium, lifecycle/correctness. Open. Affected reused transport behavior exposed by the new phase06 composition, not an unrelated suite failure.
- **Evidence:** `src/adapters/integrations/execution/mcp.rs:101–108` runs `McpClient::connect` inside `preflight`, which drops its future on cancellation/deadline (`execution/mod.rs:19–33`). Production `HttpMcpClient::connect` spawns initialization at `src/adapters/mcp/mod.rs:102–121` and awaits a readiness channel. The spawned `.serve(transport)` has only its30s timeout; it does not select caller cancellation/readiness receiver closure. The gateway has no session to close until connect returns. Dropping its wait therefore allows authenticated initialization to continue and returns before actual transport work is cancelled/closed. Worker tracking for eventual process shutdown does not cancel this invocation.
- **Independent reproduction:** [loopback probe source](logs/reviewer-mcp-connect-cancel.rs), [compile02](logs/reviewer-mcp-connect-compile02.log), [run01](logs/reviewer-mcp-connect-run01.log), [command](logs/reviewer-mcp-connect-run01.json). It uses the production compiled HttpMcpClient against an owned127.0.0.1 server, holds the initialize response, drops/awaits cancellation of the connect task, then releases the response. The server observes a new `POST notifications/initialized` after cancellation, followed by cleanup DELETE. DELETE is legitimate cleanup; the continuing initialized POST is the demonstrated defect. The probe shuts down the client and joins its server; no DB or external provider was used. Initial probe compile01 failed only because unwrap_err required Debug on dyn McpSession; retained, then corrected in probe source. Binary/library hashes are retained in [inventory](logs/reviewer-B1-R1-inventory.json); only own probe executables were removed.
- **Required correction:** make preparation cancellation/deadline/abandonment reach actual initialization and provide bounded completion of its cleanup before the gateway reports preparation ended. Cover cancellation while initialization is held, plus shutdown/abandonment, using the real production client and counted transport. Preserve legitimate cancellation/close protocol messages and existing native effect ownership.
- **Instruction lesson:** A1 accepted reuse of the supervised transport under an explicit actual-cancellation requirement; inspection of established tool-call cleanup did not prove initialization cleanup. Candidate scope: lifecycle checks for reused async clients cover initialization/admission as well as the completed-session call path. This is a code/affected-port gap against D1, not a request to change its cancellation requirement.
- **Resolution history:** 2026-11-08 open against B1/R1; no correction reviewed.

## VG-P06-B1-F3 — MCP preparation sends further authenticated requests without post-wait authority checks

- **Context:** same date/workflow/role/worktree/base/digest as F1; round VG-P06-B1-R1, D1/r1.
- **Classification:** actionable, high, authorization/requirements. Open.
- **Evidence:** `src/application/integrations/execute.rs:71–90` authorizes/resolves once, then awaits the entire `prepare_mcp` operation before checking again. Within it, `execution/mcp.rs:101–115` waits for connect and immediately starts discover without any actual host/module authority or generation callback. Production connect itself waits for endpoint/global admission and DNS (`src/adapters/mcp/mod.rs:74–75`) before sending credentialed initialization, also without such a callback. The genuine owner-configuration path reuses the same open routine. Thus revocation, membership loss or source rebind while a permit/DNS/connect is blocked is only noticed after further authenticated initialization/catalog requests have already been sent. Cancellation-token checks alone do not detect those persisted changes. The final tools/call guard correctly prevents a business call, but does not satisfy the original06/D1 requirement to recheck actual host authority after waits before continuing authenticated preparation.
- **Counterexample from actual control flow:** resolve succeeds; hold connection admission/DNS (or an initialize response); revoke owner/grant/membership or change the approved binding; release the wait. Current code sends initialize (or tools/list) with the already selected credential; only after discover returns does resolve/check deny. Existing tests hold discovery and assert eventual no business effect/catalog save; they do not establish zero subsequent authenticated preparation requests after an earlier wait. This finding is static call-path evidence; no new persisted revocation race test was authored by B.
- **Required correction:** enforce genuine business/configuration authority and selected-generation checks at the boundaries after admission/DNS and before authenticated initialization, and after connect before catalog discovery. Keep host/module locks out of network waits and close/refuse safely on failure. Add counted real-host races at those held boundaries proving no next authenticated request after denial, for business and configuration purposes. Do not substitute caller facts or a synthetic business context.
- **Instruction lesson:** original06 acceptance explicitly requires host denial after every wait; D1 retained this. A combined helper returning only after connect+discovery hides intermediate authenticated sends. Candidate scope: review each internal wait-to-next-send edge in composed transports, not only the helper's final return. A1's general reuse approval did not waive these checks.
- **Resolution history:** 2026-11-08 open against B1/R1; no correction reviewed.

## VG-P06-A2-F1 — retained WorkerTransport cannot finish cancelled handshake channel waits

- **Context:** 2026-11-08; implement-astra-reviewed-2-2; p06 architecture reopen [VG-P06-A2-R1](agent-review-notes.md#vg-p06-a2-r1); [TASK](TASK.md). Same independent B role requested Astra/high, actual settings not exposed. Worktree `/Users/mac02/.codex/worktrees/1133/openbot`; base/HEAD `ace526fd8259ec53c5199ffa7555a1a99dcba58e`, unchanged source `a781a861b6d39b7abccfdc0706619a7cfcc5573a440f5026ae0dbb492218c658`. Proposed D1/r2 SHA `9e83a43dc5bfc89490521d30793a8eba51ed9aa81d66eb33c12f6491884c0ef6`. Coordination19, proposed C005/r2.
- **Classification:** actionable architecture defect, high, cancellation/ownership. Open; blocks D1/r2 acceptance. Related open implementation finding B1-F2.
- **Evidence:** D1/r2 proposes that dropping the serve initializer transfers the still-owned WorkerTransport to a cleanup slot, where the supervising worker cancels and awaits close. In pinned rmcp1.8.0, `transport/worker.rs:208–215` close takes its private join handle, cancels its token and awaits that handle while retaining its sender/receiver. But `StreamableHttpClientWorker::run` waits for its first request (`transport/streamable_http_client.rs:466–470`) and again for initialized notification (`:533–534`) through `WorkerContext::recv_from_handler` (`worker.rs:176–183`), which observes only channel closure, not cancellation. After the initializer is dropped there is no producer for the next handshake message, while the retained transport keeps the sender open. Merely cancelling the token and awaiting close cannot complete. The before-first-request case can occur when `serve_with_ct` selects an already-cancelled token without polling its inner initializer; the later initialized wait is the same ownership issue. An in-flight HTTP cancellation select does not cover either channel wait.
- **Independent probe:** [source](logs/reviewer-A2-worker-close.rs), [compile](logs/reviewer-A2-worker-close-compile.log), [run](logs/reviewer-A2-worker-close-run.log), [command](logs/reviewer-A2-worker-close-run.json). Actual compiled pinned StreamableHttpClientTransport is constructed, yields to its worker, cancellation token is cancelled and close is awaited with a100ms observation bound. It remains pending; no HTTP request is submitted. The indefinite-wait conclusion follows from the inspected channel-only wait, not from the100ms measurement alone. Probe then drops its own channels and exits its owned runtime. Pinned source hashes retained in [identity](logs/reviewer-A2-rmcp-identity.json). No Cargo build, DB or project source mutation.
- **Impact:** the proposed supervisor can hang waiting for initialization cleanup. Timing out `close()` is not sufficient: close has already moved the join handle into its future, so dropping that future abandons the handle and cannot establish awaited completion. D1's bounded actual cleanup/permit-release guarantee would remain unproven.
- **Required revision:** specify a viable per-attempt cancellation/completion ownership mechanism against pinned APIs that terminates both handshake channel waits and in-flight network work, retains the ability to await actual worker completion, and performs bounded session cleanup where a session was established. Do not replace the guarantee with timeout-and-detach. Include cancellation before first handshake polling and between initialize response and initialized notification, in addition to the existing held-HTTP tests. This requests the corrected invariant/mechanism, not an implementation design from B.
- **Instruction lesson:** inspect cancellation throughout the reused worker state machine, including channel/admission waits before its main cancellation loop. Token availability and a close method do not establish that every startup state cooperates. Existing actual-work ownership instructions remain applicable; no instruction edits made.
- **Resolution history:** 2026-11-08 open against D1/r2; no dependent source edits or corrections reviewed. All B1-F1/F2/F3 remain open for later code recheck.
