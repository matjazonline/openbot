## F1: phase-preserving host projection

Map errors from the genuine host invocation constructor, before installing/calling BusinessDispatch, to PreparationFailed: invalid/limit/projection errors terminal Invalid, lost authority Denied, storage/transient failures Retry, actual cancellation Cancelled. Do not reclassify any error returned by native preflight/reservation/entered dispatch, or change retained earlier effects/proofs. Keep the existing16KiB portable OperationArguments bound; this does not raise a resource limit. Add actual native HTTP and affected MCP regressions across this constructor, counted no credential/transport work and zero new markers/entries/receipts, explicit typed terminal invalid/denial. No parser-only proof.

## F2/F3: required guarded MCP preparation and actual worker ownership

Add a required MCP client operation for guarded preparation, alongside the distinct existing connection-owned operation. Guarded operation requires a runtime-only work value (deadline, actual cancellation token and required async request-authority port); no optional authorization hook, default-success guard or serialized runtime capability. Explicit denying implementations are allowed only in nonexecuting fixtures. Both production modes share the same underlying transport/session implementation; this is not a legacy read/write or payload compatibility path.

The integrations execution core constructs a private authority object bound to the exact selected credential generation and full authorization snapshot, using either the real business context or genuine owner/configuration context. It invokes existing required generation/host/module checks, never caller facts or a forged workflow fence. Pass it to MCP preparation along with the private injection. It cannot resolve/export another token, send a business call or change destination/account. All implementations of affected required runtime ports are updated. Authentication bytes remain inside private composed transports.

Production HttpMcpClient applies the required guarded authority at the actual bounded HTTP request boundary: after admission/DNS/worker-lock waits and immediately before initialize; after initialize response before subsequent authenticated protocol POSTs; before every catalog page or business request after waits. Existing gateway final business guard/native entry remains authoritative. Recheck actual cancellation/deadline around the callback. No host/module DB locks span network waits. Legitimate protocol cancellation notifications and session DELETE are cleanup and remain permitted after cancellation/revocation; they cannot dispatch a business operation. Existing network/DNS pinning and endpoint policy, no redirects/retries/reinitialization, response/catalog/schema bounds remain unchanged. Also explicitly recheck after connect before catalog discovery so scripted/custom guarded clients satisfy this composition seam.

Initialization is a per-attempt supervised worker with readiness, cancellation and completion ownership from before the first authenticated request. Observe caller abandonment/readiness receiver closure, actual cancellation/deadline and client shutdown during initialization. Cancel RMCP's initializer and its transport worker, and await bounded actual transport cleanup before the cooperative guarded connect returns a preparation error. The gateway must not wrap this cooperative connect in a timeout that drops its cleanup. Dropping an uncooperative caller future still signals the supervised attempt; process shutdown joins that attempt rather than abandoning it.

Pinned rmcp1.8.0 provides serve_with_ct and WorkerTransport.cancel_token. Do not retain an SDK WorkerTransport after abandoning its initializer: WorkerContext.recv_from_handler ignores cancellation, and retained send_service would keep its handshake channel open (A2/F1). Also its non_exhaustive WorkerContext/WorkerSendRequest cannot be reconstructed externally. No fork, dependency change, unsafe layout conversion, synthetic handshake request or parallel protocol/network stack.

Instead use the existing SDK transport unchanged and DROP it when its initializer is cancelled. That releases all sending endpoints and cancels its transport token. Track actual owned HTTP capability lifetime through a private completion witness held ONLY by BoundedHttp and its SDK-owned clones. The connection supervisor holds only the completion receiver, not a client/transport clone. A request future borrows/owns such a client; SDK initialization, SSE workers and cleanup own their clones. The last-client Drop signals that actual SDK HTTP work/resources have ended. The native supervisor awaits this witness on initialization error/cancel/abandonment before sending readiness failure/completion; native client shutdown joins the supervised attempt. This is an explicit resource-completion join, not merely firing cancellation or waiting on an unrelated timer. Do not put the witness into the request-authority/control object (that would make a lifetime cycle).

The private bounded HTTP operation must select per-attempt cancellation and deadline during its actual send/response-body future, not only check before sending: the pinned SDK initial post_message await does not inspect its worker token. The per-attempt control is cancelled on readiness receiver closure, caller cancellation/deadline, or client shutdown; serve_with_ct and HTTP work use it. Drop the cancelled serve future/transport before awaiting last HTTP capability release, so the SDK handshake channel waits wake by channel closure. The guarded API awaits this cooperative completion; the gateway must not drop it in an outer timeout. Existing connection-owned API uses the same abandonment/cancellation supervisor with an explicit owned-authentication mode; the new integration API always requires its genuine authority port.

Keep a separate private bounded cleanup record (endpoint, accepted session identity and negotiated protocol headers; no BoundedHttp clone) when an initialization response exposes a session ID. Clear it after accepted native DELETE. If an initializer exits before the SDK main loop's normal cleanup and a known session remains, the native supervisor performs only the existing pinned client's cleanup DELETE, with the same five-second SDK cleanup budget, then records completion. This never authorizes initialize/catalog/business calls and is allowed after authority loss. Session identifiers and credentials never become public observations. Last-client completion plus fallback cleanup must precede the guarded preparation error; normal successful sessions retain existing explicit close ownership. The existing thirty-second preparation and thirty-five-second cleanup ceilings are unchanged, with deterministic early-failure tests. The HTTP cancellation select and closed sending endpoints must make completion quiescent within these existing bounds; no unawaited cleanup is accepted to clear a timeout.
