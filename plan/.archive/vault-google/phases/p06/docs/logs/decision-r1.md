# VG-P06-D1 / r1 — authenticated execution without moving effect ownership

Status: proposed architecture gate; no dependent source edits. Original requirements are the whole plan06 A–C and accepted03/05 producer contracts, not this proposal alone. Review the whole decision together.

## Ownership and dispatch sequence

1. Add a host integration dispatch adapter around the existing PostgresActionDispatch. It routes only persisted deterministic HTTP/MCP intents with the accepted frozen integration snapshot. Owned-secret actions continue through the existing native dispatcher. Generic tools, channel/model actions, samples and publication never acquire production integration authority. Native SQL authority, approval, knowledge-release, replay, fence, uncertainty and receipt owners remain authoritative.
2. Extract the existing remote reservation's authorization/approval/receipt/refusal preparation into one shared native helper. Expose a purpose-specific host preflight returning Ready(FrozenAction) or the same existing native observation. It may persist the existing approval parking transaction, but never writes a possible-dispatch marker or reserves a provider entry. It checks current persisted authority, budget, consumed approval, existing receipt/effect uncertainty and knowledge release. A ready preflight is no authorization token: reserve_remote and enter_remote still re-read all native facts later. Do not implement preflight by inserting a marker and rolling back, or by synthesizing an approval.
3. Host preflight runs before module credential resolution. Already committed receipts and approval parking/refusals return without refresh, DNS or catalog I/O. The host then constructs the exact AuthorizedInvocation from its persisted FrozenAction, including a bounded portable HTTP/MCP operation projection. HostDispatchAuthority verifies that projection, arguments, operation digest, target, snapshot and IDs against that same persisted action. A caller-supplied target/account cannot grant execution.
4. ExecutionContext gains a required runtime-only BusinessDispatch port supplied by the actual host adapter. It is separate from the read-only DispatchAuthority check. It accepts an opaque runtime PreparedBusinessCall capability and exact invocation; it returns only a bounded ExecutionOutcome. The capability has required call and close operations, carries no serializable credential/session fields, and is implemented inside integrations. Existing non-executing resolver test contexts explicitly install a denying dispatcher. No successful default or optional authorization operation.
5. LocalIntegrationGateway resolves credentials and performs destination validation, HTTP DNS/client preparation or private MCP connect/discovery/schema validation before calling BusinessDispatch. The resolver remains outside action transactions. Required host-first checks run before resolution and after all waits. Preflight errors are typed pre-dispatch failures, and the host maps them to a preparation failure observation rather than the generic ambiguous-dispatch path. No remote marker or entry exists on those paths.
6. BusinessDispatch invokes the unchanged native remote supervisor using a host RemoteAction wrapper over the opaque PreparedBusinessCall. Thus native reservation, approval races, replay contract, marker, final enter, ownership heartbeats, deadline, result validation and finish_remote retain their current behavior. The wrapper rechecks actual host authority plus module AUTH/grant/policy and the prepared credential generation immediately before polling the actual business call. No DNS/catalog/token-renewal work is allowed inside this wrapper. A late refusal/cancellation after native reservation retains the existing conservative possible-dispatch state; it must never be converted into fabricated not-applied evidence or an automatic replay grant. Errors before BusinessDispatch are pre-dispatch; once a native marker may exist, the native observation owns classification. Existing approval consumption and receipt truth remain unchanged.
7. The host adapter retains the exact native observation/error outside the module and maps that back to workflow handlers. It never trusts a module-provided Committed value as a replacement for a native receipt. ExecutionOutcome is a mutually exclusive typed projection of pre-dispatch rejection, bounded committed provider data or uncertain outcome; avoid independent effect/data combinations that can claim failure as success. Gateway/host code does not serialize an internal request, session or typed injection.

## Credentials, destinations, generation and lifecycle

The app registry owns a generic transport policy included in its policy digest. Static entries can authorize their exact owner-approved grant destination. Managed apps declare exact origins/endpoints and API path families. HTTP normalizes the final URL then checks both exact approved origin and app path restrictions before credential injection; deny alternate hosts/ports/userinfo/fragments, escaped path traversal and auth/header conflicts. Gmail permits HTTPS gmail.googleapis.com and /gmail/v1/ only. OAuth token/identity origins are never workflow destinations. Google MCP remains disabled unless a separately registered exact supported endpoint/authentication/scope policy is verified; general SSRF approval never authorizes forwarding a Google bearer. There is no Google branch in shared workflow handlers.

Use existing bounded HTTP DNS pinning/no-proxy/no-redirect/no-retry and response redaction rather than another network stack. Factor its credential injection so both bearer and registered API-key headers share that transport. Credentials are inserted only by the module transport composition. The public operation DTO retains its16KiB cap (no silent increase to native32KiB); all native request/header/result/network bounds still apply. Reject unsupported arguments before resolution.

Private MCP sessions are per invocation, with full identity (account AUTH revision, grant ID/revision, app policy/destination, credential generation). There is no shared session cache. Re-read/resolve after catalog discovery: if generation changed, close and rebuild, at most two complete attempts, otherwise return safe pre-dispatch retry. Check frozen tool name and input/output schema before business entry. Key rewrapping is absent from this identity. Existing McpClient/McpSession ports and supervised adapter own transport workers; module owns session close on every path, including native receipt/approval races that never call it. Call errors after possible entry are uncertain and never trigger refresh-and-replay. Native supervisor cancellation/deadline drops the actual call future; gateway awaits bounded session cleanup before returning. Do not timeout/drop native finish_remote before its receipt/effect truth resolution.

## Owner configuration discovery

Introduce a separate typed owner/configuration discovery gateway operation and required host configuration authority. It has a verified owner, actual company/admin membership and browser/session (when browser initiated), an approved configured binding and current source/catalog revisions, deadline and cancellation. It has no business action/dispatch/fence and cannot call BusinessDispatch. The existing business invocation must never be forged to reuse renewal. Refactor the private resolver's request into a typed business/configuration purpose over the same locked renewal core; owner configuration checks the actual owner and current approved MCP binding and grant. Preserve owner/account lock order, C001 consent validation, C004 strict pending recovery and host-before-module authority. Return bounded catalog metadata only; host rechecks owner/session/connection/source/catalog expected revisions under its normal save transaction after discovery. Another administrator cannot discover through somebody else's account. Required separate configuration authority cannot authorize business calls.

## Authoring and examples

Extend existing HTTP/MCP connection pages/routes with a generic registry-driven source picker. List only own grantable accounts and safe metadata for the current approved binding. Use existing explicit owner proposal/confirmation grants; selecting an account does not itself authorize use. Preserve configured metadata for other authorized administrators without listing somebody else's vault or revealing credentials. Keep connection IDs in workflow definitions, publication/direct-tool denial and inert scripted samples. Add actual supported DSL examples for HTTP Gmail read→model suggestion and explicit reviewed raw base64url MIME send with threadId. Encoding is supplied manually and validated in fixtures with existing base64; no invented transform/operator. Document preview MCP read/draft catalog separately, no send guarantee. Current Google docs checked 2026-11-08: developer preview remains and read/draft operations described.

## Failure and verification matrix

Before native marker: rejected owner/host/grant/app/destination/arguments, refresh failure/reconnect/cooldown, DNS failure, discovery/schema/generation retry or cancellation => typed pre-dispatch preparation failure, zero business calls and zero markers. After native marker: preserve native possible-dispatch/uncertain behavior including late generation/authority refusal, cancellation, network timeout, malformed provider result or receipt commit ambiguity. A known successful provider result uses native result validation/finish_remote; it cannot be reported as a fresh retry after return authority is lost.

Focused real-PG/scripted-transports tests: integration_gateway_, vault_workflow_http_, vault_workflow_mcp_, vault_authoring_ with nonzero listed counts. Cover competing refresh claimants after approval, denied/revoked/rebound host after DNS/catalog/lock waits, exact target projection, static bearer/API-key/OAuth same gateway, rejected arbitrary Google destinations and header overrides before credential transport, no serialized secret in result/error/receipt/sample, generation changes during discovery with bounded close/rebuild, key rewrap stability, cancellation/lease loss closes actual MCP work, uncertain send executes once across retries, existing receipt and approval no-refresh, owner configuration vs business purpose isolation, other-admin discovery denial and stale catalog save. Trace affected callers for native preflight/observation, HttpRuntime/McpRuntime, authority, registry policy and resolver interfaces; update every required implementation explicitly. Run affected native approval/replay/cancellation/history contracts, boundary scripts, UI/browser tests and lint/build/fmt; migration/SQLx fresh-base checks if SQL changes. Targeted-only I03/r3; no full/runtime/stack suites. Keep inherited unrelated failures unchanged.
