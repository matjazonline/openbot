## CL-P03-D01-F1 — distinguish immutable journal bytes from replaceable connection identity

- **Status:** OPEN, 2026-11-07. Actionable architecture/correctness defect, medium severity. Workflow `implement-astra-reviewed-2-2`, p03 architecture round [CL-P03-D01-R1](agent-review-notes.md#cl-p03-d01-r1--combined-architecture-gate). Reviewer `/root/cloudroom_reviewer`, requested GPT-6 Astra/high, actual metadata unavailable. Worktree `/Users/mac03/dev/openbot`, main; phase start/base/HEAD `97e5d60dc538e26c7cb976a8d63772eed80baff2`; source digest `ee02338b474bb7b234a8a8978669f952df0b36aabf125d191ae1bb2fc547aad7`. [TASK](TASK.md), [REVIEW](REVIEW.md).
- **Evidence:** [CL-P03-D01/r1](logs/CL-P03-D01-r1.md), SHA-256 `142b5d376cc93112fba8cb7186ac468b8c9274d15f5f7b770b5d1626bc875305`, says logical envelopes carry authenticated installation/connection identities, each logical message is serialized/hashed as exact bytes, and sequence reuse binds the original serialized bytes preserved by the plugin journal. It also requires every observation/ack to match the current connection generation/owner. These rules do not define a replayable byte boundary across generation replacement. If a committed observation at sequence S under generation N loses its acknowledgment, replaying its complete original logical envelope under N+1 carries stale connection identity; rewriting that identity changes the bytes whose immutable digest was bound to S. The current typed `LocalAgentObservation` (`src/domain/local_agents/observations.rs:48–67`) contains stable observation data without a connection fence, but no new protocol layer is implemented yet to resolve the proposed envelope ambiguity.
- **Required correction:** Define exactly which serialized bytes are immutable and covered by the journal sequence/content digest, which connection-scoped fields may change on reconnect, and how the currently authenticated fence is validated while reusing the saved immutable observation. Keep both changed-sequence-content refusal and stale-generation rejection; neither can be weakened to make replay work. Distinguish the transport transfer digest from durable observation identity if they cover different byte domains. Add a decisive planned test: commit S on connection N, lose its acknowledgment, replace with N+1 and replay the identical saved observation to recover acknowledgment without another state transition; concurrently prove N is rejected and changed stable observation content at S conflicts. Cover the pre-commit reconnect case too.
- **Impact:** The proposed bytes/fence interaction is under-specified at a cross-peer persistence boundary. A literal whole-envelope hash/replay implementation cannot satisfy both current-fence enforcement and lost-ack recovery. This needs a decision correction before dependent Rust/Node protocol code, not a compatibility decoder or acceptance of stale connections.
- **Instruction lesson:** Original phase 03 requires both generation fencing and crash/lost-ack replay; active C002 separately fixes immutable deadline bytes. Those are sufficient existing requirements. A candidate wire-schema rule should only be considered later if the same mutable-envelope/immutable-payload confusion recurs; no instruction edit proposed now.
- **Resolution history:** Initially open against D01/r1, before any p03 implementation. No runtime reproduction claimed; this is a decision-level contradiction/ambiguity illustrated by the required lost-ack scenario.

## CL-P03-B1-F1 — reconcile physically unsettled uncertain operations on reconnect

- **Status:** OPEN, 2026-11-08. Actionable correctness/recovery defect, **high** severity. Round [CL-P03-B1-R1](agent-review-notes.md#cl-p03-b1-r1--whole-phase-implementation-review), workflow `implement-astra-reviewed-2-2`, p03; reviewer `/root/cloudroom_reviewer`, requested GPT-6 Astra/high, actual metadata unavailable. [TASK](TASK.md), [REVIEW](REVIEW.md).
- **Evidence:** `src/adapters/persistence/local_agents/protocol/mod.rs:169–171` requires `outcome IS NULL` in the Ready barrier. `protocol/commands.rs:185–187` uses the same restriction to select deliveries, and `commands.rs:255–257` refuses every row with an outcome. `mod.rs:209–211` converts possibly delivered expired work to `uncertain`. C004/r1 and the capacity helper deliberately still count such work as physically unsettled unless matching completed/failed/stopped evidence exists. Original 03C requires reconnect reconciliation before new effects; D01/r2 requires current-generation evidence for outstanding attempted operations.
- **Concrete path and impact:** dispatch an effect, record receipt/submission intent, lose the connection while native submission/result is unresolved, and let the server deadline expire (or accept explicit Uncertain). Reconnect with the same intact journal and acknowledged cursor. The operation has `outcome='uncertain'`, possible native activity, and old `last_observed_generation`, but is absent from reconciliation delivery and does not block `finish_reconciliation`. A Ready request can enable untouched new effects without any current-generation reconciliation of that work. The server also cannot request that operation's positive native reconciliation, potentially leaving its capacity reservation indefinitely occupied. No lost journal is needed to trigger this.
- **Required correction and decisive assertion:** consistently distinguish a settled server wait from physically unsettled work in candidate selection, preparation, and the Ready barrier. Replay unresolved attempted work in Reconcile mode, never Dispatch; require current-generation recovery evidence before Ready/new effects, while retaining the expired wait outcome. Add real DB/WS coverage for attempted effect → expiry/uncertain → reconnect: it is delivered for reconciliation, Ready is false and an untouched effect is withheld until the recovery evidence commits; positive late native evidence frees capacity without changing the expired wait. Cover explicit uncertainty as well as expiry and a known-terminal late result so already settled native work does not block indefinitely.
- **Verification boundary:** source-path proof; no new failing production test was injected into frozen source. Existing `cloudroom_commands_uncertain_native_work_keeps_capacity_until_known_terminal_evidence` passes independently ([log](logs/reviewer-b1-r1-uncertain-test.txt)) but never reconnects. Existing lost-ACK reconnect tests exercise only null outcomes. The missing cross-product is decisive.
- **Instruction lesson:** existing 03C and C004 already require this; no new repository instruction is justified. This is an implementation omission, not a requested compatibility path or p05 deferral. Resolution history: initially open in B1/R1.

## CL-P03-B1-F2 — reject pre-dispatch refusal after recorded submission intent

- **Status:** OPEN, 2026-11-08. Actionable correctness/evidence-transition defect, **high** severity. Same B1/R1 reviewer, worktree, base and artifact identity as CL-P03-B1-F1; [review note](agent-review-notes.md#cl-p03-b1-r1--whole-phase-implementation-review).
- **Evidence:** `src/adapters/persistence/local_agents/protocol/observations.rs:180–198` rejects Refused only after NativeIdentity/CatalogSnapshot, allowing it after SubmissionIntent. It sets `definitive_refusal=true` and outcome Failed/Expired. `observations.rs:278–302` explicitly exempts this mutation from the deadline→Uncertain rule. `src/domain/local_agents/operations.rs:210–247` permits this dispatch/outcome combination, so typed decoding does not reject it. C004's capacity predicate then stops counting the effect because its outcome is no longer null/uncertain.
- **Concrete path and impact:** accepted Receipt → SubmissionIntent → Refused(RecoveryRequired or Expired) succeeds before native identity is known, even if the previous outcome became Uncertain at the deadline. SubmissionIntent is durable evidence that SDK entry may have occurred; a preflight reason cannot now establish nonexecution. The server records definitive failure/expiry and releases effect capacity despite unresolved native work. A later valid native terminal result cannot repair that outcome, since `validate_terminal` freezes non-uncertain outcomes and drops its state/output/usage mutation. Original 03B/03C and D01/r2 explicitly prohibit turning possible submission into proof of nonexecution.
- **Required correction and decisive assertion:** allow this pre-dispatch refusal evidence only before SubmissionIntent/native evidence. After intent, preserve uncertainty unless command-specific positive native evidence resolves it. Add real persistence tests for each refusal reason after SubmissionIntent (including already-uncertain/expired wait): reject the transition without advancing inbox/cursor or changing outcome/capacity, then accept the valid next observation at the same sequence. Keep positive tests proving legitimate refusal before intent settles untouched/local-preflight work. A distinct post-entry definitive SDK rejection would require its own demonstrated evidence contract; these preflight reasons do not supply it.
- **Verification boundary:** traced through apply, typed decode, terminal validation and persistence; source inspection, not a claimed runtime reproduction. No current new test contains Refused evidence or asserts this transition boundary. Resolution history: initially open in B1/R1. Existing transition guidance is sufficient; no instruction edit proposed.
