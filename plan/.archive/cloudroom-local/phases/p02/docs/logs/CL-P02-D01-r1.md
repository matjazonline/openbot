# CL-P02-D01/r1 — pairing, ownership and persistent boundaries

Original authority: plan/cloudroom-local/02-company-machines-and-pairing.md; p01 accepted artifact cfc3dd8052971597cce455f3c7013a5051c0abb74aed605b490017c547d93233. This is a proposed architecture decision, not implemented behavior. Review all decisions together before schema/transaction edits.

## Boundary and storage

Application owns focused LocalMachine management/pairing ports and use cases. HTTP does only canonical/bounded decoding, browser session/CSRF integration and dedicated claim-header handling. PostgresPersistence implements transactional mutations; SDK/WebSocket/SQL types stay outside inner contracts. Domain IDs from p01 remain authoritative. Profiles, sessions and operations retain full frozen selection including reasoning; no compatibility decoding/defaults/backfill.

Edit only the clean init schema. Add normalized machine, installation binding, pairing, credential verifier, profile, session, operation and observation tables (and bounded authentication-budget storage). A machine stores company, installation, administrative state, credential generation, observed presence/capability reference, connection generation/owner/expiry. Profiles and sessions use tenant-qualified foreign keys; sessions carry exactly one original conversation(thread) or workflow-run association with matching company. External thread uniqueness is scoped to installation, not global.

Reserve an installation ID permanently on first enrollment, including after revocation. Keep its small immutable company-binding tombstone even if a company's cascading deletion removes machine/credential/session rows; the historical company UUID on that reservation is audit identity, deliberately not a live authorization FK. Every live machine still has a company FK and a composite company/installation FK to the reservation. A fresh explicitly initiated re-pair uses a new installation UUID and cannot adopt old thread mappings. No mutable reassignment or release of the reservation. This avoids either silently recycling an identity or blocking normal company deletion indefinitely.

Pairing stores only the digest of a random 16-byte/128-bit code, creating actor/company, absolute database expiry, consumed/revoked state, winning installation/machine and verifier hashes. Machine/claim secrets are generated by the plugin, durably stored there before enrollment; server accepts only their canonical SHA-256 verifiers. Secret wrappers redact transient codes/tokens and no ordinary read projection returns verifier/ciphertext material. The pair response returns identifiers and resolved origin/company, never a newly minted secret. Credential verifier uniqueness prevents a key being rebound to another machine. Generations are positive bounded integers.

Operation preparation uses immutable command, digest, deadline and company/machine/installation/session relationships, separate dispatch evidence/outcome, and tenant-qualified unique logical identities. Observations are scoped to installation and stable sequence. No general enqueue/dispatch/observation protocol is implemented in p02; p03 owns its detailed transitions/chunk/wake-up protocol and must gate material extensions before use. Database checks and fallible typed decoding reject incoherent representations; no private native runtime or Cloudroom database access.

## Transactions and races

Use managed_company at application entry and reuse existing transactional company-authority/locking patterns for actual mutations. Code creation serializes on company authority, checks the five-live-code bound, and commits a ten-minute expiry. Enrollment also rechecks the issuing actor's live company-management authority; removing that authority before consumption prevents enrollment. Missing/foreign IDs and rejected claims do not reveal company or installation details. Database failures are errors, never authorization defaults.

Lock ordering is company authority before pairing row before installation/machine/credential rows. A code-hash lookup may first obtain its company without locking; re-read the pairing row under the ordered locks. Consumption uses row locking/conditional updates and live database clock after lock acquisition (not the transaction-start timestamp). Expiry/revocation races therefore cannot spend a code after its deadline. In the same transaction reserve installation, insert machine and credential verifier, consume code and bind the winning claim. Unique constraints decide competing installation reservations without reassignment. No network wait in a transaction.

An exact consumed-claim replay compares installation, claim verifier and credential verifier and returns the original machine only. A changed key/installation/claim cannot replace the winner. Header-authorized pair-status derives the claim verifier from the supplied secret and matches the saved installation; no query-string secret and no general company-data API. Revoked/deleted bindings cannot recover a valid pairing. A lost HTTP response needs no secret reissue and no second credential.

Disable is an administrative admission block, separate from observed presence and current execution. Revoke locks the machine and atomically changes state, invalidates every current credential and connection fence/expiry, and preserves unresolved operations as non-stopped evidence. No physically-stopped claim without native evidence. Connection establishment/renewal (consumed by p03) must lock/check the same machine row and match current credential generation; a race may establish then immediately be fenced, but cannot leave a valid post-revoke owner. Superseded cleanup cannot mutate a newer connection generation. Explicit replacement pairing creates new identity rather than overlapping credential generations or transferring mappings.

## Ingress and bounded failure

Pair/status endpoints remain outside application-user authentication; their credentials authorize only enrollment recovery/machine linkage. Management routes remain inside normal session auth and same-origin mutation protection. Pair JSON is small and body-bounded; code is exactly 32 lowercase hex characters, claim/credential hashes exactly 64 lowercase hex, installation a canonical nonnil UUID, trimmed machine name bounded to 128 UTF-8 bytes. Claim secret is high entropy and canonical; malformed headers/unknown claims return generic refusal. Machine bearer credentials will be used only at the connection boundary in p03.

Extend existing HTTP authentication admission/source trust for pair/status before body parsing. Add durable domain-separated source/code/claim budgets using existing HMAC key patterns; do not persist raw IPs or secrets. Keep a hard global row cap, bounded expired-row cleanup and bounded admission transactions so random identities cannot grow storage without limit. Distinct windows/limits are code-owned constants; refuse when exhausted rather than evict a live limiter. Failure responses do not distinguish wrong code, consumed/expired code, foreign installation or wrong verifier.

## Proof obligations

- Fresh task-owned database applies the init schema and validates tenant-qualified profile/session/operation FKs with direct invalid SQL, plus typed frozen-reasoning round trips. Regenerate/check SQLx metadata; record runtime-query coverage separately.
- Two genuinely competing claimants consume one code: one machine/verifier binding wins; exact retry and dedicated-header status recover that ID after discarded response; foreign claim/key cannot recover or rebind it.
- Hold company/pair locks, race expiry/revocation and revoked issuer authority against consumption; evaluate database time after locks and prove no late enrollment. Exercise owner/admin/member/stranger and database-outage error propagation.
- Prove max five codes and canonical bounds, secret redaction/no plaintext credential rows, source/code/claim budgets, global storage cap and cleanup behavior, CSRF and header-only recovery.
- Race connection ownership acquisition against revoke through real persistence (p03 later adds actual WebSocket handshakes). Verify old credential/fence cannot authenticate/renew or clear replacement state; disable remains distinct from revoke and physical stopping.
- Preserve reservation across revoke and company deletion; foreign-company reuse is rejected and explicit new installation can pair. New identity never imports old sessions.
