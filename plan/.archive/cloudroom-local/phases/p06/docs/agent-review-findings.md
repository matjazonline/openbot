### CL-P06-D01-F1 — P2: plugin mapping expiry has no authority for retained server references

**Category:** architecture/cross-peer retention and functionality. **Location:** [decision section4, line33](logs/CL-P06-D01-r1.md), in combination with section2 lines15–19 and section6 lines50–53.

Section2 correctly retains server sessions/results while active or prepared Workflow references exist, but section4 proposes expiring acknowledged terminal commands/mappings after90days based on plugin settlement/session-use times and says only that referenced mappings survive. It does not define how the plugin learns or preserves the server-only references. These references can exist without any pending plugin command: `workflow/local_agents/preparation.rs:26–31,44–83` freezes a continuation session inside the shared action, and `admission.rs:23–35` parks for approval before admitting native work. The peer has no copy of that pending action. Its mapping is essential: `integrations/cloudroom-plugin/src/sdk.ts:74–89` refuses every non-create session command if `journal.session(session_id)` is absent; Send/Inspect/Stop/Archive wire commands carry no replacement frozen selection (`protocol.ts:25–32`). Existing mapping storage is only local (`journal.ts:187–202`).

Concrete allowed sequence: session S completed and was acknowledged near day0; just before its90-day local mapping boundary, an authorized Workflow prepares a continuation of S and waits briefly for approval. Server retention preserves S because of the prepared action. Plugin cleanup crosses90days while it has no pending native command and removes S's mapping. Approval then arrives within the frozen30-minute operation deadline. Openbot admits a valid Send, but the plugin now refuses recovery_required rather than continuing the retained session. A recent server-admitted command awaiting an offline plugin creates the same visibility problem. Company locks in PostgreSQL cannot serialize these local SQLite deletions.

**Required correction:** resolve the mapping-retirement authority across the server/plugin boundary in the decision. Preserve the exact mapping for every session the server can still legitimately reference/admit, or specify a validated restoration/retirement contract that closes the race without inferring selection from an arbitrary thread or granting replay authority. State how this remains bounded under the4096-history policy. Require a combined server/plugin test crossing90days with a prepared approval or queued server command absent from the plugin; the authorized continuation must retain the original selection/thread and execute once, while truly retired mappings can be reclaimed. A local SQLite-only no-pending-row test cannot establish this.

**Instruction lesson:** existing C006 and original06 retention requirements already cover retained references; the missing producer/consumer ownership crosses the peer boundary. No new generic instruction is needed. **Resolution:** OPEN at D01-R1.

### CL-P06-D01-F2 — P2: mutual terminal session references permanently block both tree owners

**Category:** architecture/retention progress. **Location:** [decision section2, lines19–23](logs/CL-P06-D01-r1.md).

The decision assigns call/operation deletion exclusively to each workflow tree's retirement and blocks that retirement for *any* external-tree call referencing one of its originally owned sessions. That makes closed reciprocal references unreclaimable. This graph is allowed today: `workflow/local_agents/preparation.rs:85–107` requires matching company/profile/selection and original/invoking association, but imposes no original-run ancestry or ordering. Two roots A and B in the same authorized association can each create a session, then A explicitly continues B's session and B explicitly continues A's session. Their scoped call/session links are persisted independently (`admission.rs:136–172`, migration13756–13795).

After both roots, every call and every native operation have been terminal and physically settled for more than90days, A is still blocked by B's call to A's session and B by A's call to B's session. Neither tree owner can reach its own call-deletion step. There is no active workflow or unresolved operation left to justify retention, yet neither a later sweep nor ordering the two retire_tree calls can reclaim either tree. The proposed external-reference test covers protection but does not require progress for a closed cycle.

**Required correction:** define a reclamation rule for terminal settled cross-tree references that makes progress for this permitted cycle while preserving every active/prepared/unresolved external owner. Keep deletion atomic and company-qualified; do not simply ignore FK references. Add a real two-root reciprocal-continuation retention test: both old settled roots eventually reclaim, one live/unresolved member protects the necessary links, competing collectors do not partially delete a protected graph. The author should choose the ownership/eligibility adjustment; this review does not prescribe a new implementation.

**Instruction lesson:** bounded cleanup requires progress as well as safe refusal; the proposed single-tree owner introduces a reference graph without an acyclicity guarantee. Existing repository concurrency/verification requirements apply. **Resolution:** OPEN at D01-R1.

### CL-P06-B1-F1 — retained first page permanently starves mapping reclamation

- **Classification:** actionable correctness/liveness defect, **P2**, OPEN; blocks p06 acceptance.
- **Location:** `integrations/cloudroom-plugin/src/journal.ts:271–276` (`mappingCandidates`); scheduling consumer `src/connector.ts:174–183`.
- **Observed:** every request selects the same oldest 100 locally old mappings. An authenticated response containing no retired IDs changes none of their ordering/eligibility, and the connector starts the identical query next minute. No cursor or separate checked-at ordering advances past server-retained entries. A mapping can legitimately outlive its local terminal command: the plugin compacts the command after 90 days while an active original workflow, prepared approval or queued server continuation retains the SQL session.
- **Impact:** 100 such retained old mappings indefinitely hide later genuinely absent mappings. At 4096 mappings, thousands of reclaimable slots remain unreachable and all new creates stay paused until that unrelated oldest prefix becomes retireable. Reconnecting restarts the same first page. This violates original06's paginated retention and useful bounded progress; safety of refusing retained IDs does not establish eventual cleanup.
- **Reproduction:** [script](logs/reviewer-b1-r1-mapping-starvation.mjs) uses the production Journal and real SQLite fixture with 4096 old mappings, models the server retaining the first 100 and confirming absence for all others, and executes ten ordinary candidate/reply cycles. [Output](logs/reviewer-b1-r1-mapping-starvation.txt): `REPRODUCED`, 100 repeated IDs, 3996 absent mappings never requested, 4096 mappings remain, create admission false. No source files changed. This is a deterministic journal/page-consumer reproduction; it does not claim an actual server was started for the synthetic 4096-row scenario. The current server absence predicate was separately inspected.
- **Required correction:** make bounded candidate traversal advance even when some/all requested IDs remain server-owned, eventually wrapping/revisiting retained IDs. Preserve current identity/nonce, timeout/lost-response safety, immutable binding/local-reference rechecks and at most one bounded pending page. Add a regression with more than 100 candidates, a retained oldest prefix and eligible later mappings, demonstrating reclamation and resumed admission without deleting the retained prefix; exercise reconnect/timeout behavior appropriate to the chosen cursor policy.
- **Instruction lesson:** the gated ownership design remains sound; implementation omitted a progress property. Candidate guidance, scoped to retention protocols: when remote eligibility can reject a whole bounded page, test a non-retireable first page followed by retireable records. No instruction or design edit is authorized by this note.
- **Resolution history:** 2026-11-08 OPEN against the exact R1 artifact above.
