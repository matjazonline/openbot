## 1. Ownership and access

Extend application/local_agents usecases/ports and existing PG/HTTP adapters for profile CRUD, manager machine views and authorized session start/send/inspect/explicit thread-wide stop/archive. Reuse actual company and association authorizers, session auth/CSRF/layout; no Cloudroom internal SQL/SDK adapter in Openbot and no native handler replacement. General machine/catalog/workload views contain no prompt/output. Session detail/output requires current company access AND its original conversation/workflow association, including hidden channel/run rules. Manual controls on workflow-created threads can remain authorized after that run ends; they never resume the run. Copyable external thread ID only: no unproved deep link or remote localhost promise.

Add profile_id to the existing LocalAgentSession domain projection/PG mapper (schema already has it), so continuation validates the real profile rather than guessing from equal provider fields. Fresh manual sessions require a real authorized conversation association; workflow sessions store their original workflow run. Continuation is explicit, mapped, same company/profile/frozen selection and same original conversation/channel association as the invoking run; both current and original run visibility must pass. It never imports an arbitrary native thread or silently reuses another session. Existing provider-default permissions/project-directory policy remains the fixed supported choice; worktrees deferred. Profile/default/catalog edits cannot mutate an accepted session/operation.

Manager profile writes validate current machine/project allowlist and authoritative catalog; manual operation admission reuses current p03 checks and stable user request identity. Workflow local execution initially requires the existing managed-company authority as well as ordinary workflow action authority, not a novel implicit grant for local OS access. Document/refuse unauthorized actors; do not grant access because they know a profile UUID.

## 2. Existing shared-action owner, frozen approval subject and catalogue

It is a SharedAction/ResourceUse effect with durable identity recovery, budgets, suspension and deadline metadata. Native agent.run/classify/decision handlers and tool behavior remain unchanged. Use a purpose-specific entry on the existing ActionService, backed by application-owned local-agent workflow/dispatch ports. Before any local operation, use current actor/company/association and frozen published contract, live profile/machine/catalog authority, existing approval decision bound to exact immutable subject, action/root/activation/continuation budgets. Snapshot local_agent.run as a trusted, reserved STEP-owned builtin in published bundles so validate_run_authority sees it. Reuse an existing execution-scoped preparation on every claim before reading mutable profile defaults.

## 3. One execution-scoped call record and distinct deferred marker

Add a company/run/execution-scoped workflow_local_agent_calls table (one logical local step per workflow execution). It links exactly one immutable shared action intent. Its initial preparation state has no native operation/wait; the admitted state has all required scoped machine/installation/session/operation/wait links together. Encode the all-or-none transition with checks/composite FKs and unique execution/operation/wait ownership; no JSON capability supplied by peers. Calls reference existing action, execution, wait and native operation identities, not copied live state. Nullable ready_at is only a durable wake marker; native operation remains the outcome authority.

Preparation locks current company/actor/run/execution/fence and reads/replays this call before creating another intent. Factor the established intent writer's on-transaction primitive where required so call+intent/frozen selection agree atomically; retain existing other action semantics. A fresh freeze requires the current claim, not merely a row ID. Use the immutable action invocation UUID as the typed native operation identity (and deterministic new-session identity when no session supplied); logical key derives from run+execution, not lease/attempt. Retries after claim loss, process interruption or ambiguous COMMIT find exactly the same saved identities. No second prepared intent because a relative deadline/default was recomputed.

Add effect_kind local_agent to shared marker/receipt schema and exhaustive classification/retirement readers, separate from local whose marker+receipt mean an immediate same-DB effect. A deferred local_agent marker may await native evidence; an unknown marker never becomes proof of no effect. Add local_agent.run to marker-owned recovery only when its sole native effect path is this ActionService transaction. Do not raise existing root/continuation/queue bounds; refuse before admission when they cannot cover the required park/wake.

## 4. Atomic authorized admission and parked ownership

After current approval/policy and fence checks, one bounded SQL transaction locks the machine/capacity and:
1. records the shared possible-dispatch marker and charges the existing action budget once;
2. creates/reuses the authorized frozen session and native operation with absolute canonical deadline;
3. creates the existing effect-type workflow wait and attaches the call's scoped links;
4. closes exactly the current task attempt/job as local_agent_parked, clears its lease, and sets the run waiting.
No socket/SDK/provider call occurs here. Return Suspended(wait); extend responsible suspension confirmation to prove the exact local call/marker/attempt, preserving the existing approval and message paths. Ambiguous COMMIT is resolved from this call/marker/wait/attempt proof, never a retry-generated operation. Offline enabled machines keep this bounded saved work until its absolute deadline.

The existing wait dispatcher currently routes all effects to message receipts; extend it deliberately for local calls. Completed local effect waits that merely reopened an I/O job must be excluded from the generic terminal-wait replay selection, like other continuation-owned waits. Charge the existing continuation/root budget; protected approval plus native wait are distinct consumed continuations. Do not keep a worker execution lease during native work.

## 5. Live delivery, outcome/wake and fresh-claim result

Enable the previously refused workflow-session producer only with this complete consumer. Before a first transport attempt, re-read current actor/company/original and invoking association, saved action subject/published contract, exact profile/selection authority, approval disposition, run deadline/state and the exact active local wait/call. A parked wait authorizes this delivery under the independent current connection fence; it does not pretend its old worker lease is still live. Withdrawal prevents new delivery; uncertain prior delivery never authorizes a new operation. Reconciliation and explicitly authorized existing-thread controls retain p03 semantics.

On native outcome acceptance or server expiry, commit the server's operation receipt/output and the matching call.ready_at in the SAME transaction. Ready is not a capability and does not copy a mutable outcome enum. Queued/accepted Submission with no terminal turn never sets ready or releases capacity. Uncertain/cancelled/expired waits can become ready for classified failure, while late native evidence remains audit and cannot replace their outcome. Native capacity stays physical perC004.

The ordinary durable wait worker observes readiness using the exact scoped call/operation/wait, rechecks current run/association/authority/deadline, marks this continuation wait complete and reopens the saved job once. A FRESH current claim reads the same authoritative native result and creates/replays its shared action receipt under current fence/authority, then normal complete_io commits once. No callback or peer output can complete/publish a workflow directly. A crash anywhere between wake/job claim/receipt/completion reuses the same IDs and saved outcome. Cancellation, expired deadlines, revoked authority, stale claimants and terminal runs block continuation regardless of a later native success.

Return a typed bounded success result with operation/session/thread references,text,truncation flag and nullable measured usage. Keep complete authorized session output bounded256KiB in the operation; workflow action text is capped16KiB UTF8 (plus fixed metadata), explicitly flagged if shortened, within existing action/result/context budgets. Failure/uncertainty is classified workflow state, never assistant reply text or a retryable network error that spawns another thread. Publication only follows existing response/message intent paths.

## 6. Lock order, cancellation and failure behavior

Preserve company/principal/association authorization ordering. For workflow-associated local operations, take current workflow/run/execution/claim locks BEFORE machine/profile/operation/cursor locks; validate exact current machine/connection fence before inbox dedup/ACK. Read bounded operation→workflow link metadata first as necessary, not a dedup result or authority. Adapt outcome/expiry/delivery producers consistently so no machine-held transaction later waits for a workflow lock held by admission. Profile writes keep machine-before-profile ordering and authoritative profile identity is rechecked after locking. Existing manual/catalog/control paths retain their scoped ordering and bounded transactions.

Cancellation must revoke continuation even if local physical work keeps running; no automatic broad stop. Delivery authorizer rejects a cancelled/withdrawn run, expiry ends its server wait, and late evidence remains audit. Manual authorized controls can target its known mapped thread separately. Retention must keep call/intent/wait/native result while any active/unresolved workflow depends on it; p06 owns bounded maintenance, proposedC006 carries this dependency. Preserve files/native transcripts/provider logins.

## 8. Direct session follow-up and immutable native operation origin

Evidence/trigger: original05A requires authorized session start/follow-up/inspect/stop/archive. The implemented commands.authorize_session currently treats every effect on a workflow-created session as a workflow delivery, requiring an active parked call. It therefore refuses an explicit user follow-up, including after the original run ends. Dropping this check or inferring workflow ownership only from a nullable call would permit a missing call to downgrade a workflow operation into direct authority. Keep the two producers explicit.

Persist immutable server-side operation origin with a closed domain enum Direct/Workflow, SQL values direct/workflow, default direct for existing direct enqueue/catalog writers. This is initial-schema design/reset, not a compatibility default/decoder. It is NOT a peer field, command-hash input or public API selector. The workflow admission owner explicitly inserts Workflow; the authenticated management owner/direct protocol enqueue inserts Direct. Add origin to the existing native immutable-input guard and native scoped UNIQUE/FK identity. workflow_local_agent_calls carries constant operation_origin=workflow and a composite FK including that origin, so a direct operation cannot become a workflow wake source. A deferred insert guard requires every new Workflow native operation to have its scoped call/marker/wait/intent by COMMIT, reusing the atomic park proof. Workflow-origin commands are create/send effects only. No unknown/legacy source decoder.

First delivery uses persisted origin before any native lock: Workflow requires current parked call, original/invoking association, frozen shared action/current approval/profile authority; a missing/deleted call fails closed. Direct requires current managed-company actor and original session conversation/workflow visibility, with current exact frozen selection/catalog for new create/send. A direct explicit follow-up may target a known mapped workflow-created thread after that workflow ends; it creates its own stable operation/request identity and never links a new call, consumes an old action approval, changes the old workflow result, or reopens the old run. Direct inspect/stop/archive retain existing disabled-machine control headroom and thread-wide semantics. A revoked actor or inaccessible original association prevents first delivery for either origin. Already-attempted operations remain reconciliation-only per C003/C004; origin is never rewritten to gain new delivery authority.

Manual start requires a real authorized conversation, validated profile/current selection, stable caller request UUID and one atomic session+operation insertion. A retry reads/reuses the saved same actor/profile/association/prompt/command before consulting mutable defaults or recomputing deadlines. Direct follow-ups likewise freeze/replay once. Sessions keep their original association and selection. Management detail has a bounded recent operation page, with explicit truncation and current original-association authorization; broad machine/catalog/profile lists contain no prompts/outputs. CSRF/session auth applies to browser writes. No generic machine-wide transcript or unassociated session creation.

Verification mapping additions: actual direct follow-up of a workflow session after terminal run, showing a second distinct native operation but no old run/call/receipt mutation; foreign/private association refusals on read and all controls; current role withdrawal races first direct delivery; explicit origin immutability and cross-origin call FK rejection; workflow origin without call/park cannot COMMIT or deliver; both origins preserve immutable native hash/current connection fence/reconciliation and uncertain physical capacity. Keep existing workflow atomic claim/wake tests, shared message guard and registry/sample/native regressions. These are requirements for B1, not exercised proof at this gate. P06 retention keeps Workflow origin/call links; deletion cannot turn Workflow into Direct. P07 combined native/browser acceptance remains required, Linux native waiver unchanged.
