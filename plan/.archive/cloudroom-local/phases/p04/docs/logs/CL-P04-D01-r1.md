## 2. One process-lifetime owner and serialized SQLite dispatcher

Own connector work through bb.background.service. Acquire one exclusive nonblocking OS flock on a fixed file beside the public plugin database handle.name. Open0600 with O_NOFOLLOW; do not unlink lock files or infer stale ownership from PID/time. Retain fd until network/SDK/dispatcher tasks have actually settled and final writes complete. A second connector fails controlled admission/retries with capped backoff and never opens a socket or calls SDK. OS exit releases lock even after SIGKILL. Scope is that plugin profile/database; deployment uses one installation/company and no per-agent isolation.

Native feasibility proof already ran on this macOS/Node24.21.0: fs-ext2.1.1 compiled, a competing process was denied, graceful close released it, and owner SIGKILL released it without stale-file deletion. Files native-lock-probe.cjs/native-lock-proof-r1.txt and lock-probe-resource.json retain the evidence. Only that disposable fixture's pinned fs-ext install script (node-gyp configure build) was enabled; no global install policy changed. Linux native execution remains NOT EXERCISED under the user disposition.

Use only bb.storage.database() for plugin-owned data; set synchronous=FULL on its WAL connection and assert it. One dispatcher serializes mutations, using synchronous short SQLite transactions. Persist each related command/mapping/outbox/cursor change atomically, never keep a transaction open across SDK/network awaits. Keep correctness work in retained promises; no detached event/timer callback may submit SDK work or mutate storage.

Minimal tables: journal meta (installation binding, journal UUID, allocated sequence/ack cursor); commands (ID,digest,exact frozen wire/SDK input,state,thread/request/turn identities,deadline,terminal/tombstone data); session mappings (installation/session/thread,frozen selection/policy); immutable outbox (sequence,typed observation JSON,byte size); bounded public-event cursors/correlation/output state per mapped thread. Credentials never enter these tables. A command row is the durable local invocation; no separate broker or custom agent runtime.

## 3. Enrollment, secret/origin binding and local discovery

Settings: HTTPS origin, machine name, selected project IDs; status is available through local plugin CLI/status and Openbot presence, not a reachability claim of inference. A secret pairing-code field is transient and cleared after enrollment/definitive failure. Claim recovery secret and machine credential use Cloudroom secret settings (0600 files, not frontend/KV/journal/log/URL). Generate/persist claim credential before the HTTPS enrollment attempt; lost response retries the same claim and frozen enrollment identity, never another installation. Non-secret installation/journal metadata commits after the receipt; interrupted local finalization with a persisted credential goes recovery-required rather than manufacturing an empty journal. Re-pairing is explicit and cannot silently discard old journal/thread state.

Bind credentials to the approved canonical HTTPS origin at enrollment; changing origin while paired fails configuration instead of sending the old credential elsewhere. Reject userinfo/path/query/fragment/non-HTTPS and redirects on pairing; normal certificate validation stays on, WSS tests use trusted test CA. Credential only in Authorization header. Authorization rejection stops reconnect retry until explicit pairing repair/settings change. Ordinary network loss retains all identity/journal/native state.

Use bb.sdk.system.config().primaryHostId and public host/project/environment queries, not hosts[0], guessed files/ports, Electron or provider files. Require a connected persistent non-cloud primary host, supported platform, and selected project local_path source on it. Never advertise/select another host or a cloud/new-machine environment. Resolve the project checkout through Cloudroom's own explicit project-checkout environment provider with existing primary host and no path/branch overrides; do not let mutable project-default selection change a frozen operation. Confirm this public explicit form against actual source-built SDK before acceptance. If unavailable, refuse; do not fall back to another provider/workdir/model. ## 4. Durable cuts, acceptance and real turn correlation

Every incoming command strictly validates the current fence/installation/generation, closed fields/types, safe integers, frozen payload SHA256 and exact canonical deadline string, prompt/capacity/selected local selection. Same operation+digest returns saved state; changed digest conflicts. Never rebuild the deadline hash through Date; Date may only compare time. Canonical command field order follows the Rust types, with the existing actual Rust→Node proof extended to the real plugin decoder. New observations always receive a monotonically allocated sequence in the same journal transaction as the state they report.

Durable cuts:

1. Persist command+Receipt outbox before any local acceptance acknowledgment or effect.
2. Preflight exact frozen selection/deadline/capacity. A definitive preflight refusal is journaled before send; only before local SubmissionIntent.
3. Persist dispatch intent+SubmissionIntent outbox and deterministic SDK input before calling SDK. Check cancellation immediately before starting the call; no transaction crosses it.
4. Save returned thread/queue identity, session mapping and corresponding observation together before network send.
5. Save matching native request/turn state/output and observation together. Only server contiguous ACK allows outbox pruning; terminal data cannot be dropped on disconnect.

Recovery from a command already marked dispatching never repeats spawn/send/control. For create, positively find exactly one matching plugin-origin/project thread with installation/session/operation/digest metadata using bounded public reads; recover identity, never infer absence from a bounded listing. For send, only mapped thread/public event evidence can recover it. Missing local entry, missing journal/profile, multiple candidates, changed identity or no positive match remains recovery-required/uncertain. No --last, thread recreation, machine reassignment or fallback. Reconcile delivery is read/replay only; a pre-intent local command may be definitively refused for recovery rather than started on reconciliation. Cancellation/deadline never invokes a broad automatic stop.

### Correlation without unsupported request-ID guarantees

The local SDK ignores supplied API requestId for turn correlation: thread-send.ts:666 generates a new native client request ID, and SendMessageResponse returns sent/queued, not a native turn ID. Accepted p01 proof correlates unique prompt marker→client/turn/requested.requestId→turn/input/accepted.clientRequestId→same scope.turnId terminal. Reuse that public mechanism instead of changing native runtime/event ownership.

SDK input is the exact authorized user prompt prefixed by `[Openbot operation <canonical UUID>]\n` (57 UTF8 bytes). The original wire/user prompt limit stays32768 bytes; this fixed non-user metadata overhead is bounded separately (SDK input≤32825). Test both exact UTF8 user boundary and overflow; this is not permission or executable input. The header is visible in Cloudroom and lets users identify the corresponding Openbot operation. Persist exact SDK input before intent. Find exactly one public client request whose full input matches that saved input on the mapped thread and appropriate spawn/tell source, after the saved pre-call cursor. Then require its actual accepted native turn and matching terminal scope. Human/UI prompts without the exact header/full input cannot complete it; ambiguity/manual edits/gaps remain uncertain. Request IDs are evidence only, never idempotency. Initial thread metadata plus exact input narrows create recovery; no idle/latest-assistant completion. Native auto-retries/children are not automatically new Openbot work or permission.

Persist bounded event cursor/correlation/output per page; pages≤100 and bounded pages per poll, resume later rather than reading infinite history. Polling remains authoritative if events/hints are lost. Output only from matching native turn; cap256KiB UTF8 with explicit truncation, preserve character boundaries and mark replacement of nonrepresentable/NUL data. Unknown usage is null/unavailable, never zero. Known measured usage must belong to that turn and fit safe counters. Permission interactions are surfaced only with corresponding thread/turn evidence; user answers in Cloudroom, no tool auto-approval.

## 6. Bounds, reconnect and supervised shutdown

Enforce accepted limits at both peers: frame64KiB/chunk16KiB/logical2MiB, one ordered assembly/30s, heartbeat15s/stale45s/hello10s,8 unsettled effects,32 queued commands with8 control reserve, outbox64MiB. Strict physical chunk hashes cover current envelope bytes; journal payload stays immutable and is rewrapped under new current identity. No partial terminal ACK. Bounded incoming command queue and serialized SDK admission, with read-only recovery before new effects. Unknown/expired-but-physically-unsettled work consumes capacity until positive native terminal evidence, including across reconnect. Server Ready must not be bypassed. Disabled machines only perform existing explicitly authorized controls, never new effects.

Journal reserves worst-case final-observation space (3MiB/accepted outstanding command, covering the2MiB logical ceiling plus fixed receipts) before SDK effects. Stop/coalesce progress before allocating new sequences if only terminal reserves remain. Never overwrite an allocated observation or skip sequence to coalesce. Backpressure/refuse before exhaustion; if a command cannot be journaled durably, close/stop admission without SDK and expose recovery, rather than acknowledge or silently drop it. Bound local command/mapping history (initial4096 records each); completed acknowledged records can have prompt/output payload compacted to immutable tombstone data, never forget an operation identity while it could be replayed. Reaching the metadata cap stops new admission and surfaces a controlled capacity condition; p06 owns the reviewed retention/maintenance policy, not an unbounded cache or automatic destructive reset.

Connector owns WSS handshake/pairing timeouts, reader/writer/heartbeat/reconnect/poll promises and bounded exponential backoff with jitter (cap30s). Abort closes pending pairing/WSS work and propagates to real SDK HTTP calls through the reviewed patch; await actual calls, journal their ambiguous intent, flush and release lock before returning. No fake success/physical cancellation from abort. Gate proof must show lifecycle fits Cloudroom's5s drain with delayed SDK/network bodies and has no task/journal mutation after disposal. Local native work continues unless separately proven stopped. No detached correctness callbacks or broad queue replay.
