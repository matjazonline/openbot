

## CL-P04-D01-F1 — persist the pending enrollment identity before its first request

- **Status:** OPEN, 2026-11-08. Actionable architecture/correctness defect, **medium** severity. Workflow `implement-astra-reviewed-2-2`, phase p04, architecture round [CL-P04-D01-R1](agent-review-notes.md#cl-p04-d01-r1--combined-architecture-gate). Reviewer `/root/cloudroom_reviewer`, requested GPT-6 Astra/high, actual metadata unavailable. Worktree `/Users/mac03/dev/openbot`, main; phase start/review-base/HEAD `97e5d60dc538e26c7cb976a8d63772eed80baff2`; unchanged accepted-p03 source `1e4f5b2148970677a7f1c388fa5a38cc52b1e7685061a4fac15857ea6b1325d9`. [TASK](TASK.md), [REVIEW](REVIEW.md).
- **Reviewed decision:** [CL-P04-D01/r1](logs/CL-P04-D01-r1.md), SHA-256 `cf4f35a691e11bdd2f1c84f4aad69cce97c594bcb7599639840ae34381edac8b`, section3/line31. It requires saving credentials before enrollment and promises lost-response replay with the same frozen enrollment identity, but then says “Non-secret installation/journal metadata commits after the receipt” and routes interrupted finalization with a persisted credential to recovery-required. No prior durable pending-enrollment identity or distinguishable enrollment state is specified.
- **Actual consumer evidence:** `src/adapters/http/routes/local_machines.rs:124–142` requires both `x-openbot-pair-claim` and `x-openbot-installation-id` for status recovery. `src/application/local_agents/pairing.rs:232–250` passes both through; `src/adapters/persistence/local_agents/store.rs:159–173` matches the exact installation ID plus claim verifier. The machine credential cannot replace the missing installation header. The actual response-loss test (`local_machines_tests.rs:171–242`) succeeds because it retains the original installation ID. Original02B requires durable pre-request credentials and recoverable same-claim enrollment;04A/04B require restart/crash recovery and forbid manufacturing another installation.
- **Failure cut:** first pairing request commits on Openbot, then the plugin process dies before receiving/persisting the receipt. Under the stated metadata write order, the restarted process has its secrets but no durable original installation ID/bound pending request. It cannot issue the accepted status request or exact retry. Treating this ordinary enrollment interruption as journal loss/recovery-required defeats the promised response-loss recovery; creating a fresh identity would violate the contract. The same ambiguity affects the approved origin binding during an interrupted attempt.
- **Required decision correction:** specify which pending-enrollment identity and binding fields are durably saved before the first credential-bearing request, how separately persisted secret/settings/journal writes recover at every cut, and how a pending enrollment is distinguished from a previously paired installation whose journal was lost. Keep completed pairing metadata after the receipt where appropriate, keep credentials out of ordinary storage, and preserve the existing no-silent-rebind rule. Recovery must retain the original installation/claim/credential/origin and finish the same pairing through the existing API; this is not permission to weaken its identity checks.
- **Decisive planned verification:** crash/reopen before request, after server commit with lost response, after receipt but before local completion, and between each required secret/non-secret write. Assert the same installation and claim recover the same machine with no second enrollment/SDK effect and no credential sent to a changed origin. Separately prove deletion of a previously paired journal remains recovery-required and does not reinitialize it. A memory-only lost-response retry is insufficient.
- **Origin/lesson:** the gap is in this gated persistence decision, not a defect in accepted p02/p03. Existing original enrollment and crash-cut requirements suffice; no AGENTS/skill edit proposed. Resolution history: initially open in D01/R1. Inspection-only decision finding; no product failure reproduction claimed.
