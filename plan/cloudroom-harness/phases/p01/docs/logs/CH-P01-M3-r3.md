## Decision and observable behavior

Expose one static public Cloudroom plugin tool, `openbot_company_mcp`, with list/describe/call/status operations. The actual plugin callback receives trusted thread/project/signal context from Cloudroom, looks up its durable positive native mapping, freshly checks Openbot authority, and selects only the immutable published agent's MCP aliases. Unmapped/unconfigured/foreign threads get an explicit refusal. Static registration grants no company capability to ordinary threads.

List and describe expose frozen schemas and aliases. Call takes only an alias and bounded object arguments. Identity comes from authenticated explicit originating request/model-call context, never a model-generated request key. Status takes a returned opaque broker-call id as a reference, never as authority. The active native tool promise stays open while its real MCP workflow waits for approval; it returns only an effect result or an explicit terminal/unknown/cancelled outcome within its absolute bound. It does not return a nonterminal “pending, continue later” result that would let the originating native turn complete while dispatch remains authorized. Existing Openbot approval/run views show the human approval and its link during the wait. Completed MCP error envelopes remain MCP errors, unknown effects remain reconciliation-required, and transport failures never become successful model text. No credential, arbitrary endpoint, connection selector, reviewer, workflow identity or originating-operation selector is accepted from the model.

Each call is owned by a genuine, atomically admitted Openbot workflow running the existing `mcp.call` step. Openbot's normal worker obtains the real workflow job/lease/fence and executes existing McpActions and reviewed action gateway. The native proxy never manufactures WorkflowFence/AgentToolOrigin, borrows a fence from an unrelated run, directly decrypts a credential, or calls a remote MCP service itself. Manual native sessions and workflow-created native sessions both work.

### Proven producer contract, not runtime-current substitution

- A real `UserPromptSubmit` hook supplies a native CLI prompt_id while acknowledging the exact submitted SDK input. This is NOT the UUID supplied on SDKUserMessage: the probe demonstrates they differ.
- A real `PreToolUse` hook supplies that SAME native prompt_id and the model's actual tool_use_id.
- The real SDK MCP tools/call request carries that SAME tool id in request.params._meta['claudecode/toolUseId'], independent of model arguments and the transport request counter.

Build the explicit producer contract from that chain:

1. Before SdkSession.pushInput, record a bounded input-owner intent with the actual canonical ClientRequestId received on thread/start or turn/steer, exact submitted input digest, and a per-SdkSession epoch. Serialize acknowledgment of the pending input-owner queue. Do not treat a model prompt marker or SDKUserMessage.uuid as authority.
2. The SDK's UserPromptSubmit hook must match exactly one oldest pending bridge-owned input intent (same session epoch and exact submitted input digest). It permanently binds the native prompt_id to that intent's canonical ClientRequestId. Unknown, duplicate/conflicting or out-of-order acknowledgment refuses Openbot MCP; do not choose current/latest. This is an explicit trusted SDK submission acknowledgment, not interpretation of model-generated text. A native/local prompt not submitted by this bridge has no intent and receives no Openbot MCP authority.
3. PreToolUse binds the actual tool_use_id to the immutable prompt_id owner using that explicit native hook field. It cannot fall back to resident/current prompt, attachment state, input text or permission-policy fallback. Unknown prompt, changed tool identity/input, mismatched epoch or missing metadata refuses the proxy. Preserve prior A bindings while callbacks are possible, including after B is accepted. Hooks capture their exact SdkSession epoch/object; an old session callback must not look up a replacement resident session and inherit B's map.
4. The actual MCP handler reads the OUTER native SDK metadata toolUseId (never an argument named _meta), resolves the retained tool-use binding and forwards an explicit `{clientRequestId,callId:toolUseId}` originating descriptor. Never synthesize this from the currently running thread/turn or call counter. Bounded missing-map wait can cover hook ordering; failure is an explicit no-effect refusal. After process restart/lost producer map, refuse unknown old callbacks rather than reconstructing from current turn. The existing server receipt/reconciliation path remains available.
5. Carry this optional originating descriptor unchanged through the actual bridge schema/decoder, agent runtime, daemon contract/client, authenticated host/thread route and public PluginAgentToolContext.nativeInvocation. These consumers validate bounds and preserve the explicit source; absence remains absence even if ordinary runtime turn association was filled for display. Public context is readonly and cannot be supplied by model/plugin arguments. Openbot requires it, whereas ordinary upstream tools may continue using their current context semantics.

Existing instructions/complete skills/native permission support for other providers is unchanged. ## Structural identity, native read, dispatch and historical reconciliation

It uses retained frozen facts; it does NOT require the original actor's current membership, a live machine/connection/native operation, an active parent or an unrevoked grant. Missing or changed provenance always refuses; an ended owner is not missing provenance.
2. **Current native-client read authorization** at list/describe/status/result APIs verifies the current credential/generation/lease, current actor membership and session/harness/capability read authority. Retained lookup also requires the original actor to equal the authenticated current invocation actor and obeys existing workflow knowledge/view restrictions. It never dispatches. Native clients lose this access when revoked, while authorized operators retain their independent historical review path.
3. **Live effect authorization** at actual action preparation/freeze/credential opening/reservation/final dispatch verifies structural provenance AND original native operation/explicit request ownership, original actor/source authority, session/machine/credential state, deadline/cancellation, exact frozen agent binding and current connection/review/grants. Original operation completion/stop/expiry or parent authority loss forbids every later effect; a newer invocation does not replace it.
4. **Operator historical reconciliation** uses the existing reconciliation service's current operator/company/association/resource/knowledge authority plus structural frozen origin. Original actor removal, machine revocation, operation/parent termination or client disconnect does not block an otherwise authorized operator recording the historical applied/not-applied/unknown outcome. This never directly dispatches. Applied returns a recorded receipt; unknown remains reconciliation-required; not-applied does not restore native liveness. Any later execution still passes purpose3 and therefore cannot redispatch after revoked/ended ownership. Unauthorized operators/reviewers are refused.

The action remains a real workflow action with mandatory native provenance. Use the frozen reviewed operation version/schema/policy; current company MCP grant, review, agent binding grant and original actor/source authority remain live for effects. Use existing durable approval submission/resolution and workflow polling, with the original actor as configured human reviewer when required. Full native filesystem permissions do not bypass MCP policy. During approval the native tool promise remains pending, so its original operation/parked source remains live. An abort, explicit stop, deadline or native turn completion observed unexpectedly cancels dispatch eligibility; a later approval cannot revive it. Existing approval views/notifications expose the actual decision; no event stand-in is accepted as approval.

Conservatively classify broker arguments/results at the original actor's current access ceiling with content_exact=false, carrying a workflow-native parent's stricter source ceiling when applicable. ## Closed cross-owner ordering and propagation protocol

Avoid blocking cycles rather than imposing a new company-first order after an existing run fence. The following dispositions are part of the decision, not optional implementation advice:

| Entry | Ordering/allowed waits and propagation |
| --- | --- |
| New native admission | Authenticate/observe ids without owner locks, then existing account/company/actor/association authority, originating workflow owner when applicable, agent publication/source/grants, machine fence, native operation. All newly coupled owner acquisition is nonblocking under the contention rule below. Insert NEW broker run/execution/job/provenance after these checks; these unpublished rows cannot be owned by a worker. Reuse registry records as immutable reads; replay/status never locks an existing broker run while native locks are held. |
| Native status/replay | Current native read authority in its existing source-before-machine order, then MVCC reads of retained immutable call/run/receipt facts. Hold successful native authority locks through the existing reservation/final authorization transaction. Never wait for an original workflow owner while a broker owner is held. |
| Broker lease claim/validate/renew | Preserve existing run-first workflow fence/capacity order. They update only their existing native state, never acquire a broker/originating run lock and never call workflow cancellation while native locks are held. Their committed invalidation is itself durable evidence used by live dispatch/heartbeat and the bounded sweep below. |
| Native tool abort/cancel API | Authorize the exact originating native call and commit desired-cancel on that call only, without locking a broker run. Abort signal also ends the client wait. **Contention rule:** every NEW cross-owner lock acquisition that could invert an existing order is `NOWAIT`, including nested helper locks. Reuse authoritative validation under a scoped zero-wait equivalent only if every helper is audited; do not let an opaque blocking helper acquire another owner. Distinguish contended from revoked/invalid. Before first dispatch, return a controlled busy/no-new-dispatch outcome (or existing bounded workflow backoff where available); do not hot retry, silently default authority, or consume an approval. An already possibly dispatched action remains unknown/receipted according to its ledger, even if the new check is contended. No SQL transaction spans remote I/O. Use existing bounded lock/statement deadlines as an additional backstop, not as evidence that a blocking lock cycle is safe.

This protocol leaves ordinary workflows and B2 native lifecycle entry points unchanged except explicit eligibility/pinning predicates. Added cross-owner wait edges are forbidden; new run rows are not shared until commit. Prove these dispositions with actual competing transactions, not only sequential same-key tests.

## Deadline, cancellation, replay and retention

A call has one absolute deadline, min(native operation deadline, admission time+15min); retries, status and restart never extend it. The native tool Promise remains pending until terminal/result/unknown or that bound. Each Openbot HTTP request is independently bounded to at most15s; bounded polling with backoff serves the same native call intent. The actual pinned daemon tool transport already awaits a streamed response under its real signal; do not detach or inject an unadmitted continuation turn. No nonterminal pending result is returned to let the original turn retire. If any real provider/transport has a shorter deadline, honor the shorter cancellation and stop dispatch rather than detaching work. The native operation stays active while its tool awaits; normal completion can follow only after its admitted MCP calls stop waiting.

On deadline/abort/turn completion, desired cancellation and the native committed owner state revoke future dispatch immediately. An approval arriving afterward cannot authorize an effect. The existing effect ledger determines applied/not-applied/unknown; there is no automatic new call, request identity or workflow after timeout/unknown. Read/schema/result payloads fit existing budgets and at most2MiB at the native boundary; an oversized retained result gives explicit result-too-large/read-link without truncation or replay.

Retained status across a later turn is READ ONLY via the opaque call id and same actor/session/harness/current read authority. A replayed old native `(clientRequestId,modelCallId)` always addresses its original intent, even after operation pointer B, cancellation or local/server restart. It may recover an existing result/unknown/collected state; it cannot make B the owner or extend A. If the originating operation ended, its pending effect is cancelled/reconciliation-required rather than left eligible for later approval.

Active, parked or reconciliation-required calls pin their live native origin and broker run/provenance. Once both owners are resolved/terminal and the normal retention age is met, the existing run-first workflow collector may remove large action/run payload and transition the native call to an explicit tombstone in the SAME transaction. Keep immutable native invocation key, opaque call id, originating operation/actor/session/harness identity digests, original run UUID, content digest and terminal outcome. The live run FK is nullable only in that retired state, with a deferred witness proving the corresponding actual run no longer exists; it cannot be detached from a retained run. Native operation identity/tombstones remain the parent of call identities; payload/session cleanup waits for all live pins. The retired state cannot be admitted again and returns payload-collected, not an empty success. Preserve frozen broker definition/version references while live runs need them; collect unreferenced large artifacts using the existing workflow/publication retention rules. No collector holds native-owner locks while acquiring a run lock.
