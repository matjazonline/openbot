- Decision evidence: D1.1 migrates ReplyApprovalPolicy to principals and says account enrichment uses current locks; D1.3 specifies only selected-agent→principal capture locks. Neither defines how policy principals become the account lock set before existing company/run gates, or how the mapping is revalidated. - Actual evidence: action_authority.rs:42–93 currently extends the user prelock set from policy.reviewers(), sorts it, locks users FOR SHARE, then authorizes company. Account and principal UUIDs are different namespaces.
- Impact/schedule: directly reusing principal policy IDs as users misses the intended locks; locking a principal before resolving/locking its user can invert retirement. - Required correction: record an explicit ordered protocol for discovering, locking and revalidating principal→account facts across the affected prelock consumers and lifecycle writers. Preserve existing bounds; include deterministic competing production account-retirement/approval schedules that assert coherent success/refusal, not generic timeout/deadlock. Do not settle the protocol implicitly during source editing after this gate.
- Instruction lesson: root concurrency rule and verification-contract guidance already require competing claimants and actual lock order. The changed wire namespace reaches a synchronization protocol outside notice composition. No new instruction amendment proposed.
