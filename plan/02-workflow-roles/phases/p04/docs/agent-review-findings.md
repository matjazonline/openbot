- Classification: actionable architecture/recovery/resource-bounding gap, **P2, OPEN**.
- Decision evidence: D1.2 bounds two automatic hops per case/run and uses a unique case/run key. D1.4 sends an agent notice by inserting an ordinary canonical message plus workflow admission intent into its current default desk. - Actual source: thread/inbound.rs:712–769 creates new intent identities carrying supplied directives; application/workflow/message_admission.rs:485–520 constructs a fresh Message trigger/root admission from each intent. These are not child runs sharing an existing root budget. The existing internal transport hop guard is in application/use_cases/thread/ingest/policy.rs:153–176; direct reuse of persistence inbound::commit_on does not invoke it, and no proposed rule says how escalation-origin hops survive another failure. Stable keys deduplicate one notice attempt, not the next case/run.
- Counterexample allowed by the proposed contract: an agent's notification desk has an escalation-enabled binding whose notify role points to that agent (or two such desks point to each other); the workflow handling each escalation message fails/refuses. Each new root receives a distinct case and emits a new stable message/intent, so every local two-hop limit is respected while the automatic chain continues indefinitely. Internal-only reply policy avoids SMTP; it does not stop these DB admission/event cycles.
- Required correction: decide and persist an explicit bounded handling rule for escalation-generated admissions and their subsequent refusal/failure, including authenticated origin/provenance and terminal owner attention. The review does not choose the mechanism. Add actual worker→agent message intent→refused/failed admission tests for self and cross-desk cycles, proving a finite bound, observable terminal disposition, and no fresh-root loophole. Preserve ordinary user-triggered escalation and retry idempotency.
- Instruction lesson: existing bounded-work/recovery guidance applies. A bound per entity is not a bound on a cycle that creates new entities. No new instruction proposed.
- Resolution history: opened2026-11-12 against D1/r1; static contract/caller analysis only.

- Decision evidence: D1.2 promises the complete nearest eligible holder set, described as “all person holders, or the eligible single agent”; D1.4 defines both person and agent delivery. Do not import model-step single-agent cardinality accidentally into notifications or filter away a conflicting local holder without a stated rule. Add discriminating production projection/ladder cases for mixed and multiple-agent reviewer roles and the bound; original no arbitrary first-holder and nearest-ancestor rules remain applicable.
- Instruction lesson: existing mode/discriminator impact guidance applies; a resolver with two task-specific modes does not define a third consumer's semantics. No new instruction proposed.
