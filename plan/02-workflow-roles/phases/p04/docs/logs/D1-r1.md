# 02WR-P04-D1 / r1 — complete escalation and follow-role contract

Proposed architecture gate for cohesive B1 (original04A+04B). Source prerequisite is accepted p03 5bd5645a4256002c4202f11f1bdfdea9814c98188e1d6e2dcbd181cd503ba1db. No p04 source edits. Only channel.call-denied is deferred by C001/r1. C002/r2, C003/r2, C004/r3 remain binding. This decision supplements the original plan's sketch to represent no-run refusals, terminal runs, multiple holders and current person-only notification infrastructure honestly.

## D1.1 Binding and time configuration

Add validated EscalationPolicy with DepartmentRole notify and typed HopLimit (1 or2) to immutable BindingConfiguration and all its producers/serialization/persistence/forms/readers. Binding update creates a new configuration revision. Optional means disabled unless configured; no compatibility decoder. Activation and department detach use the existing company/channel serialization, check escalation even without a role-bearing bundle, and refuse binding.escalation_needs_department for company-only or unowned channels. Department-owned thread associations qualify through their channel. Existing role department validation remains.

AppConfig reads ESCALATION_ACK_HOURS (default24, integer1..168, startup rejects all other values). NotificationMailSettings carries the validated value into the existing NotificationWorker, including explicit test constructors. Capture it when materializing the first hop, then keep it immutable on the case: retries/config changes do not move a deadline. First notice and subsequent hop each receive that duration from durable hop creation. Tests cover absent/1/168/0/169/malformed configuration and create-update-read binding roundtrips plus activation/detach races.

## D1.2 Honest durable escalation subject, immutable ledger and bounded ladder

Introduce tenant-scoped escalation case, hop, recipient and administrative decision/command facts in the init schema, with composite FKs. A case identifies exactly one source: an actual run, or a definite admission refusal with immutable binding revision and canonical source key. A no-run refusal never gets a fabricated run_id. Run cases retain run/execution/step and typed static reason; refusal cases retain step/role, source identity and desk. Snapshot the opted-in policy and originating department when creating the case. Stable unique keys are company+run for run failures and company+binding+revision+source for refusals; ON CONFLICT replay returns the existing case. A run may escalate only once automatically. The first failure reason is retained; later events cannot overwrite it.

workflow_run_escalations is the append-only hop ledger, keyed company/case/hop, with nullable real run_id, hop1|2, typed role/reason, frozen department, created/deadline and settlement facts. Recipient rows capture the complete bounded nearest eligible holder set (all person holders, or the eligible single agent; no arbitrary first person), immutable labels and identity. Empty sets are represented by the hop row, never by a fake recipient. Resolve hop1 in the originating department using the existing nearest-role rules; hop2 is only the originating department's parent lead. Snapshot the originating department identity, but use the current parent and current holders at the moment hop2 is created. A deleted/retired department has no holder and proceeds to owner waiting. Policy hops1 never creates hop2.

Create one durable notification_events control event per case/generation: start1, advance2 and final3. Use existing leases/fences/retry limits/backoff/dead-letter visibility; no second queue or scheduler. Control events have a distinct typed source/action; they do not create bogus user notifications or email. Start atomically inserts hop1, bounded recipient facts, corresponding notice events and the next available_at deadline event. Empty hop1 advances immediately when hops2 is allowed. An unsettled hop1 deadline creates hop2 once; empty hop2 or its deadline marks owner attention. Hops1 goes to owner after empty/expired hop1. Owner attention is a waiting-on-a-person item, never an automatic third hop. Unique case/hop and per-recipient event keys prevent replayed or competing sweepers from resending a hop. Existing worker claims remain bounded; failures leave backoff/dead-letter state and a poison batch is not immediately reclaimed.

## D1.3 Triggers and authored handling

Emit the case/control event in the SAME transaction as the authoritative refusal or terminal transition. Admission::create captures roles before inserting a run; a missing-holder capture error therefore has no partial run. Handle this typed error at the admission owner: retain authentication/current binding/claim validation, persist the refusal case, and return the same definite refusal without committing a run. Also cover refusals produced by application preparation before persistence admission: route through a purpose-specific fenced persistence operation that revalidates binding/revision/source and cannot enqueue unauthorized/obsolete/manual forged sources. Message and schedule consumers must not both create duplicates; replay uses the canonical key. Accepted inbound message remains delivered and definite intent refusal/noRun/noRetry remains unchanged.

For run outcomes integrate at authoritative terminal writers (recovery final failure, wait failure/expiry, run-deadline maintenance and guard retirement) rather than polling all terminal runs. Human decision deadline uses actual decision timeout routing. A selected authored final-error handler suppresses the default ladder; record/escalate only when no handler actually accepts the outcome. A child failure waits until parent propagation decides whether an authored handler consumes it; do not notify prematurely from the child and again from the parent. If a deadline/guard bypasses routing, classify its specific nonhandled terminal reason explicitly. Never revive a terminal run just to park escalation acknowledgement. Cancellation by a user is not a sweeper/guard failure and does not itself start a ladder. Only the explicitly unavailable channel.call trigger is absent.

## D1.4 Existing notification path, person and agent delivery

Extend typed notification source/action variants for escalation control, escalation recipient notice, and followed decision reviewer notice. Retain the existing DeliveryFailure path and its current policy. New sources are handled through dedicated projection helpers within the existing NotificationPersistence/NotificationWorker port: resolve, compose if needed, fenced revalidation, atomic source/event/projection/outbox commit. Current authority/visibility/preferences are rechecked at commit; no payload/proposal contents are placed in notices. Only safe labels/typed reason/step and secure link appear. Resolved or retired recipients withdraw/cancel old notice/outbox through existing cancellation protocols. New events retain stable logical delivery/message keys independent of attempts.

People receive ordinary in-app notifications plus email unless opted out; the target remains a principal and account/email is current delivery enrichment. Never equate an agent principal with a user account. An agent notice is an internal canonical message + workflow admission intent in its CURRENT existing default desk (company_agent::default_desk_key and provisioning result), committed with the event fence and notice receipt. Reuse thread::inbound::commit_on on the caller's transaction, exposed only inside persistence, with an explicit system/application envelope, a stable message key, actual active binding/configuration snapshot and internal-only reply policy. Validate channel enabled/admission/access and current agent/default desk association; no SMTP loop and no direct workflow start. The notification is routing metadata, not a role privilege grant. Plan03 must replace ONLY this destination adapter with principal binding routing after reset, not carry default desks as compatibility infrastructure. Missing/disabled/deleted agent desk produces an observable undeliverable recipient and advances the ladder rather than claiming successful delivery. Agent receipts store principal/message/intent, not recipient_user_id. Existing user list/open queries select person projections; administrative decision and run views retain agent delivery history.

New projection commits discover recipient account/channel hints without locks; acquire sorted channel gates BEFORE account locks, then sorted accounts (where needed), then company NO KEY UPDATE, run/source/decision, then event/fence. Revalidate all hints under these locks; stale projections retry, lease loss rolls back. Control events need company/source/event but no accounts; agent channel gates are acquired from hints before company. Do not add account locks after company to any role/lifecycle writer. Old-source projector protocol is unchanged unless actual shared cancellation ordering requires an explicitly reviewed affected adjustment. New variants are exhaustive in renderer/list/open/census/monitoring tests.

## D1.5 Audited administrative decisions, same UI and current authority

An escalation administrative decision is a real separate typed decision row linked to its case/hop, so no-run and terminal-run subjects do not weaken workflow_decisions' run/wait invariants. Render it within the existing workflow Decisions UI/navigation, including waiting-on-a-person owner view, and expose authenticated API plus the existing agent tool surface to the same purpose-specific command service. Do not fabricate a Business wait, workflow execution or proposal. Commands are append-only acknowledge/reassign/cancel with actor account AND authenticated principal where applicable, stable bounded command key and fingerprint. Replay returns its prior result; changed-payload reuse conflicts. Settlement is serialized with hop advance and notice commit under company/case locks; simultaneous actors yield one settlement and one result.

A current assigned person with current company membership and source payload clearance can acknowledge or explicitly reassign this escalation to an eligible same-company person/agent; these actions settle only the administrative escalation. Current owner/admin can also do so and act on owner attention. Cancel additionally requires the existing actual run-control authorization; no-run cancellation is unavailable. Terminal cancellation is an audited already-terminal result, never revival. Roles alone grant no workflow-control, protected-approval, token, data-access or administrator privilege. Agents act only through the actual authenticated run_as account/tool authority; owner/admin may settle as operator, but principal assignment never substitutes for an account. Do not grant an agent privileges merely to make it acknowledge. Deleting/demoting recipient, revoking membership/clearance or changing run authority invalidates new commands.

Explicit reassignment settles/stops the automatic ladder and creates an audited manual assignment with one fresh target notice keyed by the command. This is a requested new assignment, not automatic resend of a run/hop. Retain the original automatic hop ledger and labels. Manual assignment chains are bounded32 per case with an explicit limit error; each command is idempotent. Current manual assignee may acknowledge/reassign; cancellation keeps run-control checks. No timer keeps retrying a settled automatic hop. Escape every displayed label/reason, hide inaccessible payload links, show disabled controls and resulting progress in the same UI. Browser/API tests exercise actual submissions, not only cards.

## D1.6 Follow-role specification, context and sealed later resolutions

Compile reviewers_follow_role as a static bool on decision.human, defaultfalse for new source definitions; reject nonboolean/dynamic values and non-Business/protected approval use. It is part of the immutable published artifact/digest. Agent selection stays admission resolution0 and all model/agent readers retain their0 filter. Pure pinned-principal decisions and unflagged/settled decisions are unaffected.

Freeze the original desk department context in the canonical root dependency manifest, with a guarded normalized context pointer; child ownership reuses the root context rather than consulting a moved child desk. This is distinct from the originally chosen ancestor department on each role binding. Later People resolution starts from this frozen desk department but follows CURRENT parent topology/holders; moving/clearing the current desk does not silently change that frozen context. Topology changes or retirement of a context/ancestor synchronously refresh affected parked decisions, using the same resolver as role writes. No live role lookup in ordinary execution or protected approvals.

For a flagged parked Business decision, persist immutable selector specification (literal roles + pinned principal identities), frozen context, and selected assignment revision. On initial park resolve current eligible People holders under company serialization; if it differs from admission0, append a new resolution before parking. A later resolution has its OWN immutable canonical fact keyed root/manifest/version/step/role/revision, including exact sorted principal set (possibly empty), chosen department/context and typed refusal if resolution is unusable. Normalized workflow_run_role_bindings revisions>0 must match this canonical set exactly at commit; complete-set deferred guards reject missing/extra/rekeyed/forged members and all updates/deletes outside tenant/run deletion. Nonzero revisions never contain agents. Sequence allocation is serialized by company/root ownership; no max+1 race outside its lock. An empty fact exists without a fake member row. Decision assignment points to the exact resolutions it selected; another child/decision at the same step does not silently change it. Membership facts remain valid history after principal retirement.

The effective current reviewer set is the deduplicated union of pinned identities and current eligible person holders of all named roles, bounded16. Preserve unchanged pinned identities/labels as facts; current membership/visibility still determines voting authority. Changed role-derived current rows are replaced, with each removed row first retained as immutable reviewer history including label and notice identity. A principal selected by both pinned and role remains pinned. Assignment revision facts seal the complete effective current set, including empty, selected role revisions and immutable labels; guards validate current rows exactly against the selected assignment. Existing decision submission/history/readers continue to use only current rows; expose historical assignments separately in history. A resolver overflow/unusable role is an explicit parked assignment refusal with no effective reviewers until repaired, not silently dropping holders or letting an incomplete subset vote. Pure pinned decisions remain untouched. Proposal digest/artifact/checkpoint/revision and previous submissions are never edited.

New followed reviewers use a DISTINCT pending durable notification proof on the reviewer row (notification_event FK with exact company/decision/principal/assignment binding), mutually exclusive with actual-delivery and provable opted-out modes. This permits same-transaction role-write replacement without acquiring accounts after company or pretending an unsent notice is an opt-out. The projection worker later resolves current account/preferences and atomically commits delivery or true opt-out proof under the ordered protocol. All producers/consumers distinguish pending/delivered/opted-out explicitly. A database caller cannot attach an arbitrary event to authorize a reviewer. Ordinary pinned/unflagged parking keeps the existing synchronous provable-notice mode. Empty effective set stays parked with its existing deadline and atomically creates the opted-in escalation source; a role assignment can repair it and withdraw still-open empty-reviewer escalation. A settled escalation remains audit history.

## D1.7 Synchronous hooks, bounded work, lifecycle and deletion

Every actual role placement/clear writer (assign_department_role_on, place_in_department_on and equivalent membership/topology/deletion paths) calls one purpose-specific refresh_on after the mutation, before commit. It uses the same canonical People resolver, current-row replacement, assignment history and durable notice enqueue path. Calls from lead-desk provisioning/repointing participate; no hook only in the public assign_role wrapper. Principal retirement clears every held role and appends the existing administration audit in that transaction before principal demotion/deletion; never appoint a replacement person. Refresh sees final postmutation role/membership state. Agent and member/account lifecycle producers participate even when their SQL deletes roles indirectly. Retirement of a nonholder with no affected follow decisions makes no spurious history or notices.

Bound at most256 concurrently parked follow-role Business decisions per company, enforced when parking under company serialization, so every role/topology/lifecycle transaction can refresh the complete bounded set rather than silently truncating. At most16 effective reviewers, at most2 named roles/decision and existing department hierarchy bounds apply. One writer may refresh all256 (explicit bound) and only changed assignments append facts/notices; no full historical run scan. Every role writer takes company NO KEY UPDATE before principal/placement/follow-decision locks; deterministic decision/role ordering. Vote uses the same company then run/decision order and cannot commit against a removed current reviewer. All source/event locks follow that order.

Account retirement already locks users before companies. Strengthen its sorted touched-company locks (currently KEY SHARE for nonowners) to NO KEY UPDATE BEFORE membership/principal/role changes; preserve user-before-company and deterministic company ordering. Membership removal similarly takes company before member/principal/role changes. Role writers never acquire user locks. New guards validate member/person identity under company serialization without adding user SHARE after company; account retirement has to reach company before demotion, so it cannot race this proof. Deferred relationship/sealing constraints still enforce identity on bypass callers. Run retirement and notification commit revalidate current authorization, preserving C004/r3.

The known inherited same-workflow-tenant owner account-deletion FK failure is an explicit affected lifecycle dependency here when that owner holds a role. Permit the narrow init-schema change making workflow_decisions_action_identity DEFERRABLE INITIALLY DEFERRED (same composite identity, no ON DELETE relaxation): tenant teardown can delete both referencing decision and intent within one transaction, but orphan/wrong identity still fails at commit. This is a p04 fix, never rewrite p03's historical gap/disposition. Test actual committing owner account removal with an active role/follow decision and protected action provenance plus direct wrong-identity/deletion rejection outside full teardown. If other inherited blockers emerge, retain failures and assess scope instead of claiming commit coverage.
