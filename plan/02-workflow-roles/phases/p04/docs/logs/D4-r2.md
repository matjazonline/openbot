## D4.1 Durable tenant-scoped origin identity

Create an internal immutable origin token per authentic original agent notice, minted only from a real workflow_escalation_agent_receipts insertion inside the fenced notice transaction. Deterministic token id may equal the original notice UUID; no wire/client field can mint it. Composite company+id keys/FKs prove tenant scope. Token has an optional company-scoped live notice FK. Source notice/case history retention may clear that live reference using FK ON DELETE SET NULL(notice_id), preserving company and immutable token identity. A guard permits only that source-deletion clearing, never arbitrary replacement/clearing while source exists. Tenant deletion cascades all owned facts. Do not make a live descendant depend on retaining its source case forever.

Separate immutable normalized run/message origin links reference that token (one origin per canonical run/message, not an unbounded origin set). The direct receipt remains delivery audit. The independent canonical-notice target fact and ownership seal below preserve source/message/intent/default-binding/revision relationships beyond source-receipt retention. Origin alone is suppression, never acknowledgement or settlement authority.

- Child/rerun run INSERT derives the exact predecessor's run origin using the existing parent_run_id/rerun_of_run_id relationship. Source proof is required on INSERT; a nullable post-retention pointer is not a way to insert an unproven new origin. Clearing follows the same narrow absent-source rule as token live-notice clearing. Actual active child/rerun/message behavior after source retention is tested.

At most one origin link per owner and existing finite child/rerun/relay budgets remain. No existing bound is raised. Owner/member visibility and all destination admission authority still apply.

An origin-bearing owner never starts another automatic case. Only the existing intended handling-root owner can settle original recipient handling failure. Descendant failures remain their typed original audit history linked through origin; they cannot mark a still-capable root failed. Authored routes and explicit new authenticated user work retain their existing semantics. Success alone is not acknowledgement.
