# 02WR-P04-D4 / r1 — durable internal notification causality

Architecture supplement to accepted D1/r3 (especially1.9/1.12), D2/r2 and D3/r1. No origin-propagation implementation yet. Original intended-root receipt/ownership and terminal settlement remain unchanged. The purpose is to implement the promised authenticated suppression across descendants, reruns, generated canonical messages and the existing internal email relay, including retention. No backward compatibility: edit init schema and use fresh disposable databases.

## Original constraints, actual owners, scope

D1.9 and D1.12 remain authoritative: exactly one intended handling root per original agent notice; descendants and reruns retain suppression but cannot claim intended-root ownership or prematurely mark that recipient failed; ordinary new authenticated user work does not inherit merely by sharing a thread; authored error routes suppress unhandled failure; case/hop/notice/root limits unchanged. No new client origin flag, wire header, route privilege, public cross-company transport or direct workflow dispatch.

Actual source owners: receipt writer notification/agent_notice_message.rs commits private canonical message/intent/receipt under event fence; admission_write.rs::insert_admission and existing handling-root capture own root admission. admission_write.rs::insert_run is shared with actual children/reruns. message_publish.rs::write_destinations_on writes canonical workflow_message_destinations; channel_reply_publish.rs::write_publication atomically records its canonical message/delivery in channel_reply_decisions. Both call message_writer.rs::write_destination_on. Internal email transport is EmailSender::relay_internally -> InternalMailRelay -> thread/ingest/relay.rs -> canonical thread/inbound.rs. Current relay::resolve_internal_destination explicitly rejects cross-company destinations; preserve and test that rejection, rather than introduce cross-company delivery. D1.9's suppression requirement applies to every actually accepted internal hop; no absent cross-company producer is claimed exercised or implemented. Any later cross-company capability must gate origin translation before it can accept delivery.

## D4.1 Durable tenant-scoped origin identity

Create an internal immutable origin token per authentic original agent notice, minted only from a real workflow_escalation_agent_receipts insertion inside the fenced notice transaction. Deterministic token id may equal the original notice UUID; no wire/client field can mint it. Composite company+id keys/FKs prove tenant scope. Token has an optional company-scoped live notice FK. Source notice/case history retention may clear that live reference using FK ON DELETE SET NULL(notice_id), preserving company and immutable token identity. A guard permits only that source-deletion clearing, never arbitrary replacement/clearing while source exists. Tenant deletion cascades all owned facts. Do not make a live descendant depend on retaining its source case forever.

Separate immutable normalized run/message origin links reference that token (one origin per canonical run/message, not an unbounded origin set). The ordinary direct notice receipt and intended handling-root table keep their stronger source/message/intent/default-binding/revision relationships. Origin alone is suppression, never acknowledgement or settlement authority.

## D4.2 Exact automatic derivation and sealing

Use the actual normalized persisted ownership edges, never caller input/run input/thread ancestry/Message-ID alone:

- Original notice receipt seals its canonical message's origin and token in the same fenced transaction. Lost/stale notice attempts roll back token and message origin too.
- Child/rerun run INSERT derives the exact predecessor's run origin using the existing parent_run_id/rerun_of_run_id relationship. Source-message admission derives the exact canonical message origin after workflow_admissions INSERT. Deferred complete-set checks cover insertion order: omission, foreign tokens, unrelated manual runs, substituted parents/messages, changed token, and extra links fail at commit. Existing frozen run identity/source guards remain. No unbounded recursive ancestry query.
- Canonical workflow_message_destinations INSERT derives message origin from its actual producing run. A final channel reply publication derives from the actual run bound to its proposal/decision when the canonical message/delivery is sealed. Cover both outputs, agent tool-message actions and their wrappers. A raw unrelated canonical message cannot claim a producer; deferred or immediate guards prove exact normalized producer ownership. Changes/deletes of origin links are rejected while canonical owner exists.
- Source rows may be physically retained for less time than their downstream work. Origin links retain the immutable token even when an optional source-run/message/delivery FK is cleared by legitimate source deletion. Source proof is required on INSERT; a nullable post-retention pointer is not a way to insert an unproven new origin. Clearing follows the same narrow absent-source rule as token live-notice clearing. Actual active child/rerun/message behavior after source retention is tested.

At most one origin link per owner and existing finite child/rerun/relay budgets remain. No existing bound is raised. Owner/member visibility and all destination admission authority still apply.

## D4.3 Server-authenticated internal relay proof

Extend only server-internal transport/app context with typed delivery/part provenance from the ACTUAL DeliveryRecord/RenderedPart handed to EmailSender. This proof is not serializable inbound JSON, a MIME/header field, an origin boolean, or a client-selectable routing flag. Propagate it through the private internal relay ingress into canonical commit. Public network adapters cannot construct this proof from inbound headers. Avoid silently-successful port defaults; mocks state actual behavior.

At canonical receiving commit, prove the exact company/source channel/delivery/part key against persisted sealed delivery/part data, recipient destination, RFC key and canonical content. Verify source producer's immutable origin by indexed company+delivery/message keys. A guessed/foreign/missing/mismatched provenance is a definite controlled refusal with no message/intent/token/root committed; never accept it as unmarked new work. Ordinary non-workflow application deliveries use their own real delivery proof and legitimately derive no token. All real email sender calls supply proof. Replace simulated internal relay fixtures with authentic proof fixtures or explicit application-delivery fixtures; preserve original discovered test names and assertions. External spoofed headers/RFC ids cannot mint or erase origin.

The existing provider/delivery lease fences, durable part payload, dedup hash, recipient/source authorization, gate order and relay hop/trace limits remain; origin propagation does not authorize stale provider work or a new source/destination. Any proof needed by a transaction is discovered before its established lock prefix, checked again at the actual write, and cannot introduce a gate/account acquisition after company. Do not take a foreign tenant's case/decision lock. The current cross-company relay path refuses before canonical acceptance, so no source case is read/mutated across companies. No SMTP fallback is allowed to wash a server-recognized suppressed internal effect into an unmarked local workflow.

## D4.4 Failure/history/retention

All automatic case producers (admission refusal, pending/pure failure, actual I/O final retirement, parked wait/decision/child propagation, expiry/guard) check the immutable run/message origin. An origin-bearing owner never starts another automatic case. Only the existing intended handling-root owner can settle original recipient handling failure. Descendant failures remain their typed original audit history linked through origin; they cannot mark a still-capable root failed. Authored routes and explicit new authenticated user work retain their existing semantics. Success alone is not acknowledgement. Explicit ack winning serialization remains settled; later failures never revive the ladder.

Retire origin links with their canonical owners using company-scoped cascades and narrow immutable-guard deletion exceptions. Keep tokens while ANY message/run/receipt/retained source depends on them. Add bounded orphan-token cleanup to existing retention work, with indexed reference checks; no new daemon/queue. FK protection and actual competing propagation/cleanup tests prevent deleting an in-use token or silently accepting unmarked work. A token whose entire source context is retained away still suppresses but confers no source-case visibility or action authority. Tenant teardown must remove all tokens/links/receipts without relaxing unrelated retention FKs.
