## 02WR-P05-R1/F1 — Two departments-doc escalation sentences state behavior the code does not have

- **Context:** 2026-11-14; round [02WR-P05-R1-N1](agent-review-notes.md); batch p05 B1 (docs), batch review; reviewer Claude Code subagent B, Opus 5.5 `claude-opus-5-5` (effort requested xhigh, not visible to B); phase `02WR-P05`; worktree `/Users/mac02/.gui-cloudroom/plugins/environment-git-worktree/host-data/worktrees/thr_jt43h4qc8d-1/openbot`; base/HEAD `2bbe2649`; digest `905f05c23d9b8b0894467a6601ddf89f81d36b06f8bef29b1973fa6236efb28f`.
- **Classification:** actionable defect, P3 (minor); requirements/documentation. Origin: implementation (B1 docs), not a gated decision.
- **Evidence:**
  1. `docs/departments.md` "Escalation": "A notice only says that something needs attention and links to the escalation decision, which shows the run, the step and the reason." That holds for person notices, which are payload-free (`notification_worker::compose_email`; p04 F6 disposition). It does not hold for agent notices. `src/adapters/persistence/notification/agent_notice_message.rs` `commit_on` builds the agent's private message body as `A workflow needs action.\nReason: %s\nStep: %s\nOpen: /ui/workflow-decisions/escalations/%s` from `workflow_escalation_cases.reason_code`/`step_id`. So the agent notice itself carries the reason code and step.
  2. `docs/departments.md` "Roles": "Nobody is appointed in their place: a department left without a lead reports 'no holder' the next time something escalates to it." Both resolvers walk to the nearest ancestor that holds the role: `application/workflow/roles.rs::resolve_role` and `application/workflow/escalation_recipients.rs::resolve_notification_recipients`. The same doc's hop-1 bullet says so too. A department without a lead therefore yields `no_holder` only when no ancestor holds the role, or at hop 2, which reads the parent department alone (`escalation_hops.rs::select_on`). The `no_holder` hop resolution is written only to `workflow_run_escalations.resolution`. No HTTP route, page or API exposes it (`rg no_holder|recipient_limit` over `src/adapters/http` finds only the admission error mapping). Nothing "reports" it to an operator except the admission refusal `workflow.role_no_holder`, which is subject to the same ancestor rule.
- **Required:** plan file 05 Batch 04A: "Name only behavior the code has". Root `AGENTS.md`: production documentation must not promise behavior the code lacks. Impact is low, but a reader of (1) would wrongly conclude that an agent desk's thread never holds the reason or step, and (2) contradicts the hop-1 rule a few paragraphs below it.
- **Suggested correction:** (1) say that a person's notice only links to the decision, while an agent's private notice also names the reason code and step. (2) say the role is cleared and nobody is appointed in the holder's place; until someone is assigned, the next escalation or role step uses the nearest ancestor that holds the role, and is refused as no holder (or advances, for escalation) when none does. Docs-only; no Rust/DB suite needed (root AGENTS.md).
- **Instruction lesson:** the author traced each doc claim to the code path for the *typical* recipient (person) and did not repeat the trace per recipient kind. A candidate instruction, scoped to doc batches in this workflow: when one sentence covers several variants (recipient kind, hop, role), trace it for each variant. Hypothesis, single occurrence.
- **Resolution history:** 2026-11-14 recorded, open.
