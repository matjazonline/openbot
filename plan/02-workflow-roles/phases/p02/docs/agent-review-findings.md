## 02WR-P02-D1-R1/F1 — Define the role capture/deletion lock order before relying on company serialization

- Classification: actionable defect; severity P2; architecture/concurrency. Status: OPEN.
- Decision evidence: TASK D1.2 (line24) proposes existing company/channel serialization plus principal/agent shared-key locks; failure invariant line31 and AC5 line41 promise coherent competing admission/deletion. No order is specified between the newly read principal and agent or the principal-demotion channel updates.
- Actual source: admission.rs:11-61 acquires company NO KEY UPDATE then association channel SHARE before capture; agent_authority.rs:49-63 later takes agent SHARE. agent.rs:437-462 takes company KEY SHARE then agent UPDATE, and finish_agent_delete_on:465-501 demotes the principal before deletion. init_schema.sql:15537-15561 removes derived grants and UPDATEs their channels during demotion. Company KEY SHARE is compatible with NO KEY UPDATE, so it does not serialize these two paths.
- Impact/schedule: deletion can own agent UPDATE while admission owns channel SHARE. Deletion's demotion then waits to UPDATE that channel, while admission waits for agent SHARE. Adding principal KEY SHARE before the agent also permits an agent→principal versus principal→agent cycle. The eventual published-revision FK refusal occurs after demotion work and does not prevent this cycle. A generic timeout/deadlock is not evidence of the intended coherent capture protocol.
- Required correction: record one explicit ordered protocol covering role holder reads, selected agents, company/channel gates and production retirement/demotion; identify any affected deletion/memory callers and their checks. Add discriminating competing schedules that exercise these intermediate locks and reject deadlock/timeout as an accepted business refusal. Reviewer does not select the implementation mechanism.
- Instruction lesson: existing rule already requires tracing shared callers and testing competing claimants; the missing evidence is the compatibility/order of the actual lock modes, not an absent general rule. No instruction amendment proposed.
- Resolution history: 2026-11-11 opened against D1/r1. No source changes or behavioral reproduction claimed.

## 02WR-P02-D1-R1/F2 — Seal the membership of a frozen role resolution, including inserts

- Classification: actionable defect; severity P2; architecture/immutable state. Status: OPEN.
- Decision evidence: D1.3 (TASK line25) specifies row FKs, kind/identity insert validation, one-agent uniqueness and update/delete rejection. D1.7 (line29) reserves later resolution revisions for human follow-role. No mechanism is stated that freezes the *set* of principals in resolution0 or seals a later resolution after its creation.
- Counterexample to the stated guard: after committing a human-role resolution, a new row for another valid person under the same root/manifest/version/step/role/resolution0 passes the described tenant FKs and kind check; the partial agent uniqueness rule does not apply. Existing rows need not be updated or deleted, yet admission's reviewer set changes. Similarly, the proposed guards do not establish that the initially committed role rows exactly cover the frozen source requirements. This is a shared p02/p03/p04 schema contract, although human role input parsing belongs to p03.
- Required behavior: README decision2 and 02B.1 require an immutable admission result; p04 permits a distinct new resolution rather than editing an old one. Existing agent manifests show the distinction: init_schema.sql:12574-12631 combines update/delete rejection with exact membership validation against canonical immutable content. The proposed role relation currently describes only the former protection.
- Required correction: define how each completed resolution's membership and requirement identity are sealed, how late inserts into resolution0 (and completed later resolutions) are rejected, and how legitimate future human reassignment can append a distinct resolution without reopening old membership. Add negative SQL tests for late member insertion/incomplete or mismatched capture and positive teardown/future-resolution boundary tests as applicable. Do not implement p04 behavior in this phase merely to address the contract.
- Instruction lesson: existing persistence invariant and verification-contract instructions cover this. Immutable rows alone do not prove an immutable one-to-many fact; record the complete-set invariant in this decision. No broader instruction amendment proposed.
- Resolution history: 2026-11-11 opened against D1/r1 and proposed C002/r1. This is a missing schema decision, not an observed implementation failure.

## 02WR-P02-D1-R1/F3 — Make AC5 distinguish new capture safety from pre-existing revision retention

- Classification: actionable defect; severity P2; verification. Status: OPEN.
- Decision evidence: AC5 (TASK line41) plans a competing production agent deletion/admission assertion that a retained root blocks deletion. AC3 only plans sequential reassignment/new revision/replay (line39).
- Actual source: init_schema.sql:12298-12314 makes every published agent revision retain its agent through a deferred FK; agent.rs:504-524 explicitly reports this condition. A valid role agent necessarily has a published revision for admission. Its deletion is therefore already refused without any run or role-binding row, so the planned assertion can pass even when the new role capture does not synchronize or freeze correctly. A generic error assertion could also hide F1's lock timeout/deadlock.
- Required correction: preserve the original competing-delete requirement but state its stronger-existing-guard limitation and assert the expected refusal class. Add a competing production change capable of committing (role reassignment and/or active revision change) whose assertions distinguish a coherent captured holder/revision from an interleaved or re-resolved one; retain the old-run/replay checks. Include deterministic overlap/barriers for the new capture boundary and the lock-order cases in F1. Do not weaken the existing revision-retention guard to manufacture a delete success.
- Instruction lesson: verification-contracts.md already requires discriminating concurrency cases and decisive assertions through the production branch. Current planned AC5 overstates which mechanism it proves. No general instruction amendment proposed.
- Resolution history: 2026-11-11 opened against D1/r1. No p02 tests have been executed.
