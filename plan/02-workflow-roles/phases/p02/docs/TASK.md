## Architecture D1 / revision1 (proposed)

1. Pure `resolve_role(chain, role, need)` in application/workflow/roles.rs. Ordered owning-department→ancestor facts, bounded depth8; select the first department holding the role, stop there on wrong kind/ambiguity rather than falling through. Agent need requires exactly one agent holder. People need requires all holders be people, deduplicated and bounded by the existing MAX_REVIEWERS after resolution. Typed NoHolder/WrongKind/Ambiguous/DepthBound/TooMany refusals; no I/O or arbitrary holder selection. Only the current two fixed roles, no custom keys. People resolver is tested now; published human role inputs remain p03.
2. Resolve role requirements during the existing admission dependency-closure walk under the existing company serialization and channel association locks. Load a bounded department/holder fact set once per root capture, with tenant scope and the existing depth8 and reviewer/selection/deadline bounds. Include role requirements discovered in every pinned child or agent-granted workflow reached by the closure, not just the root. Add resolved agents as ordinary Agent nodes to that same dependency walker, preserving its cycle, 256-selection, five-second and live resource/capability/run-as checks. Capture the exact current published revision using the existing agent manifest revision/authority path and principal/agent shared-key locks; no new publication snapshot or parallel authority implementation. No role table dereference during execution. Replays return the prior root's frozen selection.
3. `workflow_run_role_bindings` stores company_id, root run_id, version_id, step, role, department_id, principal_id, manifest_id, optional agent_id/agent_revision_id, resolution_revision (0 at admission), created_at. Include version_id because nested versions may reuse a step name. One row per resolved principal. Composite FKs to the root's run/manifest ownership, the captured manifest's workflow version and exact agent revision, company-scoped departments/principals/revisions. Agent fields are both present or both absent; insert guard verifies agent/person kind and the captured principal-agent identity. A partial uniqueness constraint permits only one agent per requirement/resolution; multiple people remain possible. Run/manifest creation and role rows commit atomically, with all resolution/capture success before inserting the run. Updates/deletes refused while the root exists; cascading parent-run/company teardown allowed under the existing immutable-fact pattern. Deleting a department retained by a role snapshot is a history conflict, not silent nulling/cascade. No backfill/shim.
4. Runtime selection is centralized: pinned inputs retain exact AgentReference/use validation; role inputs must match the compiled requirement (step/role/mode), then select resolution0 for that version/step through the actual run→root manifest ownership and frozen role rows. Verify the role revision is the manifest's revision and use existing selected_on/live authority logic. Update execution selection, knowledge/memory checkpoint selection, history origin consumers, PublishedBundle::prepare_step_inputs and run inspection. Sample simulation has no real admission/department context: it must refuse a role-dependent model step with a precise role/department-context message rather than use a live fallback or arbitrary agent. UI preview/grouping comes in p03.
5. Role refusals are typed application errors with bounded step/role/cause fields and static public codes; HTTP returns400 naming the step/role and no principal list. Message admission classifies them as definite refusals, records under its existing fenced per-binding intent outcome, and never creates a run. Preserve the existing64-byte reason-code bound; store any structured role detail in a separate bounded/versioned optional field, not an enlarged free-text reason. Carry the same typed detail through scheduled occurrence refusal and manual API error surfaces so a required consumer does not silently degrade into transient retries or generic500. Existing non-role refusal behavior and lease/idempotency protocols remain unchanged. Schema/port/reader changes will be cohesive; no silently-successful defaults.
6. Show captured principal and department with a via-role marker in run inspection and board results, including pre-execution captures. Read frozen IDs/revision, not today's role holder; ordinary display labels may follow existing metadata conventions. Extend agent filters to include actual role-selected agents without changing procedure Used-by's pinned-reference meaning. Apply existing tenant/access/payload-projection rules and bounded list/truncation conventions. Do not add speculative performance indexes or change pagination; verify the affected query contract and existing query-plan gate if its SQL changes.
7. Future p04 follow-role support may append a later resolution_revision for human decisions; agent execution always reads0. Human decisions use their current reviewer rows after parking, so an empty replacement can remain an empty reviewer set with a typed decision event/escalation rather than resurrecting admission holders. This schema does not implement p04 behavior or pre-approve its eventual architecture. All applicable available escalation triggers remain required; only channel.call denied-child is user-deferred.

Failure/recovery invariants: no run/snapshot/job/partial role rows on refusal; definite intent refusal is fenced/idempotent and privacy bounded; a role reassignment after admission cannot change an agent or revision; concurrent delete either loses to retained references or admission refuses with no orphan; actor tools/skills/connections/knowledge remain checked with the binding run_as; shared resources, worker limits, waits, lease/stack budgets unchanged.
