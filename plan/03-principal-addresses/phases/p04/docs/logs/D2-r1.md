# 03PA-P04 D2/r1 — Deliver pending MCP cancellation outside a stopped SDK queue

No backward compatibility. No database, public API, timeout increase, new provider or dependency.
This corrects an exposed lifecycle dependency of the integrated native MCP path; it does not change
source authority, effect permission or D1/r5 account ownership. Ordinary and native MCP consumers
retain the same existing cancellation/cleanup contract.

## Evidence

The required full suite and exact isolated network-denied run both fail
mcp_dropped_call_sends_protocol_cancellation_and_joins_cleanup: completed3of4 exchanges, missing
notifications/cancelled. Exact diagnostic logs/orca-mcp-cancel-exact1.txt (2.45s). Adapter files and
scripted peer equal current main; this is an exposed dependency defect rather than a regression in
the prefix code. It is within FC2's native effect/lease-loss cancellation interface, not a reason to
edit unrelated service sources. Existing workflow MCP cancellation tests require this notification.

Session.call stores the real SDK RequestHandle id. rmcp1.8.0 send_request_with_option reserves it
before enqueueing the request. Session.close calls cancel_pending, but client.notify_cancelled only
queues a notification: it does not await the HTTP send. Session.close immediately cancels the same
Control.stop token that drives the SDK service/transport. HttpMcpClient.shutdown can cancel that
parent first as well. Thus the queued cleanup notification can be discarded before HTTP dispatch,
even though BoundedHttp explicitly exempts this cleanup notification from live authority checks.
The final joined SDK worker proves no work remains; it does not prove the cancellation was sent.

## Decision

1. Keep Session.pending_call and its single-owner Mutex::take semantics. Do not infer request IDs,
   track arbitrary new messages, retry effects or retain a detached cleanup task. A completed call
   still clears pending_call; unsuccessful/abandoned calls retain it for bounded cleanup.
2. Send that fixed notifications/cancelled message through the existing http::Cleanup client and
   shared BoundedHttp::request builder, instead of the SDK notification queue that is about to stop.
   Use the real saved RequestId, current endpoint, credential and last protocol headers. Only this
   protocol cleanup message bypasses live generation/source authority; initialize/list/call retain
   Control::check/run. No caller-controlled method, endpoint or parameters are added.
3. Preserve the existing3second cancellation attempt bound and one best-effort attempt. Await/drop
   its actual reqwest future before continuing SDK shutdown. No background spawn, new retry,
   duplicate cancellation or increased bound. Keep cancellation before the ordinary Session.close
   stop/SDK close/lifetime join/DELETE sequence. Adapter-wide shutdown may already have stopped SDK,
   but cannot prevent the independent bounded HTTP cleanup request from being attempted.
4. Cleanup currently remembers headers only with a stateful session. Remember the last legitimate
   protocol headers for stateless sessions too by making SessionIdentity.id optional and capturing
   that metadata on outbound SDK messages. DELETE still runs only with a real session id; an already
   successfully deleted session clears its metadata, and needs no further cancellation. No fake
   session id, default protocol version or discarded authorization header is permitted. Cleanup
   traffic uses only metadata already owned by this one established connection.
5. Prefer the installed rmcp model's typed notification construction for the direct JSON-RPC body.
   Wire encoding stays within adapters/mcp. Cleanup failures retain the existing best-effort policy;
   a missing notification never authorizes retrying an uncertain business effect.

## Invariants and failure modes

Normal completed calls send no cancellation. A dropped/timed-out pending call attempts exactly one
fixed cleanup notification. A stopped SDK cannot swallow that independent attempt. Preparation
canceled before admission still sends no credential/request. Stateful cancellation preserves the
real session and protocol header metadata and precedes normal DELETE; stateless cleanup does not
invent a DELETE. All workers and returned HTTP/SSE bodies remain owned/joined by existing lifetime
and close machinery. Pending ID is consumed only for this bounded cleanup attempt, never reused.
An HTTP rejection/timeout remains an unknown remote-effect outcome, never a NotApplied proof.
