# 03PA-P04 D2/r4 — Serialize SDK admission and request-ID publication with cleanup

No backward compatibility. No schema, public API, dependency, credential policy or raised timeout.
Supersedes only D2/r3's incomplete registration boundary; retain all other D2/r3 decisions/proof.

## Evidence and invariant

Independent B1-R4/F1 identifies SDK Peer.send_request_with_option enqueuing the request before
Session.call publishes RequestHandle.id (rmcp1.8.0 service.rs616–680; local mod.rs204–213).
The service/HTTP worker can consume that queue on another runtime thread while Session's poll is
preempted. SDK delete_session can then win cleanup.gate, observe no pending ID, DELETE and clear
metadata. Later publication cannot recover the missing cancellation. Existing tests did not hold
this exact interval. The single cleanup owner must cover publication, not only its consumers.

## Decision

1. Reuse the existing per-connection Cleanup.gate. Session.call acquires it before invoking
   send_cancellable_request and holds it through publishing the returned real RequestHandle.id
   in the existing shared pending_call mutex. Release it before awaiting the business response.
   No guessed IDs, transport interception, second pending-ID copy, new actor or protocol is added.
2. Under that gate, reject an already stopped/closed session before enqueue (Session.stop and
   RunningService.is_closed/is_transport_closed). Existing worker cancellation still owns the
   operation; all real HTTP requests retain Control.check/run after every prior wait. An aborted
   gate waiter enqueues nothing. No gate is held during response wait, so cleanup can cancel an
   outstanding operation and complete its ordinary bounded teardown.
3. Current PeerRequestOptions::no_options has no progress-watcher await. SDK Sender.send is
   cancellation-safe while pending; after successful enqueue it constructs/returns the handle
   without another suspension (service.rs640–681), and local publication is synchronous. Thus
   future cancellation cannot introduce an after-enqueue/before-publication suspension. OS-thread
   preemption is protected by the gate. Keep that ownership visible in the code comment; do not
   insert a production await in the successful handoff interval.
4. Preserve the fixed direct notification, shared one-take pending owner, real session/negotiated
   header/credential metadata, cancellation-before-DELETE, known-RPC completion clearing and
   unknown transport outcomes without effect retry. Existing3second cancellation/5second cleanup/
   35second SDK-close bounds remain. No new retry or detached task.

## Failure and deadlock analysis

The gate covers enqueue/publication only, not await_response. Queue admission is one request from
this serialized ProxySession; the SDK receiver remains independently driven. If shutdown closes a
blocked queue, its send returns an error and releases the gate; if worker cancellation drops the
pending call, Tokio Sender.send has not sent it. Existing worker shutdown/reply.closed selection
can drop a pending gate acquisition or queue send. An already-terminal SDK fails the guarded
precheck or enqueue. SDK delete_session may wait for publication, but never for business response.
All cleanup waiting/HTTP attempts retain their existing caller-owned bounds. A possible effect
remains unknown; absence or failure of cleanup never authorizes a retry.

## Required discriminating proof

Keep all existing3new cleanup cases and all original assertions. Add one per-connection cfg(test)
probe, absent from production, to pause the actual Session.call poll synchronously after the real
SDK handle returns but before pending publication. It must use bounded synchronous coordination,
not an async await that invents a cancellation point. Configure it only for the dedicated test and
observe actual SDK delete_session entry immediately before its existing gate acquisition. A real
multi-thread loopback stateful session must observe tools/call and the real id, start competing
caller abandonment and adapter shutdown, reach SDK deletion while publication is paused, and then
release the pause. Assert exactly one cancellation for that original id, original credential/
protocol/session headers, cancellation before exactly one normal DELETE, no second effect, all
workers joined. Always release the pause before reporting an assertion to avoid a stranded thread.
The test must fail the old unlocked publication ordering; a mutex-only assertion is insufficient.
Probe lifetime/teardown stays inside this test/connection; no global hook or provider surface.

Run focused adapter/current API/native/workflow cancellation/recovery families after the fix,
source-module reachability for any new Rust helper, SQLx metadata if SQL changes, then restart
required final repository/CI verification and independent whole-integration recheck. Retain failed
full gate2's completed static/offline/Clippy/migrations/SQLx proof without calling it full green.
