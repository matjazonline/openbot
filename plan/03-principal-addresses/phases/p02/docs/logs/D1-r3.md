# 03PA-P02 D1/r3 — Direct threads and bindings

Architecture proposal, 2026-11-14. Original requirements are plan03 README decisions
1–7, phase02 batches 02A/02B, C006/r1's moved 01B work, and coordination revision12.
No backward compatibility: change the init schema and migrate fresh disposable databases.
This gate approves decisions and verification, not implementation or executed checks.

## 1. One target, shared ingress and persistence

Reuse `AddressTarget::{Desk(Uuid), Principal(PrincipalId)}` from the domain address
module, deriving serialization, hashing and ordering there. `Thread` carries this
target, not a desk UUID pretending to be a principal. Ingress candidates, commit
associations, admission intents, transport bindings and reply routes carry the same
typed target. `ThreadTarget::{Existing, Create}` remains the separate resolution
decision. Target comparisons always include the discriminator and tenant.

Generalize the existing transport-binding model to address targets. Its existing
email endpoint mechanism serves direct addresses too; no mailbox, channel, DNS,
credential or synthetic desk is created. SQL `channel_bindings` gains nullable
`principal_id` beside nullable `channel_id` and an exactly-one check. Its application
entity/write/read APIs use `target: AddressTarget`; retain existing table/type names
where a rename adds no behavior. Non-email installed integrations remain desk-only
and are refused for principal targets by constraints and boundary validation.
There is one canonical email binding per principal, provisioned transactionally with
its address. Person creation/promotion provisions it now; C006 keeps agent creation,
slug equality and automatic-desk replacement in p03. p02's agent fixture explicitly
registers an address and email binding at a slug no desk holds. Rename updates the
canonical endpoint in the same transaction, retaining its stable binding UUID.

Extend existing thread lookup/creation/list ports to accept an `AddressTarget`,
rather than adding a parallel direct-thread store or inbound commit. Namespace
resolution loads the addressed principal and delegates policy to that entity.
Every recipient produces at most one association and intent per typed target,
including mixed desk/principal mail, using the existing whole-message preflight
and transaction. A failed recipient leaves no partial thread/message/intent/delivery.
Principal context suffixes remain refused. A policy-denied stranger gets exactly
the unknown-address rejection; suggestions and directories exclude private targets.

## 2. Thread identity, participants and concurrency

The user selected **like desk mail**. Apply the existing explicit-thread,
reply-message, external conversation, nearest-ancestor and Thread-Index resolution
order, scoped by the typed target/binding. An unmatched message opens a new thread;
there is no unique-per-principal or unique-per-sender thread key, and subject alone
does not merge unrelated conversations. Preserve the desk path's existing subject
handling and quoted-history stripping.

Reuse the inbound commit's sorted provider-key advisory locks, re-read conversation
mapping under those locks, and preserve canonical hash deduplication. Two competing
deliveries sharing a provider conversation key converge on one direct thread;
two unrelated roots to the same principal may produce two. Redelivery creates no
extra thread, canonical message, intent or delivery. Existing-thread locks remain
sorted by UUID; every target/tenant must match before writing.

Direct thread membership contains the target principal and authenticated writer;
it does not inherit desk participant lists or `add_3rd_party`. Further legitimate
writers can be recorded for attribution. Participant membership never widens direct
viewer/access policy or bypasses an agent's revoked public flag. Existing thread
injection and content-level checks apply to direct targets too.

## 3. SQL ownership and membership pins

Add nullable principal target columns beside nullable channel columns across thread
and workflow associations. `thread_principals` already uses `principal_id` for a
participant, so its target column is `target_principal_id`; do not confuse the two.
Exactly one target is required on threads, their messages/principals, external
threads/messages and reply contexts/settings. Workflow bindings/runs/jobs may have
neither for company scope, but never both; a thread requires a target.

Keep the existing composite desk foreign keys and add tenant-scoped principal
counterparts and corresponding unique keys. Nullable-FK bypass is closed by the
shape checks: every non-company association has exactly one fully populated FK.
The thread-message membership pin is `(company, principal, thread, message)` on
direct targets, matching the desk pin's meaning. Thread-principal primary key
becomes `(company, thread, participant, role)`; the target is enforced by its
composite thread FK, rather than a nullable primary-key field.

Apply this consistently to the inventory's dependent tables: internal notes,
workflow message intents/destinations/history members, workflow bindings/runs,
background tasks, agent history sessions/conversations, admission refusals,
reply settings/contexts, external threads/messages, notifications, delivery
attribution and escalation receipts. Distinguish a recipient/responder principal
from the thread's target principal wherever both exist. Preserve all immutable
run/context/proposal, canonical message, tenant and membership guards.
Retained direct history prevents deleting its principal; deleting an unused
principal cascades only its unused address/binding. No historical IDs gain authority.

Update target-sensitive SQL functions from the inventory: notification visibility
and rechecks; job/run/schedule association guards; agent-history scope and snapshot
guards; reply capture/context/run/proposal/publication guards; follow eligibility;
escalation source/handling-root association, authority and refusal context.
Desk schedules stay desk/company scoped: principal bindings are explicitly
incompatible, never misclassified as company-wide. Company-wide is generated from
both target columns being NULL. NOTIFY wakeups carry target kind/id; they are hints,
and readers reload current authorized state. Preserve existing lock budgets/fences.

## 4. Access, public settings and revision fencing

`Principal::direct_access` and `direct_viewer_access` own decision5. A person's
direct threads admit/read/write only that person and the company owner. An agent
admits team writers; outsiders only when `open_to_public`. The team may read agent
threads; public never grants reading. New routing to external/system targets is refused. Retained personal targets
are readable by the owner under the lifecycle contract in section8 below. Department membership/roles never widen direct access.
SQL notification/follow/escalation visibility mirrors this with a database-backed
equivalence matrix. Content-level and verified-identity obligations are inherited.

Add `principals.open_to_public NOT NULL DEFAULT false` (agents only) and monotonic
`settings_revision`. A material slug, public flag or principal-kind/identity change
moves the revision; a no-op does not. Inbound commit locks the addressed principal
rows `FOR SHARE` in deterministic order before binding/thread/message writes, after the identity-key prefix in section9, then
rechecks revision and current kind/policy. Stale/deleted/retired targets return
`Superseded` with the whole transaction rolled back. Admission takes the same
current principal authority gate; the old intent is never redirected by a rename.

Address/public edits serialize on the principal row before changing the address or
binding. Raw address changes also bump the principal revision in a trigger; normal
writers take the principal lock first to avoid address/principal lock inversion.
Ingress does not lock address rows after locking principals. Person rename,
agent settings and membership retirement must preserve this ordering, the existing
account/company prefixes, and bounded failure handling. Keep desk advisory gates
and principal row gates distinct; acquire the whole ordered set before downstream
locks. Recheck all old p01 address/retirement races after extending these writers.

Carry the public flag through principal reads and company-agent create/update
JSON and settings form. Extend `AgentUseCases` construction with the existing
`SpamScanning` fact and reuse the public-ingress acknowledgement helper. The flag
defaults false and requires explicit `confirm_spam_disabled` when opening without
scanning. Library agents have no principal and cannot be opened. Preserve the
independent desk public control and clear members-only when choosing public.

## 5. Workflow bindings, roles, final replies and notifications

Extend `RelatedAssociation` with principal scope and make its thread variant carry
an `AddressTarget`. Shared conversion/authorization helpers decode the target pair
fallibly; do not treat a NULL channel as company scope without checking principal.
Update all consumers from the association caller inventory, including management,
controls, actions, local agents, history, attention, decisions and escalation.
Bindings on non-agents are refused both in the application and SQL. Message-trigger
selection/caps serialize per typed target. Company bindings remain company-wide.

Principal role context uses the target agent's **distinct current departments**:
exactly one resolves; zero is missing; several are ambiguous. Activation refuses
missing/ambiguous context for a role-bearing version or policy. Admission captures
the same context under existing role/account/company locking and revalidates
current facts. Department/roster edits must not leave an active role binding with
ambiguous context: extend existing detachment validation/refresh mechanisms.
C004's real refusal producers remain fenced persistence capture; scripted samples
and authoring validation do not create escalation cases. Retain C002 audit bounds.

Generalize existing final-reply settings/context and route/publication machinery
to typed targets so agent direct bindings can answer without a desk. Selection,
immutable source/actor/contract, proposal integrity, current binding revision,
approval, publication ownership, history membership and delivery fencing retain
their existing proof. Reply sender is the direct address when the source thread
is direct, and the desk address when desk-bound. All private application RFC
Message-IDs still come from `TransportRenderer::application_message_key` (C005).
Direct deliveries carry principal attribution and the real principal email binding,
with the same audience/egress checks. No null/synthetic source binding fallback.

Notifications carry the source thread target and recheck current direct visibility
at projection, listing and open. Links use authorized direct routes. A person's
direct traffic cannot leak through attention, agent history, diagnostics, assets,
internal notes, streams, escalation or workflow sibling views. Add a bounded
"Direct" list for each readable principal and use existing message panes and
target-aware compose/reply paths. Subscribe before reading on live lists/panes;
preserve current read-race and cursor rules. No new live protocol is required. Section10 specifies the new incoming-personal-mail
notification source; target attribution alone is not its producer.

## 6. Relay and trace; p03 boundary

Replace the UUID-only `trace_channels` with bounded typed `trace_targets`, including
SQL intent storage, application carriers, integrity documents and email header
parse/render. Email encodes each target with its discriminator; reject malformed
or oversized entries. The hop budget remains five, one target per hop. Revisit the
actual parser/renderer callers, not only field-name occurrences. A principal loop
is caught without conflating a desk with a principal holding the same UUID.

p02 permits existing authorized desk-origin relays to a principal, with the source
sender check **before** delivery. It does not add the p03 right to send as a running
agent's own principal. Agent desk removal/address registration and C001/C003's
authenticated agent-notice principal adapter switch remain together in p03.
Their existing origin suppression, exact targeted binding/revision, zero-or-one
root, account prelocks and rollback/backoff protocols remain intact during p02.
Generalized target types must not silently weaken or break that live desk adapter.

## 8. Personal ownership survives retirement (R1/F1 correction)

A person principal has a lifetime historical account UUID,
`historical_person_user_id`, installed when it first becomes a person. A SQL guard
sets it from `user_id` and prohibits changing/clearing it afterwards; when the row
is a live person, `user_id` must equal that snapshot. Enforce at most one lifetime
person principal per `(company_id,historical_person_user_id)`. The snapshot is a
historical UUID, not a live FK or authorization grant; deleting an account must
remain possible. Fresh anonymous/external/agent/system rows have no such snapshot
unless an external row legitimately first becomes a person. An archived person
cannot become a different account or an agent/system principal.

Membership removal/account deletion preserves this UUID while demoting the person
to external and clearing live `user_id`, exactly as existing retirement does. It
removes the address, bumps routing revision and marks its principal email binding
`orphaned` with a typed `principal_retired` reason/audit in the same transaction.
Orphaned bindings do not claim a live endpoint, cannot receive/send, and preserve
old correlation/history rows. There is at most one lifetime canonical email
binding per principal. Normal rename/reactivation reuses its UUID rather than
creating a second binding or redirecting old mappings. A never-used principal can
still be physically deleted; direct history prevents deleting its target.

`direct_viewer_access` permits the live company owner to read an archived personal
target, while denying all former members and other teammates. Its write/access
method refuses delivery, compose or reply through a retired target with no active
address; history remains intact. Owner access still enforces canonical content
levels. Directory/sidebar history listings may name the archived target for its
owner without advertising a deliverable address. SQL mirrors this branch.

On rejoin, production person creation first finds this account's lifetime principal
in that company. It restores that same principal only after proving the same
authenticated account UUID and current membership; the historical snapshot alone
never authorizes a read. This restores the same account's history. If a different
account verifies/adopts the former external email identity, allocate/reuse that
new account's own principal and move the transport identity via the existing
account-identity helper; do not promote the archived person's principal. Its
direct target/thread IDs and old source binding remain pinned to the archive.
Identity adoption may continue existing attribution/grant behavior but never
rewrites a direct **target** or gives access through participant membership.
A raw mismatched re-promotion is rejected by the SQL guard, not accepted based on
application intent. Deleting the old account does not allow UUID/slug/email reuse
to transfer the archive. A reactivated address uses the current namespace allocator
and cannot displace a slug claimed meanwhile. Old withdrawn notifications do not
reactivate or email merely because the same account rejoins.

Decisive B1 proof: real removal leaves owner-readable content but no former-member
read/write/notification; account deletion followed by another account adopting
the same email keeps principal/thread targets distinct and old content private;
same-account rejoin restores its own target only; a retired endpoint is immediately
reusable at a new target without old reply-chain transfer; a raw mismatched
promotion is rejected. Also run p01 removal/promotion/rename races.

## 9. Identity keys precede principal gates (R1/F2 correction)

The reused ingress commit resolves identities in thread-principal insertion and
canonical author/participant writes. It must not first hold target-principal SHARE
and later acquire a sender identity key. Add one bounded prelock pass for the
**entire** set of qualified identities those operations will observe: envelope
author, canonical participants, and every identity-bearing thread-principal intent.
Known target principal IDs are written as such, not synthesized into external
identity observations. The set is derived from the same message-write/association
values later consumed, deduplicated and sorted by company, transport, namespace,
subject. Existing per-helper acquisition is reentrant inside the transaction and
therefore introduces no later key. Do not prelock only the author or one target.

Direct inbound commit order: existing ordered desk advisory gates (if any), all
identity advisory keys, all addressed principal SHARE rows in UUID order, revision
and current access checks, binding/provider-key locks, sorted existing-thread
locks, then thread principals/canonical message/mappings/intents/outbox/events.
Use existing request bounds and a transaction-local statement/lock timeout; any
failure rolls the whole commit back with the existing retryable/superseded result.
A deadlock abort is not accepted as the normal contention outcome.

Account rekey keeps its existing account → sorted companies → all old/new identity
keys per company → principal/identity row locks → dependent refresh order. No new
principal lock is inserted ahead of its identity keys. Person creation/promotion
keeps its account/company caller prefix, then identity key, then sorted principal
rows for the external holder and lifetime personal target, then address/binding.
The lifetime-principal lookup is initially nonlocking; acquire the whole discovered
principal set sorted and revalidate under the identity key before promotion.
Settings/address writers that never observe new identities may lock their principal
first but must not call an identity-observation/rekey helper afterwards. If a
combined writer does both, it uses the identity prefix first. Raw SQL mutations
retain atomic guards and may abort on invalid competing mutation; production
paths must use the explicit order and both contenders must complete normally.
Preserve existing account/company prefixes and C003's distinct NOWAIT protocol;
this rule does not add a blocking principal lock to its private-notice path.

Decisive B1 proof uses real confirmed email-change and real direct self-mail
transactions with barriers in both orders. Assert bounded completion without a deadlock or lock-timeout victim. If mail
obtains the identity-key prefix first, it commits once before rekey completes;
assert the existing old-identity retirement/attribution behavior after rekey. If
rekey wins first, a draft preflighted under the old self identity must return the
explicit Superseded/current-policy refusal with **no** thread/message/intent/event
commit; rerouting that obsolete sender must remain refused. The rekey itself must
commit successfully in both orders. Do not force successful stale mail admission
to obtain a green contention test. A newly preflighted message from the current
verified identity is separately admitted once. Include person-promotion
racing direct mail and address rename/removal in both orders. Trace any newly
introduced identity helper before extending the prelock set.

## 10. Incoming-personal-mail notifications (R1/F3 correction)

Use the existing durable notification event/worker/projection path with one new
source/action pair: `direct_message` / `direct_message_received`. The source ID is
the target-scoped thread-message association UUID, generation1. Successful direct
ingress to a **person** enqueues that event in the same transaction that creates
the association, with the canonical author's principal for existing self-send
presentation rules. The event has a unique source/action/generation identity, so
redelivery creates no second event or notification. Mixed recipients each get
only their own target's event; agent inboxes do not create personal notifications.

The worker rehydrates the real association/thread/message and live person target,
checks current membership, exact lifetime account ownership, direct visibility and
content level, then projects a notification **only to that person**. The owner can
read its thread but receives no duplicate personal notification. Add a direct
thread `NotificationTarget` and authorized direct href; the projection's account/
company/source locking follows existing projection-lock and claim-generation rules.
Do not put message bodies, secrets or stale entity snapshots into event payloads.

This phase delivers an in-product notification, with no new email preference or
email delivery for this family (`email_preference=false`). Existing failure/decision
mail controls retain their meaning. Self-mail may retain the in-product notification
as the existing self-triggered rule does; it never emails. The notification stays
active with existing `read_at` presentation state after authorized opening. Source
deletion resolves it; membership/target/ownership/content authority loss withdraws
it. Projection/list/open each recheck current authority, and revoked projection
never exposes a direct label/href/body to a teammate or replacement email holder.
Old withdrawn sources remain withdrawn across rejoin; a new association creates a
new event. Opening the thread as owner does not mark another recipient's notice read.

Add positive real ingress → real notification worker → list → open coverage,
asserting the source association, exact target account, href and persisted
`read_at`. Pair it with concurrent/redelivery event uniqueness, self-send, mixed
recipients, sender/teammate refusal, member removal/account deletion before worker
and between projection/open, content-level refusal and replacement-email-holder
privacy. Keep the existing poisoned-batch/claim/lease notification tests.

### D1/r3 verification clarification (R2 residual on R1/F2)

This revision changes only the rekey-race oracle, not the lock protocol. Source
authority may be revoked while a mail preflight is waiting. Explicit stale-input
refusal is the correct ordinary outcome when rekey wins; the test must distinguish
that controlled result from a deadlock/timeout abort. AC11 and section9 now state
the two-order outcomes separately. Historical r1/r2 decisions remain immutable.
