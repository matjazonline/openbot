## Durable source authority across removal and rejoin

Add nullable direct_membership_id UUID to notification_events. It is mandatory
only for source_kind=direct_message (the new source/action pair) and NULL for the
other source families. Its value captures the exact company_members.id held by
the addressed live person when this association is inserted. It is a historical
source identity, not a foreign key or live grant: membership deletion must not
delete history or require holding a dead membership row. The native event source
guard proves association tenant/target, a live person, exact lifetime account
ownership, and that membership belongs to that person at INSERT. The captured
membership UUID is immutable, including raw SQL UPDATE; event lease/status fields
retain their existing mutable protocol. Producer conflicts DO NOTHING and never
rewrite this fact. Do not use timestamps as membership epochs.

Projection rehydrates the exact association/thread/message, current principal,
current account and membership. Active requires person kind, historical account
UUID=current account, member.id=event.direct_membership_id, direct visibility and
current content-level permission for the canonical message. Missing source resolves;
revoked authority withdraws. A rejoin allocates a new membership row, so an old
pending/claimed/completed receipt can never become active again, even if no worker
ran during the absence. New mail has a new association/event pinned to the new
membership. Renames keep the same target/binding and do not transfer notification
ownership. Another account adopting the email has a different lifetime target and
membership and receives no old personal receipt.

## Reuse projection and read ownership

Retain projection_lock's account SHARE -> company NO KEY UPDATE -> source locks ->
event fence order. A direct source lock follows the existing company prefix, locks
the addressed principal SHARE then exact association/message SHARE, and repeats the
source authority read. The preview/current comparison and existing claim-generation
fence reject changed sources without sending or exposing stale content. Membership
retirement uses its existing account/company prefix before principal mutation;
do not add a principal-first account acquisition or identity observation here.
Concurrent retirement/projection/open must complete without deadlock/timeout victims.

Generalize notification inbox attribution to Option<AddressTarget>, including the
existing schema channel_id/principal_id pair, projection snapshots/recipients and
read rows. Reuse both existing desk and direct SQL policy functions through one
target-aware dispatcher. List and open additionally validate the direct source's
membership pin and message content stamp. List uses a bounded set query rather
than one projection/query per result. Direct href is the authorized current
/ui?company_id=...&principal_id=...&thread_id=... route. No body, secret or stale
principal/entity snapshot enters an event payload. The target person alone receives
the notification; the owner retains history access but gets no duplicate receipt.
Authorized opening persists read_at without resolving the active notification.
Existing failure/decision preferences, control/agent notice paths, poison-batch
backoff and lease ownership remain unchanged.

Retirement/list/open withdrawal uses the same current source-authority predicate;
withdrawn direct receipts are hidden from direct lists when their membership pin
no longer matches. Rejoining does not clear withdrawal/read state or create email.
Preserve immediate native withdrawal across membership/target/content-authority
loss and existing canonical source-deletion resolution behavior.

## Decisive verification

- Actual personal ingress -> actual worker claim/commit -> list -> authorized open:
  exact association source, one event/notification, exact recipient, correct typed
  href and persisted read_at; target person only, no outbound email, self-send kept.
- Mixed person/desk/agent recipients and competing redelivery: one canonical message,
  one association/event per personal target; no event for agent/desk or duplicate.
- Retirement before worker, between projection/open and during claimed work, plus
  same-account rejoin before worker and after projection: old event never reactivates;
  fresh current-member mail does. Include actual account deletion and replacement
  verified-email-holder isolation. Neither owner nor sender/teammate gets the notice.
- Content-level loss at projection/list/open hides body/label/href; source deletion
  resolves. Raw SQL cannot supply a different company's/target's membership pin or
  change an existing pin. Run direct Rust/SQL access equivalence and existing
  notification poison/claim/lease, reviewer and agent-notice regressions.
- Actual competing retirement versus projection/open in both lock orders must give
  ordinary bounded outcomes with no deadlock or lock-timeout victim, no stale active
  projection/email, and preserved claimant fences.

## D2/r2 — retain a withdrawn personal projection across membership retirement

The first runtime notification run produced15 PASS/2 FAIL of17 selected tests
(B2-notification-focused1.txt). The projected-personal-retirement test found the
notification row absent after actual remove_member. The schema's
notifications_recipient_member_fk(company_id,recipient_user_id) ON DELETE CASCADE
removes the projection when company_members is deleted, even though the new
withdrawal hooks had transitioned it. D2/r1 assumed source withdrawal could retain
the projection under the existing key. That assumption is false. The other test
failure is mixed-recipient ingress and remains independent/unresolved; do not
attribute it to this lifecycle key change or call the runtime source accepted.

Keep personal notifications as durable withdrawn projections (with existing
read_at) after membership removal, as the source lifecycle contract states. Preserve
other source families' existing member-cascade behavior without a second write path:

- notification_events.direct_membership_id remains the immutable historical source
  pin. No change to the accepted capture/current-membership comparison or queue.
- notifications.recipient_user_id references users(id) with ON DELETE CASCADE, so
  actual account deletion still removes the recipient's projections. Existing
  tenant-qualified recipient-principal FK and native direct source/recipient guard
  continue to prove company/account/source ownership.
- Replace the membership FK's child user key with a generated column
  member_recipient_user_id = CASE WHEN source_kind='direct_message' THEN NULL ELSE
  recipient_user_id END. The existing composite membership FK points to
  (company_id,member_recipient_user_id), retaining ON DELETE CASCADE for every
  existing family. The generated value has no caller-controlled state and is not
  another authority definition. It exempts only the personal retained projection
  from a live membership FK; current direct authority stays native + projection +
  list + open gates. The personal event's historical membership pin is never FK'd
  to a live member.
- Removal/content/target revocation withdraws the row synchronously. No worker may
  reactivate it across rejoin because the captured membership UUID differs; list
  and open continue to hide its label/href. Existing source deletion resolves it.
- Unused-principal physical deletion remains permitted after source history is
  removed. Where the existing recipient-principal FK clears a deleted principal,
  the immutable direct recipient guard must permit only that exact NULL clearing
  after the referenced principal is gone (as event actor FK clearing already does),
  never replacement or retargeting. The existing target FK may cascade the unused
  projection. Retained direct history still prevents target deletion.

This adds no compatibility path, backfill, optional setting or new worker. It is a
new reset schema definition. Same account/company/source/event lock order. Focused
proof must show personal row state/read_at survive removal and stay withdrawn on
rejoin; existing delivery/reviewer/escalation membership-cascade tests remain
unchanged; account deletion/replacement holder and native tampering are covered.
Original AC1–AC12 and all D2/r1 remaining runtime obligations still apply. Source
is frozen for this delta architecture review; no dependent retention-key edits yet.
