### Ownership and representation

Create domain agent capability identities (AgentId, AgentBindingId, AgentRevisionId, positive AgentDraftRevision) and an ordered typed AgentToolBinding { id, alias, source }. Sources are a closed trusted built-in enum, HTTP {connection, registered operation name}, MCP {connection, registered operation name, reviewed operation version, remote tool name}, and Workflow {registration name, exact workflow/version/params}. Alias and remote/registration names are distinct typed values. A source includes its exact target/pin; retaining a binding ID while changing any source fact is rejected. Duplicate aliases or IDs are rejected. Reserved message.*, provisioning names, and search_knowledge may only name their exact trusted built-in; external aliases cannot spoof built-ins. Provisioning grant addition remains restricted to trusted Builder creation.

Application agent module owns complete ResolvedAgentDefinition and ResolvedAgentTool, immutable revision content/hash, ModelSettings, SkillSnapshot and approved policy enums/struct (move actual shared definitions out of workflow publication, update imports). Workflow-specific snapshot/slot classification stays in workflow until its consumers migrate in phase03/04; it consumes agent-owned facts, not the reverse. No wrapper service or provider abstraction. Existing compiler/schema validator remains authoritative for tool schemas. Resolved tools include source/identity/alias, exact input/output schemas, action policy and approval_required; no endpoint secrets or credentials. Agent and skill texts stay <=16384; bindings <=32, skills <=16, tool operation <=65536; resolved definition bounded <=1MiB. Canonical ordered JSON serialization uses existing sorted JSON object semantics; order of tools/skills is meaningful, hash SHA256 over validated content, excludes revision ID/time/idempotency and all credentials.

Define DependencyManifest as typed immutable identity selections (one revision per agent, exact child workflow versions), bounded combined nodes <=256, depth <=32, serialized bytes <=4MiB and bounded lookup work before provider entry. Phase03 owns closure assembly, cycle detection, transactional capture and propagation. Queue work continues to carry existing run/execution identifiers only.

### Native schema and retention

Edit init schema only; recreate owned disposable databases. Add agents.draft_revision positive bigint. Replace agents.workflow_tools with agent-owned ordered typed bindings. AgentWrite uses optional tool_bindings on update; skill_ids remain ordered current ownership model. Normalized binding registry rows include company/agent/binding identity, alias, source discriminator and mutually exclusive typed target columns. Source checks and per-kind tenant-qualified FKs point to actual HTTP/MCP operations and connections and exact workflow version/registration. Unique company/agent/alias in draft assignment, immutable binding identity/source, bounded position 0..31; assignment table separates editable ordering from retained identity/source. Global library agents permit portable trusted built-ins only, with the existing explicit NULL-library ownership rule enforced natively; copying gives new company-owned binding IDs and never copies foreign connections.

Keep binding identity/source rows immutable once created, retain historical IDs when draft assignment is removed. To permit native target FKs and historical retention without defeating revocation, extend existing HTTP/MCP/workflow registration rows with explicit revoked state instead of physically deleting them. Existing primary registry identities remain their company-qualified keys; do not add another registry. Active lookups/counts filter revoked rows; register can replace/reactivate existing registry keys subject to existing optimistic checks. Revocation atomically tombstones associated live binding grants; recreating a registry key cannot restore those binding IDs. MCP reviewed version and workflow exact pin remain in frozen binding source; current live comparison must reject drift (phase02/04). Connection deletion keeps existing durable soft-retirement; replace its operation DELETE with revocation. Current credentials stay in their existing tables and secret ports.

Add immutable agent_revisions (company, agent, revision ID, source draft revision, bounded validated content, SHA256, creation time) and active selection keyed by company+agent, FK to that exact agent revision. Store immutable ordered revision-binding and revision-skill identity links with tenant-qualified FKs. Live binding/skill grants are separate rows from draft assignments, reference immutable identities, and allow only one-way revocation of an existing grant incarnation. Publishing removals revoke old grants; re-adding a revoked target/assignment requires a fresh binding/assignment incarnation to avoid ABA. Revisions do not read mutable skills during execution; skill snapshots retain their text and required aliases. Existing agent_skills remains draft ordering; live skill grant incarnation is independent. Phase02 implements publication/activation and immediate revoke commands; phase01 provides storage contracts and native constraints only.

Manifest storage: immutable dependency_manifests (company, manifest ID, root run reference), manifest_agent_revisions with one selected revision per company agent, manifest_workflow_versions with exact tenant-qualified workflow/version FKs, and run_dependency_manifests linking each root/descendant run to that manifest. Root-run/manifest reference is deferred to allow atomic admission; all foreign keys include company and exact owner (agent for revision; workflow for version). Retain referenced revisions and manifests; no per-queue copied entities. Phase01 has no production admission writer of manifests until phase03; native tests exercise storage.

All immutable-row mutation guards permit only whole-company cascade deletion, checked by absence of owning company; ordinary UPDATE/DELETE is rejected. Referenced agent/skill/registration deletion cannot erase history; phase02 adds deactivation/retirement behavior where needed. Existing company cleanup remains usable. Invalid cross-tenant/target/active-revision/run references fail in PostgreSQL independently of application checks.

### Locking, transitional consumers and phase boundaries

Agent draft writes lock owning agent FOR UPDATE and increment draft_revision once with the full model/instructions/bindings/skills write. Binding identity/source insert never mutates existing IDs. Serialized owner lock protects reorder and alias uniqueness. Unchanged sources may retain IDs; changing targets under an alias needs new ID. No publication/admission/effect protocol is introduced in phase01.

Switch all current name-grant storage reads/writes and fixtures to typed bindings in this phase; remove agents.workflow_tools and AgentWrite.workflow_tools. Existing workflow publication/runtime temporarily projects aliases from typed configuration because its embedded agent snapshots are replaced in phase03/04. This is one storage representation, not dual reads/writes or a compatibility decoder. Direct MCP alias dispatch and run binding authority move together in phase04; phase01 does not claim that final behavior. Old workflow UI grant editor may resolve a requested existing target through native registrations into typed bindings until moved to agent authoring in phase06; ambiguous/missing targets fail. Draft storage and future live grants remain separate; phases02/04 switch runtime to live grant incarnations before final release. No running deployment or staged rollout is involved.
