## AUTO-P01-G1-F1 — Manifest immutability blocks accepted run retention

- Classification: actionable architecture/correctness defect; high severity; acceptance blocking.
- Evidence: TASK.md:51 adds an immutable dependency manifest referencing its root run and immutable run-to-manifest links; TASK.md:53 permits immutable-row deletion only after company deletion. The accepted collector, `src/adapters/persistence/workflow/storage_retention.rs:4-77`, locks the still-existing company, captures the terminal tree older than 90 days, archives usage, and deletes its workflow runs (lines 46-50). `src/application/workflow/storage.rs:65-115` calls this through the existing sweeper; `src/adapters/persistence/workflow/storage_tests.rs:245-258` proves competing collectors remove a tree exactly once. AUTO-I005/r1 and the accepted knowledge pin line 26 explicitly preserve global 90-day retention and immutable usage history.
- Consequence: a retained manifest's root FK either prevents the run DELETE, or its cascade reaches a manifest/link DELETE rejected by the proposed guard because the company still exists. SET NULL would likewise require a forbidden mutation. Once phase03 writes manifests, ordinary terminal-tree retention cannot complete. Permanent manifest retention also retains run identity/history beyond the existing lifecycle.
- Required correction: define the manifest/link lifetime and guarded deletion behavior compatible with the existing retention transaction, while continuing to retain revisions referenced by surviving runs and preserve archived usage. State which native constraints/guards distinguish authorized tree cleanup from arbitrary history mutation. Do not defer this contradiction until phase03.
- Focused verification required after implementation: an actually admitted old terminal root plus descendant with a manifest is retired through the existing collector; manifest/link cleanup and surviving referenced revision behavior are asserted; competing collectors still commit once; an ineligible/live tree cannot be erased; whole-company cleanup remains valid. Add these to the phase01 storage verification plan.
- Instruction lesson: the retention contract is already explicit; the observed gap was failing to trace deletion consumers when introducing retained FKs. Candidate scoped guidance: every immutable FK-backed storage addition should name its normal retention owner and test that owner's deletion transaction.
- Resolution history: OPEN, 2026-11-05, initial G1 review. Origin is the gated design, not implementation.

- Resolution update, 2026-11-05: FIXED/CLOSED at architecture gate AUTO-P01-G1-R2-N1, decision revision2. The manifest is root-owned with tenant-qualified cascade lifetime; its associations prove the same root through existing budget membership, and direct mutation while that owner exists remains refused. Revision rows survive independently. The existing retire_on transaction remains the only collector, with no new run-deletion authority or changes to archived-usage provenance. Rechecked storage_retention.rs:4-77 and schema preserve_workflow_budget_identity (init schema:1130-1146), plus existing native job-provenance and archive guards. Required actual collector/root-child, competing-collector, ineligible-tree and direct-mutation cases are now explicit. This closes the design finding; implementation/test evidence remains outstanding.

State how initial transactional capture remains possible and how descendants may attach to the already frozen manifest without reopening its dependency membership. Preserve exact root/descendant manifest association when defining those attachment constraints.

Initial complete creation and legitimate descendant attachment must still succeed. Test canonical content versus normalized-link agreement and same-tenant wrong-tree attachment if the schema stores attachment rows independently.
- Instruction lesson: existing native-invariant requirements apply to collections as well as rows. Candidate scoped guidance: when describing an immutable object spread across tables, review INSERT after publication as well as UPDATE/DELETE.

Immutable bounded canonical parent content plus a native digest and deferred exact-set/ordered-link validation closes both missing-initial-member and late-INSERT expansion. Parent locking supplies serialization; all parent/member mutations schedule validation. Independent descendant attachment proves exact same-root ownership using tenant-qualified composite FKs and does not reopen dependency membership. Retained typed skill-assignment incarnations supply the revision-skill identity. Complete initial capture, later insertion refusal, malformed/missing projection and wrong-tree cases are explicit. This closes the design finding; concrete SQL validation/null handling, concurrency and cascade behavior must be verified at implementation review.

## AUTO-P01-G1-F4 — KEY SHARE does not fence operation activation against grant revocation

- Context: 2026-11-05, implement-astra-reviewed-2-2, p01 reopened architecture gate, note AUTO-P01-G1-R3-N1; independent B `/root/autonomous_p01_reviewer`, requested Astra/high, actual runtime metadata unavailable. - Classification: actionable architecture/concurrency/native-integrity defect; high severity; acceptance blocking for decision revision3. Origin is the proposed delta, not implemented grant-lifetime code.
- Evidence: revision3's “native operation activation invariant” requires a matching active company grant locked `FOR KEY SHARE`. Grant revocation updates the non-key `revoked_at` field, then an AFTER UPDATE trigger revokes visible operations. A KEY SHARE row lock is compatible with a non-key UPDATE. Existing `replace_grants` (`src/adapters/persistence/mcp.rs:130-144`) is the replacement boundary being changed; the existing operation FK (`migrations/20260817000000_init_schema.sql:10633-10637`) proves only key existence. Public company/connection locks do not enforce this promised invariant for native writes.
- Reproduction: [bounded competing-transaction probe](logs/AUTO-P01-G1-R3-key-share-probe.py), [actual PG18.6 result](logs/AUTO-P01-G1-R3-key-share-probe.log). The reduced schema uses the proposed BEFORE operation activation check/KEY SHARE, an AFTER grant status-revocation cascade, and the real FK shape. Transaction A inserts a new active operation under an active grant but remains uncommitted. Transaction B revokes that grant and commits; its operation UPDATE cannot see A's uncommitted row. A then commits. Both commits succeed, with final `grant revoked=true | operation active=true`. This is a deterministic two-session database proof of the proposed lock protocol, not a claim that the unpublished application implementation contains that trigger yet. The uniquely named throwaway probe database was removed; owned application/test DB schemas were untouched.
- Consequence: the claimed native active-operation/active-grant invariant does not hold under concurrent writes. Regranting later would expose an approval that escaped revocation; binding tombstone propagation cannot repair an operation missed by the revocation cascade. Sequential invalid-activation tests and public-writer races alone do not cover this native race.
- Required correction: specify a native serialization/commit-validation protocol that actually conflicts with permission status changes, preserves the existing lock order, and ensures activation versus revocation cannot commit this invalid state. Account for both a new operation row and reactivation of an existing revoked row; keep the no-ABA/fresh-reviewed-version guarantees. Author owns the concrete correction.
- Focused verification: retain a deterministic native competing activation-versus-revocation test with an inserted-but-uncommitted operation (and reactivation where relevant), in addition to the planned real McpPersistence grant removal/regrant cases. Demonstrate a valid serialized result or controlled refusal, never active operation plus revoked grant. Do not weaken source/current-grant or revocation assertions.
- Instruction lesson: lock mode must conflict with the specific mutation being fenced; native CHECK-equivalent concurrency promises require native competing writers, independent of application lock conventions. The actual PG probe supports this narrowly scoped guidance.
- Resolution history: OPEN, 2026-11-05. All other r3 delta concerns were reviewed without further actionable findings; prior F1/F2/F3 remain closed at design level.

- AUTO-P01-G1-F4 resolution update, 2026-11-05: **FIXED/CLOSED at architecture gate AUTO-P01-G1-R4-N1, decision revision4.** The native active-grant guard uses FOR SHARE through commit, which conflicts with the revoked_at update. Both winner orderings, new-row insertion and retained-row reactivation are explicitly included; timeout/deadlock aborts are whole-transaction failures, never successful authorization. The existing public company/connection order and fresh reviewed-version/no-resurrection rules remain.
