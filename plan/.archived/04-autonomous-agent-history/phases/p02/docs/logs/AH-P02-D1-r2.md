# AH-P02-D1 / r2 — durable input and atomic accepted-output ownership

Proposed cohesive architecture gate, original02A/B and shared invariants, accepted01 producer e62ebc6c/AH-C002r3. No phase02 implementation before independent PASS. Decisions below cover storage, authority/fencing, ordering allocation, failure/commit recovery and payload lifetime together; P03 turn serialization and P04 selection remain later dependent gates.

## One logical record and authoritative payloads

Add one `agent_history_exchanges` relation. Company + actual execution is unique; typed exchange ID equals that execution UUID. Retain conversation/actualAgentId/revision/manifest, actual source run/execution/job, positive conversation-local order, bounded model/output-contract provenance, state queued/active/completed/failed/cancelled, monotonic access_level, optional native checkpoint ID and accepted output, timestamps. No attempt/repair/tool/human continuation creates another row. Revision/level remain outside the conversation key.

Reuse the actual immutable `workflow_executions.frozen_inputs->'context'` as the single authoritative original logical input. Store its canonical DB digest in the exchange to enforce equivalence, and expose it through a bounded exchange read joined to that exact execution. It remains separate from provider prompt/selected history. JSON null/scalars/arrays remain actual values. Do not copy the expanded prompt or append checkpoint tool/repair traces as exchanges. Source input cannot be retargeted or rewritten; explicit changed input/provenance under one execution is a conflict.

Accepted output is a bounded exact JSON value on the exchange, written only with its native accepted final checkpoint. The final checkpoint keeps its own structured output; the same transaction owns both immutable representations, with native agreement checks, so there are no independent mutable writers. `output IS NOT NULL` exactly for completed distinguishes JSON null from absence. Failed/cancelled rows keep their original input and have no assistant output.

Tenant-qualified FKs bind actual conversation+agent, agent+revision, source run+execution, source job and native checkpoint/company/task; native creation/link guards prove exact source execution/job/agent/selected revision and checkpoint scope agreement. Initial provenance derives from the existing run-selected immutable manifest and PreparedAgent, never caller history JSON. Reuse existing identity/newtype/lifecycle/order contracts. Store only bounded model/schema identifiers and fields; contract currently caps schema65536bytes, so cap serialized provenance at262144bytes; original logical input/output retain existing1MiB bounds. No secrets, approval tokens, request headers or attachment expansion.

## Monotonic native enqueue order

Extend conversations with nonnegative `last_exchange_order` bigint, initially0. Existing tenant/scope/creator identity columns remain immutable. Under the normal current authority and own execution fence, obtain the conversation row lock, read the last position and assign exactly+1, checked for exhaustion. A native insert/order guard plus unique(company,conversation,position) prevent duplicate/gapped allocation from competing commands; an AFTER INSERT owner advances the counter to that inserted position in the same transaction. The conversation update guard permits only the exact counter advance backed by that new exchange, never a scope change or reset. Counter rollback follows failed enqueue; native conflict DO NOTHING cannot consume a position. Duplicate execution lookup precedes allocation and returns the same row only after exact source/input/provenance match. No timestamps as dedup/order keys.

Indexes: unique actual execution; unique conversation order; tenant/conversation/state/order pending path; tenant/conversation/access_level/recent completed order path. Phase04 must filter levels in SQL before payload loading/counts. Phase03 will add exclusive active position/acquisition/wait recovery; this phase does not claim conversation turn serialization merely from queue positions.

## Before-provider capture through the existing preparation owner

Extend the existing narrow AgentPreparation boundary with explicit LeasePolicy so its database work uses the established WriteBound, actual fence and bounded lost-ack reconciliation. Keep one preparation owner; do not add an independent history callback, optional trait default, provider abstraction or second runtime.

Refactor native preparation to load immutable selection/facts without local run locks after current account/company authority, check current association and actual frozen agent capability/model grants in global order, then lock/recheck the existing execution fence. Reuse/factor accepted01 identity resolution and trusted boundary derivation. Do not call agent authority late after `runtime::facts` has already locked the run. Build PreparedAgent from genuine frozen inputs and existing selected configuration, allocate/get the same conversation and enqueue the original input/order/provenance/stamp in this transaction. Read content_level under the existing locked run; enqueue stamps that value. A commit occurs before provider credential retrieval/checkpoint creation/provider admission.

Bind a typed server-produced exchange reference into eligible PreparedAgent's immutable checkpoint preparation document (reset-only version4); model-only preparations have no exchange reference and remain isolated. It is metadata outside workflow `with`/context and never chosen by model/business JSON. Checkpoint open/link and actual native provider-entry/current-selection checks require the matching exchange for actual agent.run; missing/foreign/changed proof refuses, never backfills at provider entry. Queue/selection/link checks do not trust a forged model-step label. Samples retain their sealed nonproduction paths, no production enqueue/read.

A crash after enqueue but before checkpoint leaves queued input with a stable actual execution. Retry/replacement performs the same current authority/fence checks, matches its durable record and reuses its order. A lost enqueue acknowledgement is resolved with a read-only actual execution/scope/input/provenance lookup under current authority/fence; no second writer in resolution. A failed credential lookup or interrupted worker cannot forget input, silently allocate a new exchange or grant provider entry.

## Native checkpoint link and accepted completion

Link queued exchange to the actual checkpoint at `open_workflow_checkpoint/open_on` in the existing owner transaction after immutable spec and native scope checks. It becomes active at that guarded checkpoint boundary for now; P03 will move eligibility/acquisition into its serial-turn protocol. Existing checkpoint ID remains stable across attempts and human/tool continuations; strict matching includes the immutable exchange reference. A foreign execution/checkpoint cannot attach. Model-only and non-agent native fixture owners are kept exhaustive, rather than enabled by a shared helper.

`WorkflowCheckpointUpdate::FinalOutput` maps through the existing `checkpoint_updates::update_on` transaction. Only after its current owner, revision/reservation, saved execution and token/approval checks and `RunCheckpoint.apply` accept the structured final output, persist the final checkpoint and complete the matching exchange in that same transaction, read source run content_level under its already stronger run lock and use GREATEST. Validate exact structured JSON/original contract provenance using the accepted checkpoint data; do not revalidate old output against a newer schema. Native deferred agreement checks require the eligible linked final checkpoint and completed exchange to commit together with identical accepted output/source/agent/contract; partial writes/rollback cannot leave either side accepted alone.

AlreadyApplied finals return the same exchange/output and never append. Ambiguous acknowledgement is reconciled by durable actual execution/checkpoint/final output under a current live owner on retry, not a callback or second provider request. Stale fences and changed payloads refuse. Preserve existing provider usage, remote uncertainty, received tool truth, and token-settlement/revision behavior; history adds no fresh permission or counter reset. Model-only steps/sample outputs do not gain exchanges.

## Exhaustive failure/cancellation and monotonic stamps

Native hooks at genuine workflow run terminal failure/cancellation and execution final_error routing terminalize only queued/active exchanges in the same existing transaction. They use GREATEST(exchange.access_level,run.content_level) and never touch a completed exchange or invent output. Cover native guard failure, deadline/exhaustion, operator/parent cancellation and routed failure. A persisted invalid-output terminal checkpoint can close its linked exchange through the same checkpoint transaction, with no rejected candidate as output.

Do not interpret every failed job/attempt as a terminal exchange: retries, token/human waits and action reconciliation can retain the same activation, including unknown provider/effect outcomes. Keep it recoverable until a genuine terminal owner or accepted output settles it. Existing global/parent/run/child authority and lock order remains; hooks do not inspect another run under a conversation lock or perform external work. P03 adds atomic turn-pointer release to these same completion/terminal transactions, not an independent terminalizer.

The run row already serializes knowledge observation and checkpoint completion. An observation contained in the accepted checkpoint must have raised run content before completion can acquire that row; the final exchange cannot be lower than that observed content. Failed/cancelled input audit also keeps the latest committed stamp. Stamps never decrease, schema rejects10, no level-based stream split.

## Explicit existing control retry — F1 correction

A failed workflow root is not always the end of its logical execution. Preserve existing `control_retry::retry_on` and the single native `workflow_control_retry_safe` predicate, including current command authorization, root-only/incomplete-execution restrictions, actual same job, original absolute deadline, prior attempt evidence, remaining retry/activation/action budgets and unsafe/exhausted exclusions. Do not broaden or duplicate that predicate, disable safe retries, or reset checkpoint/model/tool/repair/token/attempt accounting.

Ordinary exchange progression keeps the accepted01 terminal-state rules. Add a distinct explicit control-retry lifecycle operation for Failed→Queued, permitted only in the existing genuine native workflow Failed→Running transition for its exact old terminal execution and same retry-safe job. The native run transition/eligibility proof gates that one history change; presence of an old failed row or a caller's requested next state never authorizes resurrection. Current operator/association authority remains owned by the existing control command, and execution remains the actual original run actor. Publish this narrow lifecycle refinement to AH-C002 after gatePASS before dependent code. Completed and cancelled exchanges cannot take this edge.

Reopen the same exchange ID, original input/digest, selected agent/revision/model/contract, conversation and original order. Keep its checkpoint ID and immutable preparation when present, and preserve its stamp with GREATEST. Allocate no new row/order and do not advance the conversation counter. A reopened queued exchange may therefore already have its preserved checkpoint; queued does not imply checkpoint-null. Checkpoint opening under the replacement live fence reactivates it through the same guarded boundary, including committing that history transition when matching checkpoint open is AlreadyApplied. Current authority and stale fencing still apply before any provider work. Failure/attempt and control-retry audits remain in the existing linked workflow/attempt ledgers; reopened current state does not erase those failure records or fabricate an assistant answer.

If final agent output was already accepted before a workflow-level failure, its exchange stays Completed through control retry. The existing completed checkpoint replays that exact output, with no model call, additional row/order or history state reset. A true new task/rerun retains existing new-activation identity semantics. Cancellation, expired deadline, exhausted allowances, invalid/repeated-output failures and unsafe effects remain refused by their existing owners/predicate; this operation is not a generic recovery override.

Phase03 consequence: the reopened exchange re-enters pending work at its original immutable logical position and must obtain the same exclusive conversation-turn gate before resuming. It cannot execute alongside a newer active turn or displace it. Already completed newer exchanges remain completed and are never replayed retroactively. Pending selection can choose the oldest eligible pending position, including a reopened one; it must not assume every position below the greatest completed order is permanently settled or use that greatest order as a monotonic eligibility watermark. If an original preparation/checkpoint exists it is replayed, rather than selecting later history into an existing activation; phase04's live authorization/level checks still apply. Exclusive turn mechanics and wake/fairness bounds remain phase03's independent gate.

## Lifetime and existing retention

Use restrictive source/checkpoint FKs, without cascades deleting exchanges when a workflow source is pruned. Reusing the source input is valid only while these relationships preserve its lifetime. Extend existing workflow retention eligibility to skip source trees referenced by retained exchanges, including completed exchanges and child branches; direct premature source/checkpoint deletion fails natively. No first-run anchor for shared conversations. Company teardown may cascade the whole tenant intentionally, while active exchange direct deletion is refused under a live company.

Phase06's bounded history cleanup prunes eligible terminal exchanges/preparations first, respecting the explicit failed-but-resumable deadline/control-retry pins above; only then can the existing90day workflow owner prune unpinned source trees. Phase04 selected-history references will restrict deletion of required exchange payloads while queued/active preparation pins exist. Do not add a reciprocal permanent checkpoint FK that creates an unprunable deletion cycle: immutable prepared references can become explicitly expired after completed preparation retention, and views must report expiry rather than reconstructing missing history as exact. No unbounded new retention framework, no active source cascade, no source payload duplication to evade lifecycle checks. Detailed hard retained-byte/record admission backpressure is phase06's prescribed gate; no all-plan growth guarantee is claimed in02.
