**Classification.** Actionable acceptance-blocking defect; P2 / medium; concurrency and ownership correctness. Initial status: **OPEN**.

**Evidence and impact.** New `src/adapters/persistence/workflow/history_reader.rs:116–118` raises the content watermark and commits it. The enclosing `frozen_history` at `:54–124` uses only `claim.fence.scope`; it never validates the worker, generation, attempt/job ownership or lease expiry. `http_runtime.rs:12–32` checks current actor authority and locks the active run, while `:78–102` compares frozen step/input facts; neither validates the live claim. `knowledge.rs:139–158` deliberately provides only a scoped GREATEST update and requires its caller to hold ownership. Consequently a superseded or expired claim with unchanged frozen inputs can read history and durably raise the active run's content/revision. A later checkpoint fence rejection cannot undo this already committed mutation. This can cause low-egress refusal in the replacement execution despite the stale result never being committed. Run-row serialization alone does not establish lease ownership.

**Required correction/verification.** Establish the actual live claim and bounded lease/deadline validity for this newly mutating history transaction, retaining the established authority/run/execution/job lock order and ensuring no history or rise is committed when the fence fails. Add real old/new claimant and expiry coverage, including expiry during the bounded transaction: the stale call must return no history and leave content/revision unchanged; a current claimant must still consume history and raise atomically. [Numbered source evidence](logs/B-WB1-r1-finding-evidence.json). Existing knowledge tests passed but do not exercise this stale history claimant. B has not authored or executed a dedicated stale-fence reproduction; the missing validation is established by inspecting the complete new mutation path and its called helpers.

**Origin/instruction lesson.** G1 D3 explicitly says database/read/fence failure returns no history and commits no rise, while assuming existing fence checks remain. The formerly read-only path did not establish that fence, and adding a durable mutation makes the assumption consequential. Candidate guidance, scoped to persistence ownership: when a read path acquires a write, independently trace live ownership and commit-time validity rather than inheriting its previous read-only authorization assumptions. This also exposes an earlier gate coverage gap, linked in the G1 follow-up. No instruction files changed.
