# AUTO-P06-G1-D1 revision 1 — agent authoring and immutable execution visibility

Original requirements: plan/02-autonomous-agent/06-authoring-and-operations.md, all06A/B. This is one cohesive phase batch, including UI, JSON commands, application ports, persistence projections, documentation and focused proofs. No implementation edits precede this gate.

## Observed gaps and retained producers

The agent settings page exposes skills but no agent-local tool selection, publication, active status or history. Company form/JSON mutations call AgentUseCases.update_agent without an expected draft revision. The storage update already increments agents.draft_revision and the Agent entity already exposes it. The old workflow grant editor uses global names, although accepted bindings are now typed, agent-owned and immutable. Phase03's StepView contains selected revision identity but the HTML projection drops it and still describes capabilities as frozen by workflow publication. RunView lacks a complete bounded manifest projection.

Accepted producers remain authoritative: independent AgentPublications, immutable binding and skill-assignment identities, separated draft/live grants, root admission selection and native ownership, child attachment, live revocation/credentials, ephemeral sample isolation and knowledge visibility. In particular, an ordinary draft edit does NOT revoke a published grant; publication removing a binding or an explicit revoke does. No deactivated agent is automatically reactivated. Library-only selection remains a draft under accepted05/C007; composite runnable creation keeps atomic initial-only publication. No new schema, scheduler, executor, stored compatibility representation or deployment transition is proposed.

## D1.1 — one company draft command with an expected revision

Add a cohesive application-owned draft persistence port and a typed company-agent update request. AgentUseCases retains shared normalization, company-manager and model-selection validation, then calls this required port. All three company mutation transports (agent settings, older HTML agent form, JSON update) must supply the draft revision they saw. Create and operator library update keep their separate meanings; absence of an expected revision is not interpreted as permission to overwrite an existing company draft.

The Postgres command reuses the accepted account→company→agent authorization/row-lock order, checks company+agent and expected agents.draft_revision while the agent is locked, resolves requested capability assignments, and updates metadata, ordered skills and draft bindings in that same transaction. Extract the existing update-on-transaction core so ordinary internal/library writes and the guarded company command share one SQL/capability replacement implementation. Do not introduce a check-then-update gap, nested transaction, second draft counter, optional default authorization method or stale fallback. Actual competing writers using one expected revision yield one committed update and one conflict with no losing partial relationships. Publication racing draft save follows the same lock order and existing expected-draft/active CAS.

A stale HTML save preserves submitted metadata, tool choices and skill order with an actionable conflict; the active revision and grants remain unchanged. JSON refuses the stale command and returns the current revision through its normal conflict/read contract. A malformed/foreign target or skill rolls back the complete update. Required mocks implement the new port explicitly. Existing unguarded public workflow grant mutation routes/editor are retired as their consumers move to the agent page; no redirect, old-name decoder or second public write policy remains.

## D1.2 — typed selections, existing immutable incarnations, bounded discovery

Expose application-owned authoring read/catalog and assignment types. A tool choice names an explicit builtin or company HTTP connection+operation, MCP connection+reviewed operation/version+remote name, or registered workflow/version. Workflow registration parameters remain server-resolved configuration; choices carry the exact selected version/parameter digest rather than exposing credentials or letting a late repin silently change the choice. Selection never grants a connection, approves an operation or discovers a peer.

The UI displays the agent-visible alias next to its actual scoped connection/operation or workflow/version. It uses selects and bounded catalog pages rather than global names or workflow slots. HTTP/MCP discovery is narrowed to an explicitly selected company connection, with keyset operation pages (default50, maximum100, one extra row for continuation). Connection and workflow registration pages are similarly bounded and tenant-qualified. Required/current selections are loaded by their exact scoped identifiers so a page cutoff cannot silently drop a configured binding. Catalog projections contain safe identifiers, labels and reviewed metadata; no transport credential, raw authorization or current secret is hydrated into public catalog/general agent JSON. Read operations use bounded transactions/deadlines and no per-option database or network loop. Current MCP grant/discovery/operation policy is projected distinctly; final publication/dispatch continues to validate the actual current sources through accepted code.

Updates submit ordered tool assignments with an optional existing binding ID. The same owner/ID/alias/choice preserves its exact draft source, including an existing historical workflow pin. A new alias/target gets a fresh binding ID; an ID cannot be reassigned to another alias, source or owner. Fresh choices resolve exact server-side scoped sources and compare selected review/version/digest; stale selections refuse rather than select today's replacement. Foreign IDs are refused without leaking their ownership. Preserve alias bounds, provider encoding/collision checks, assignment bounds and native scope constraints.

Preserve the existing privileged builtin rule: a company agent may keep or drop its existing Builder provisioning bindings, and ordinary authoring cannot add such a capability, even by spoofing the Builder name/slug or alias. The ordinary add catalog offers message/knowledge builtins; a trusted Builder copy retains its actual existing bindings. New draft saves cannot revive a revoked incarnation. Message and approval authority remain supplied by actual workflow context, and classify/decide remain model-only.

The metadata/skills/tools editor saves one complete draft command. Existing skill ordering is visible and can be changed without typing UUIDs. Dynamic controls only serialize the bounded typed assignment/order fields; server validation remains authoritative. Partial catalog reads replace only their panel and cannot erase unsaved editor fields. Competing reads use the existing last-intent protocol; accepted writes queue/disable instead of being aborted. Use existing CSRF/session middleware, scoped ownership, escaped text/attribute/JSON contexts, accessible labels/focus/errors and visible pending/failure feedback. New interaction browser proof is registered in CI.

## D1.3 — shared preview, publication and immediate revocation

Add authenticated company-scoped HTML/JSON actions through the existing application AgentPublications port. Preview uses the exact saved draft and reports actionable missing required skill aliases or unavailable/revoked/review-changed targets. Publication carries expected draft, expected active revision and a stable request key. It retains current publication idempotency/replay and never updates the workflow version. Current typed failure conditions are shown distinctly; diagnostic improvements belong in the common application/resolver boundary, not divergent route string matching. Do not disclose secrets, prompts or arguments in tracing.

The editor clearly distinguishes saved draft, active revision and bounded immutable history (20 newest rows plus explicit continuation/truncation). Publication acts on the SAVED draft, in a separate status/action panel, so it neither ignores a purported unsaved publish nor destroys unsaved metadata on a refused action. A successful save refreshes its revision/status inputs; a stale or validation-refused action retains user input and active state. Explain that future admitted runs select the active revision, existing runs retain their revision, and current access removal can stop running work. Explicit revoke carries the exact owned binding or skill-assignment identity shown, with current manager authorization; it is not an alias mutation or implicit draft publication. Deactivation is separate and uses the existing expected active identity.

## D1.4 — workflow references and immutable run/step/tool provenance

Workflow authoring selects a same-company agent identity and can apply its canonical reference to a selected model step through the existing source decoder/retargeting helper. This modifies editor source without admitting/publishing an agent or adding MCP resource slots. Preserve unrelated unsaved source and existing draft conflicts. The capability panel is explicitly CURRENT information, not a promise about a future run; show active/draft/unavailable state and link to agent authoring. Agent directory options use bounded pages and retain directly referenced selections.

Extend existing RunViews and its step projection rather than creating another execution/read engine. A tenant-scoped bounded batch query reads the run's actual native manifest, immutable selected revision definitions and exact workflow dependency versions. Reuse immutable data for labels/model/alias/binding/target identity; never replace them with today's agent draft, active pointer, registration parameters or connection labels. Target summaries omit credentials, prompts and argument/parameter payloads. Step and saved tool-call views identify actual agent/revision/binding and workflow/child versions using existing durable origin and manifest relationships. A changed/revoked current target cannot rewrite historical provenance.

Bound agent/workflow dependency lists at50 plus one for explicit truncation; each stored definition retains its accepted size/shape guard, and root capture's aggregate bound still applies. Use bounded batch hydration, not one query per row. Revision history uses metadata-only rows, not whole canonical bodies. Preserve knowledge PayloadVisibility and current run/channel access: restricted RunView/StepView projections clear newly added capability payloads too. Old/current/foreign IDs, child lineage, malformed or missing immutable native data and unavailable targets have explicit refusal/projection behavior; never silently reconstruct from mutable rows.
