# CHS-P03-D1 / r1 — proposed whole-phase architecture

No backward compatibility: update the sole init schema, reset only adopted disposable databases. Baseline accepted p02 aa7cd3e8, HEAD769a23aa, B PASS CHS-P02-B1-R2. Current coordinationr5/C001r1/C002r1 and proposedC003r1. No p03 code edits yet.

## 1. Two durable facts, with one final decision

Use a bounded immutable terminal proposal per execution for the validated business output and, for automatic reply, canonical projected content, original C001 source/context link, run actor/sender/policy evidence and integrity digest. The proposal stages a completion; it is not terminal success and is not a delivery record. Use a separate final decision unique(company,owned root run), tenant-qualified to channel_reply_runs and that actual terminal execution. An automatic decision references its immutable proposal; a suppressed decision carries no publishable content/action. Unique identities reject conflicting content/reused keys and replay the exact stored decision. Only the authentic designated-root link participates; passive contexts, observer/manual/scheduled/child/sample runs create none.

Write the final decision in the existing shared completion transaction, alongside execution output/disposition, run progression and job/attempt settlement. Suppression still validates business output, skips projection/action/approval, and writes explicit suppressed decision atomically. Normal automatic output must satisfy the frozen channel contract before success. A rollback leaves no terminal success or final decision. No delivery/provider acknowledgement participates in business success.

## 2. Explicit final-effect policy and trusted origin

Actual baseline has no channel final-approval configuration. Add an optional typed approval policy to channel reply settings, separate from the subject/body projection. Use the established static user-reviewer/deadline shape, max16 reviewers, current eligible privileged company reviewers, and existing bounded validation. Extend configuration CAS and immutable ingress context capture to freeze it; absence means the current built-in workflow messaging policy, not a model-selected exception. Existing configured channel ownership is the explicit workflow-level final-message grant; it does not manufacture an agent tool binding or relax any existing agent-origin/explicit-action checks.

Represent this effect with a typed channel-final invocation/publication origin, tied to its proposal, root link and exact content/source/destination scope. Reuse FrozenAction canonical/digest/current messaging policy and approval evidence. Final actions cannot be dispatched through the active-workflow STEP/model-tool entry points; those retain their existing source/grant/fence checks. Dedicated final authority loads the immutable C001 grant and current company/channel/thread messaging authority. It must not claim to be an agent tool or invent an active workflow fence. Extract shared message authority checks rather than duplicate their rules.

The approval policy is independent of the selected responder identity: edits to selection cannot redirect a frozen response. Capture a distinct approval-policy fingerprint. Current changed/revoked send authority or policy can refuse pending publication visibly; completed workflows stay succeeded. If a proposal's required policy changes before finalization, reject stale evidence through the existing failure/error route rather than silently authorize or repeatedly reopen approvals. Looser policy never removes an already-frozen approval requirement. No stale approval or replacement communication is synthesized after success.

## 3. Stage and approve the actual terminal completion

Extend shared batch_commit::complete with an internal typed outcome (advanced with successor, or parked for final approval). Trace/adapt pure batch, fenced IO, waits/children, decisions and recovery. Successful committed receipts remain receipts only for actual completion; parked callers expose waiting/absence of success, not a fabricated terminal receipt. Final-error handling never creates a success decision. Preserve deadlines, ownership checks and uncertain-commit observation.

When approval is required, persist exact validated business output, completion route/step and canonical action proposal under the current real CompletionOwner (Pure/Fenced/Parked), create an existing protected-action decision/wait/private reviewer notice, and settle/park its actual job/attempt in the same transaction before run success. Reuse the existing decision table, formal submission, reviewer/notification preferences, digest/revision checks, expiry, first-valid ownership and error routing. Add only the channel-final invocation origin/evidence and the owner shape needed to park without an IO attempt; never fabricate an attempt or synthesize a user workflow step. Common notice/decision helpers operate on the caller's connection/transaction, not a nested transaction. Configure the existing DecisionNotices service for completion at startup; missing required notice configuration cannot commit success.

Approval reopens the same job through existing continuation accounting. A cohesive required finalization-resume port runs before worker handler dispatch, sees the persisted approved proposal, revalidates authority/policy and commits the saved completion plus decision through the shared writer. It never reruns the model/handler or projects edited content. All production and fake ports implement this explicitly, with no permissive trait default. Rejection/timeout calls the established original-step failure/error route; a later error-branch terminal execution has its own proposal. Proposal history is bounded by existing execution/continuation budgets.

## 4. Locking and resource ownership

Keep existing relative workflow lock order (run before execution/job) and completion fencing/deadlines. For an owned response, take the existing authority-owner locks in their established order before entering those workflow locks, then verify the same immutable root/source identity under the run lock. This outer prelock takes locks without making suppression require send permission; actual messaging authorization applies only to an automatic effect. Audit every completion/recovery/decision/wait entry against existing action authority and revocation order. Stage/commit may not acquire an authority lock in reverse order while another authority writer waits for its run. Preserve current bounded SQL waits/server/transaction deadlines; add actual completion/revocation/cancellation contenders.

Charge one logical final messaging action through the existing root action-budget mechanism, keyed by the immutable final invocation/proposal identity; duplicate staging, approval resumes and publication retries cannot replenish or double-charge it. Suppression spends no messaging action. No new generic budget or queue framework; existing active effects keep their own ownership ledgers.

## 5. Publication queue contract, without a second delivery state

An automatic final decision owns only canonical publication work: pending, claimed, published receipt or terminal publication failure. Suppressed decisions are never claimable. Add bounded durable polling/claim/settle operations with database uniqueness, generation/worker/expiry fencing, attempts/backoff and diagnostic codes, following message-intent conventions. Proposed bounds: page1..64, lease30s, max8 publication attempts, bounded lock/statement time; fair per-company selection and retry scheduling prevent a poison batch from being immediately claimable again. Replays use stable decision/publication identities; an unknown transaction outcome is observed by identity before retry.

A claim confers publication authority only for that immutable successful decision. It is not WorkflowFence. Lease expiry permits a fresh claimant; stale generations cannot settle. Store canonical message/delivery linkage when publication later commits, and read transport status only from the existing delivery queue. Local publication has a local receipt with no invented external send. p04 implements the shared route/planner/publication transaction and supervised draining; p03 provides the durable bounded work contract, not an in-memory callback owner.

## 6. Retention and sealed samples

Use tenant-qualified source/root/execution/action/decision links and immutable content/evidence guards. Preserve live staged approvals and pending/claimed final obligations through source/channel/thread/run deletion and retention. Failed/published audit data follows the existing bounded run/source retention; canonical messages/deliveries retain their existing lifecycle and cannot be orphaned by reply bookkeeping. Full-company teardown remains possible as in C001. Specify the actual cascade/restrict/guard paths in schema tests, including live obligations and published links.

Samples and runs without C001 ownership never enter production proposal/decision/claim/notice paths. Keep the sealed sample evaluator; typed local completion remains C002. No recipient/approval/destination/output flag in untrusted business output grants authority.
