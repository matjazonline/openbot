# CHS-P04-D1/r2 — Canonical publication and supervised recovery

Architecture proposal for whole p04 (04A/04B), before source edits. Original requirements: plan/03-channel-handles-send/04-channel-publication-and-delivery.md. Prerequisite accepted p03 R2 source849e88b7, architecture D1/r2; C001/C002/C003r2 remain binding. Targeted-only verification.

## Persistent identity and shared pipeline

A terminal run cannot use the existing explicit-message ledger: workflow_action_dispatches requires a genuine active job/attempt, and workflow_message_actions requires that dispatch and an effect wait for external delivery. Preserve these guards and generic origin refusal. Final publication is authorized only by the committed owned-root decision, its immutable typed ChannelFinal proposal/integrity/action and a current ReplyPublicationClaim. Never synthesize WorkflowFence, attempt, agent origin, workflow step, or dispatch marker.

Use the existing final decision's message_id and add a nullable tenant-qualified delivery_id as its publication receipt/link (no second transport state or action receipt). Require published iff canonical message exists; delivery_id is permitted only in published external-email form. Amend p03's placeholder published-link proof, which currently joins workflow_message_actions, to validate the real final-decision/proposal/source/canonical/thread/delivery relationship instead. The proposal invocation remains the stable logical publication key (also composer source_key), counted once by the existing128-slot reservation. No new slot/debit or dispatch row; suppression remains unclaimable.

Extract the existing application message planning into one shared MessagePlanner consumed by explicit MessageActions and final-reply publication. Planner accepts purpose-specific identity (company, invocation), parsed arguments/content and MessageRoutes; reuse email/in-app/internal routing, renderer/correlation checks, audience, reply threading, original channel sender alias, relay/hop facts, and transport ports. Frozen route decoding is strict (no fallback/unknown transport). Do not recreate a channel-only email planner.

Extract the canonical destination writer from message_publish::write_destinations_on so both origins call the same thread/message/correlation/delivery insert operations in the caller's transaction. Explicit origin still writes its own existing action/destination/receipt/wait rows and requires its real fence; final origin links directly through its decision receipt. Shared RouteCheck authorization is reused. MessageStampSource::Workflow still stamps the saved run's content level, including a succeeded run. The canonical writer is storage only; entry-point owners supply their distinct authorization/fencing.

## Publication port and atomic transaction

Add required cohesive application ports for loading a claimed immutable draft/observing a saved receipt and committing a planned final reply. No default correctness methods. Load verifies company/run/proposal/integrity and actual live claim before returning internal frozen content; an already published result returns its stored receipt. Draft carries typed final origin, original source, invocation, exact content and route, without fresh model/output/projection/binding reads. Composer executes outside the write transaction and calls no provider.

Commit serializes sorted actual account set (actor/requester/frozen reviewers) then company, run, final decision and later source/recipient/release facts. Reuse p03 prelock/current source-policy authority and knowledge_release helpers; extract typed policy/source checks as needed instead of matching error text or duplicating rules. Require real designated root, succeeded terminal execution/business result, no sealed sample, exact immutable proposal/action digests/origin, and a live matching worker/generation/attempt/expiry claim.

Recheck current messaging grants, company/channel/thread access, original source association, active responder policy equality, and current plus frozen knowledge-release/recipient facts. Freeze content/destination remains authoritative; a current responder/contract edit cannot redirect or regenerate a committed reply. Compare current routing authority with frozen source/sender/recipient/thread facts; changed concrete route refuses rather than substitutes. Missing source follows existing retention/refusal policy. Approval-required proposals must retain the exact formal approved decision, digest, action, source and completed wait, submitted within its original deadline. Recheck current reviewer eligibility/privilege/clearance; do not materialize a new deadline. Approval and workflow deadlines bound their original human submission/execution. After a valid business success they remain historical facts: neither elapsed deadline refuses final publication, safe delivery retry or provider entry. Only the current publication/delivery lease bounds its own work. Current authority/policy/source/release revocation and explicit delivery cancellation still stop new effects. No new final-expiry deadline or expired diagnostic is introduced.

Validate one Reply destination's canonical content, source, thread/channel, frozen recipients and InAppOnly/internal/email shape before writes. Commit canonical message, association/correlation, optional existing transport delivery, and published decision receipt atomically; require exact tenant/message/delivery and proposal linkage in SQL. No external fallback for internal/InAppOnly, quiet/unowned or sealed sample runs. SQL constraints/guards backstop provenance and shape; new receipt fields are immutable after published.

Use p03 seven-second storage operation bound (including acquire/commit), lock2s/statement5s. Recheck claim at the end; add a deferred publication constraint using OLD claim expiry so COMMIT after lease expiry rolls back message, delivery and receipt together. Current permission/source locks remain held through commit. Lost acknowledgement is observed via the same stored receipt; duplicate/stale claimants cannot create another effect. Refusal settles publication only, never reopens or changes business success. Authority/policy/release/invalid evidence are typed terminal diagnostics; operational errors retry through the existing bounded claim/backoff.

## Delivery admission, retention, cancellation

Final linkage must be recognized by the existing delivery queue before parent/part locks. A published final may proceed under its succeeded run and exact frozen authority/approval/release evidence; explicit messages retain their active-run/lease requirements. Enforce company/account -> run -> source/release -> delivery parent/part order consistently. Before each new provider entry, recheck current final authority and source/policy/approval/release, using its succeeded root and immutable final grant. Do not apply the old execution deadline to this origin. Refusal uses existing WorkflowRevoked cancellation semantics; explicit messages keep their own WorkflowExpired/active-run behavior. No provider call is made after a refusal. Delivery state/parts/provider receipts stay solely in the existing delivery queue.

Protect pending/claimed final decisions and published final links with unresolved delivery from owner/run retention; update storage eligibility as well as SQL run-deletion guard so protected work is skipped without poisoning retention pages. Preserve suppressed/failed/published decisions while their run survives (accepted F1 correction). Delivery/canonical/source links stay tenant-qualified; no independent evidence deletion. Permit existing whole-owner retention after resolved terminal delivery and full-company teardown. Do not remove a root while an ambiguous delivery still requires its evidence.

Cancellation racing terminal completion is decided in the original workflow transaction. After success, workflow cancellation cannot rewrite success or claim a recall. The existing delivery cancellation primitive stops unstarted pieces, retains accepted multipart pieces, and records intent on in-flight/unknown calls; test it against final-linked deliveries. User-facing controls/readers are phase06; this phase provides/verifies the same underlying cancellation semantics, not a separate workflow cancellation engine. Delivery retry targets the same canonical message/parts and never reopens or regenerates the workflow. Unknown calls are not automatically resent.

## Final parent/part transitions and recovery ownership (F2)

The direct final receipt is also an explicit origin in every relevant delivery data guard. Extend workflow_message_delivery_transition_guard and workflow_message_part_transition_guard to recognize the tenant-qualified published final decision's delivery_id as well as the existing workflow_message_destinations origin. Use one shared ownership predicate where appropriate; require final and explicit delivery links to be disjoint and final link unique. Do not let the new origin hit the existing early return. Preserve delivered/dead-letter parent and delivered/dead part immutability, including accepted multipart pieces; retain owned part evidence against independent deletion while its parent/owner survives, with legitimate whole-owner/parent and company cascades permitted. Verify SQL-only negative transitions/deletion as well as runtime behavior.

For final-linked outcome_unknown parent/parts, p04 rejects every exit (to delivered, dead/dead-letter, retryable or sending) without a genuine final-origin evidence owner. This phase introduces no such evidence/reopen owner. Existing workflow_action_evidence, workflow_message_delivery_reopens and settle_unknown_delivery_on remain exclusive to genuine explicit dispatch/destination ownership; final-origin SQL/API attempts to use them must be rejected, never supplemented with fake dispatch/attempt/destination rows. The shared guard identifies the real origin before applying its evidence rules. A final unknown result remains inspectable and protects its owning run from retention.

Supported p04 recovery: ordinary known safely retryable provider failures use the existing same-delivery/part queue, backoff and attempt ceiling; accepted pieces are skipped. Stale publication claims are independently recoverable and lost publication acknowledgements observe the same canonical receipt. Unknown provider calls are quarantined, never automatically resent or relabelled successful. Existing by-delivery cancellation can stop unstarted work and record intent on in-flight/unknown work; it cannot remove unknown truth or claim recall.

Phase06 owns bounded authorized views and controls. Publish this explicit consumer contract: known-safe delivery controls must target the same canonical message and current authority; final unknown rows expose attention/status/links and no blind resend or unsupported proof-settlement control. Adding any future final-specific evidence/reopen transition would require a separately reviewed real final-origin proof owner; it is not implied by exposing current explicit-action reconciliation controls. No new generic evidence queue/state machine is added in p04.

Generic transport status/SSE attention notifications and delivery-worker monitoring already operate on message_deliveries and cover final links. Existing workflow_message_delivery_events/action-receipt consumers remain explicit-action history; do not insert final events with invented action foreign keys. Emit the final publication/link event with its actual run/message/delivery IDs and rely on existing transport status for later outcomes. Phase06 readers join the final receipt directly. Audit relation-bound guards, events, receipt consumers, deletion and retention/reopen predicates as one ownership boundary.

## Supervision and work budgets

Add one final-publication worker to WorkflowEngine's retained spawn handles and shutdown token. Durable one-second polling is sufficient after lost wakeups/reconstruction. Claim/process at most2 responses concurrently using p03's page2 tenant-fair claims, lease30s/max8/backoff; no generic queue framework or detached task. Bound full publication processing20s, composer5s and storage7s, all within the lease. On shutdown cancel/await the actual processing futures, attempt bounded3s release of held unpublished claims; failed/uncertain releases remain fenced until expiry. A full batch moves rows out of immediate eligibility; poison rows cannot hot-spin or starve quiet tenants.

Account for two publisher database users by raising reserved connection headroom10->12 (a stricter startup capacity requirement; default pool20 still supports default2 workflow slots), preserving configured maximum slots. Update boundary tests/docs for actual startup validation. No stack/resource ceiling raised. Box substantial planner/provider seams and keep stock2MiB tests.

Also close the traced existing delivery-worker shutdown gap with explicit call-versus-settlement phases. WorkflowEngine/main retains the worker handle; no relay or provider task is detached. The delivery owner observes its original broadcast subscription while an active drain uses one mutable subscription created before work, passed through claims/delivery/provider boundaries rather than resubscribing after a signal. Stop new work after shutdown is observed. Adapt drain_once's private caller signature where necessary (actual callers run(), late_completion_tests and knowledge_e2e_support), without changing port guarantees.

A provider call is selected against shutdown and a30s real call deadline (below production120s lease); cancel/drop the actual sender future on interruption/deadline. A durable begin_part/request_started_at already exists: interruption or timeout is OutcomeUnknown, not a fabricated safe retry. When a provider result has already returned, preserve that actual result and enter settlement; if result and signal are both ready, prefer the actual result. Shutdown does not immediately drop a known-result commit.

On shutdown, give the active drain at most3s to persist a known returned result or the interrupted-call unknown through the existing fenced complete_part transaction and release unstarted held work. Do not start another provider part. If storage/claim settlement cannot finish inside that bound, cancel/await the owned drain and leave its existing durable lease/entry markers for expiry/reaper recovery; an unacknowledged commit is observed from stored truth, not fabricated. Already committed accepted multipart pieces remain accepted. In-flight request markers with no stored result recover as unknown; unstarted claims safely recover through the normal lease path. No orphan async task survives the join. Normal provider timeout also attempts the same honest unknown settlement.

Required lifecycle tests distinguish shutdown before provider entry, during a cancellable sender, after a known result before its DB settlement, after committed multipart acceptance, and while settlement exceeds the drain grace. Prove known results commit when storage completes within grace; when acknowledgement/storage remains uncertain, retain honest durable recovery and never blind resend.

Bounded structured events/metrics contain IDs/status only and reuse existing retry/lease-loss/dead-letter/unknown/stuck categories. No payload, recipient lists or tokens in logs/labels.
