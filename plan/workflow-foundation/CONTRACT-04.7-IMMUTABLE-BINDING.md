## Decision and original criterion

BRIEF§2 requires settlement to reload exact operation, marker, entries and revision and refuse stale proof; this remains required even where ordinary owners cannot change particular bytes. Do not manufacture a successful immutable UPDATE to demonstrate a stale-proof branch. The complete inventory below distinguishes same-identity replacement (blocked), additive/live-owner transitions (reachable), and destruction of the owning scope (reachable, missing-authority refusal). Missing owner is not StaleSnapshot and does not create an immutable refusal receipt. No requirement is waived, no trigger weakened, no applied migration edited.

Paths in the inventory are repository-relative. `persistence/` abbreviates `src/adapters/persistence/`; `application/` abbreviates `src/application/`. Migration filenames are under `migrations/`.

The inventory covers committed ordinary application/SQL-owner transitions for an already captured snapshot. Privileged DDL/TRUNCATE, disabled triggers, copied historical facts, manual UUID resurrection, applied migration edits and mutation of an internal snapshot token are not sanctioned lifecycle constructors. This contract makes no claim that arbitrary superuser corruption is impossible. Mutable run/resources/policy are independently validated by restore/authority; they are not an alternate writer for workflow_action_intents.operation.

## Binding at the actual settlement boundary

`application/workflow/actions/reconciliation/contracts.rs:103–141` hashes exact scope/subject/original marker UUID+created_at/operation digest/sorted entry provenance. `persistence/workflow/action_reconciliation/mod.rs:66–136` commits the authorized snapshot before provider I/O; :148–159 locks and restores current head; :170–209 reloads exact scoped intent and frozen run authority; :211–219 reloads original remote marker by full provenance. `settlement.rs:5–79` repeats company→run→association→execution/job/resource authorization and restore before recording any evidence/grant. `settlement.rs:115–152` compares revision, recomputed coverage and full saved_operation and returns StaleSnapshot on mismatch. Keep both digest and full-operation comparisons: context can differ without operation digest changing.

Therefore an admitted same-owner operation/marker-byte change has no legal committing constructor today; defense remains in code and future writers must retain this check. Reachable entries/revision differences use StaleSnapshot. If owner deletion wins after verification, `authority.rs:9–36` returns missing company (or `head_on:148–159` missing run if company survives) before any fact/command write. Company deletion after settlement instead removes history by accepted owner cascade; this is not a stale proof or reopened run.

1. Use isolated DB and existing genuine Reconcile pending-provider/parked fixture. Assert original company/run/execution/job/intent/marker absent. This proves snapshot locks were released and an actual supported lifecycle transition occurred. Existing owner-lifecycle test :174–237 proves sequential company cascades, not this paused settlement.

No evidence, refusal command, grant, consumption, job or owner resurrection. Repeating original command must still be NotFound with no additional verifier call/delta. Do not call missing-scope claim helpers that expect a surviving run; absence plus no state delta proves no scheduling. Preserve provider ledger state according to its actual fixture ownership; compare it in baseline, never manufacture external-effect deletion.
4. Run focused stock2MiB/defaultparallel, required affected regression/static/SQLx gates, independent actual-code review; root alone accepts. If real owner deletion cannot commit with this fixture, report exact guard and constructor conflict to architecture check rather than bypassing it.
